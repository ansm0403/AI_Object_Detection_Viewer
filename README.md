## 2D 뷰어와 3D 뷰어가 다르게 보이는 이유

앱을 처음 보면 두 뷰어가 같은 물체를 표현하는데 위치·거리감이 다르게 느껴질 수 있습니다.  
**이는 버그가 아닙니다.** 두 뷰어가 완전히 다른 카메라 위치와 시야각으로 같은 공간을 찍기 때문입니다.

### 에고 차량이란?

자율주행 데이터에서 **에고(Ego) 차량**은 카메라·LiDAR 센서를 달고 실제로 주행한 *기록 차량 자체*입니다.  
3D 뷰어의 원점(0, 0, 0)이 항상 에고 차량이고, 다른 모든 물체의 위치는 "에고로부터 몇 m 앞/옆"의  
상대 좌표로 표현됩니다.

### 2D 뷰어 — 에고 정면 수평 카메라

에고 차량 앞에 달린 카메라(CAM_FRONT)가 찍은 사진입니다.  
전방 약 **70° 범위**만 담기며, 물체가 카메라에 가까울수록 이미지에서 크게 보입니다.

```
[에고 차량] ─── 카메라 시야(약 70°) ───▶

╔═══════════════════════════╗
║    나무  (도로)  나무       ║  ← 2D 뷰어에 보이는 것
║         🚗                 ║    (전방 70° 범위만)
╚═══════════════════════════╝
```

### 3D 뷰어 — 에고 뒤에서 비스듬히 내려다보는 시점

3D 뷰어의 카메라는 에고 차량보다 뒤쪽 높은 위치에서 씬 전체를 내려다봅니다.  
자동차 레이싱 게임의 **3인칭 시점(체이스 캠)** 과 비슷합니다.

```
    👁 [3D 뷰어 카메라 — 에고 뒤+위]
      ╲ (비스듬히 내려다봄)
       ╲
    ────────────────────────────
    [에고 차량] ──▶ [🚗] [🚌] [🚶]   ← 3D 뷰어에 보이는 것
    ────────────────────────────        (에고 주변 전체가 보임)
```

### 같은 물체가 왜 다르게 느껴지는가

| | 2D 뷰어 | 3D 뷰어 |
|---|---|---|
| 카메라 위치 | 에고 정면, 수평으로 찍음 | 에고 뒤+위, 비스듬히 내려다봄 |
| 보이는 범위 | 전방 70° 만 | 에고 주변 공간 전체 |
| "가깝다"의 기준 | 이미지에서 차지하는 픽셀 크기 | 3D 씬 전체에서 박스가 얼마나 두드러지는가 |

에고 **15m 앞**에 있는 물체가 **2D에서는 화면 중앙을 크게 차지**하지만,  
**3D에서는 씬 전체 중 작은 박스 하나**로 표시됩니다.  
좌표 데이터는 완전히 동일하고, 카메라 시점이 달라 같은 공간이 다르게 표현되는 것입니다.

> **예시:** 에고 앞 코너를 돌아 진입하는 차량이 2D에서는 "이미 꽤 가까이 진입"처럼 보일 때,  
> 3D에서는 "이제 막 코너를 돌아오는 중"처럼 보일 수 있습니다.  
> 두 뷰어가 보여주는 절대 거리는 같지만, **화면에 얼마나 두드러지는가의 기준이 다릅니다.**

# AI Object Detection Viewer

AI 객체 탐지 결과를 2D 이미지와 3D 공간에서 동시에 탐색하는 데이터 시각화 뷰어입니다.
사용자가 2D에서 객체를 클릭하면 3D에서도 같은 객체가 강조되고, 반대도 성립합니다.

**COCO(추정 3D)와 nuScenes(실측 3D) 두 데이터셋을 데이터셋 스위처로 전환**하며 비교할 수 있습니다.
COCO 프레임은 2D bbox에서 *추정한* 3D를, nuScenes 프레임은 실제 LiDAR로 *측정한* 3D 박스와 점구름을
보여주며, 각 프레임은 `Estimated` / `Measured` 배지로 깊이의 출처를 명시합니다.

MVP 이후에는 nuScenes 쪽을 **인지(perception) 데이터의 품질을 보는 도구**로 넓혔습니다. 맨 위 줄에서 모드를 고릅니다.

- **Review** — 3D 정답 박스를 하나씩 검수합니다(승인 / 반려 / 판단 불가, 사유, 저장, 내보내기).
- **Evaluate** — 2D 카메라 탐지 모델(YOLOv8n)의 결과를 정답과 대조해 채점하고, 놓친 물체가 3D 공간의 어디에 있었는지 봅니다.
- **Explore** — 조건으로 프레임을 찾습니다("20m 안에 보행자 5명 이상", "모델이 15개 이상 놓친 프레임").

실무 도구의 핵심 흐름을 **1인용으로 재현**한 것입니다. 백엔드, 로그인, 여러 사람의 동시 작업은 없습니다.

## 주요 기능

### 멀티뷰 & 선택 동기화 (두 데이터셋 공통)

- **2D↔3D 멀티뷰 선택 동기화** — 2D / 3D / 객체 리스트 / 분석 패널이 모두 동일한
  `selectedObjectId`를 단일 source of truth로 공유
- **데이터셋 스위처 + Estimated/Measured 배지** — COCO(추정)와 nuScenes(실측)를 토글로 전환,
  프레임마다 깊이의 출처를 정직하게 표기
- **필터링** — confidence 슬라이더(COCO) ↔ 거리(미터) 슬라이더(nuScenes)를 데이터셋별로 스왑 +
  클래스 토글. 모두 셀렉터 레이어에서 일괄 처리
- **스크롤 없는 작업 화면** — 객체 목록 · 3D 뷰 · 카메라 이미지 · 분석 패널 · 타임라인을 한 화면에 고정
  배치. 1440×900과 1280×720에서 페이지 스크롤이 없고, 내용이 넘치는 목록과 분석 패널만 패널 안에서
  스크롤됩니다. 화면 폭 1024px 미만에서는 세로로 쌓입니다
- **객체 목록** — 3D 박스 전체를 나열. nuScenes에서는 카메라 이미지에 보이는 박스인지(아이콘)와
  자차로부터의 거리(m)를 함께 보여주고, 32자 ID는 앞 6자리로 줄여 표시
- **프레임 타임라인** — COCO는 썸네일 스트립. nuScenes는 프레임마다 막대 하나인 눈금 막대라서 한 장면의
  41프레임이 스크롤 없이 한 줄에 들어갑니다(막대 높이 = 박스 수, 마우스를 올리면 썸네일)
- **분석 패널** — 선택된 객체 정보 카드, confidence 히스토그램(슬라이더 임계값 오버레이),
  클래스 카운트 바(클릭 시 클래스 필터 토글)

### COCO — 추정 3D

- **COCO 어노테이션 파서** — `images` / `categories` / `annotations`를 내부 `Frame[]`로 변환,
  잘못된 bbox / 카테고리 / score를 안전하게 스킵
- **2D bbox → 3D 좌표 추정** — bbox 중심을 (x, y), 면적을 z(작을수록 카메라에 가까움)로 매핑.
  이는 추정값일 뿐 실제 깊이가 아님을 UI/배지로 명시
- **실측 confidence 분포** — ground truth가 아니라 YOLOv8n 추론 결과(`score` 0.0–1.0)를 사용하므로
  confidence 슬라이더 / 히스토그램이 실제 의미 있는 분포를 보여줌

### nuScenes — 실측 3D

- **실측 3D 박스 (쿼터니언 회전)** — nuScenes의 global 좌표 어노테이션을 `global → ego → three`로
  변환하고 회전을 쿼터니언으로 적용 (주차된 차량들이 일관된 대각 방향으로 정렬)
- **3D→2D 투영** — 3D 박스를 카메라 intrinsic으로 이미지 평면에 투영해 2D 박스를 생성.
  2D · 3D가 같은 `instance` 토큰에서 나오므로 **id가 동일**(Immutable Rule #1 유지)
- **실측 LiDAR 점구름** — `.pcd.bin`을 디코드해 voxel-grid로 데시메이션(~6.5k pts/frame),
  박스와 정확히 정렬, 깊이별 색상 인코딩
- **거리(미터) 필터** — 실제 측정 거리이므로 "50m 밖 숨기기" 같은 필터가 의미를 가짐
- **confidence 표시 없음** — nuScenes 박스는 사람이 라벨링한 실측 어노테이션이라 모델 점수가 없음.
  파서가 타입을 맞추려 채우는 `1.0`을 점수처럼 보여 주지 않도록, 2D·3D 라벨은 클래스만, 객체 리스트·
  선택 패널은 "—", 히스토그램은 안내문으로 대체 (Rule #6 — 추정·실측을 과장하지 않는다)
- **시퀀스 추적 + 자동재생** — `instance` 토큰이 프레임 간 유지되어, 자동재생(~2Hz) 시
  **같은 객체가 실제로 움직이는** 것을 추적. 객체가 사라졌다 다시 나타나면 다시 강조됨
- **카메라 Follow 모드 + 프레임 간 box tween** — 선택 객체를 중심에 두는 옵트인 카메라 모드,
  키프레임 사이를 lerp(위치)/slerp(회전)로 부드럽게 보간
- **카메라 6대** — 차 지붕의 카메라 6대(앞, 앞 왼쪽·오른쪽, 뒤, 뒤 왼쪽·오른쪽)의 사진을 모두 씁니다.
  박스를 고르면 그 박스가 보이는 카메라의 사진으로 자동으로 바뀌고(`[` `]`로 옆 카메라), 카메라마다
  촬영 시각이 조금 달라 사진마다 그 순간의 차 위치로 투영합니다
- **장면 10개를 나눠 받기** — 목차 → 화면의 장면(박스) → 나머지 장면(뒤에서 2개씩) → 프레임을 열 때 그
  프레임의 LiDAR 점과 사진. 첫 화면에 필요한 데이터는 압축 기준 210KB입니다(전체는 152MB)

### nuScenes — 3D 박스 검수

실무 라벨링 도구의 검수 흐름(판정 → 사유 → 이어서 하기 → 내보내기)을 1인용으로 재현한 기능입니다.
nuScenes의 실측 3D 박스에만 동작하며, 3D가 추정값인 COCO에는 검수 UI가 없습니다.

- **판정과 사유** — 박스마다 승인 / 반려 / 판단 불가를 남깁니다. 반려에는 사유(클래스·크기·위치·방향·
  객체 아님·기타, 여러 개 선택)와 메모를 붙일 수 있습니다. 같은 객체라도 박스는 프레임마다 따로
  그려진 것이므로 판정의 단위는 **(프레임, 객체)** 쌍입니다
- **단축키와 대기열** — `A` `R` `U` 판정, `J` `K` 이동, `1`~`6` 사유, `N` 다음 프레임. 승인·판단 불가는
  다음 미검수 박스로 자동 이동하고 반려는 사유를 고르도록 머뭅니다. 목록은 장면 순서 / LiDAR 점 적은
  순 / 카메라별 / 판단 불가 먼저로 정렬할 수 있습니다
- **판단 근거** — 박스 안 LiDAR 점 개수와 가려짐 단계(nuScenes가 기록한 값), 그 박스를 보는 카메라를
  버튼 위에 보여 주고, 카메라 칸은 선택한 박스 주변을 확대해 **3D 박스를 사진에 투영한 선**(앞면 표시)을
  그립니다. 어느 카메라에도 보이지 않는 박스는 그렇다고 안내합니다
- **저장과 내보내기** — 판정은 브라우저(localStorage)에 저장되어 새로고침 후에도, 장면을 바꿔도 이어집니다.
  검수 결과는 모든 장면을 한 파일(JSON / CSV, 줄마다 장면 이름)로 내려받을 수 있습니다. 저장이 안 되는
  환경에서는 화면에 표시합니다
- **연습 모드** — nuScenes 정답은 품질이 높아 대부분 "승인"입니다. 도구가 오류를 잡아내는지 보기 위해,
  박스 일부(프레임당 약 10%)를 정해진 시드로 일부러 어긋나게 만든 연습용 데이터와 채점(찾음 / 놓침 /
  헛짚음)을 제공합니다. 원본 파일은 바뀌지 않고, 켜져 있는 동안 화면에는 `Practice · labels modified`가
  표시되며("Measured"로 표시하지 않음) 판정도 원본 기록과 따로 저장됩니다

### nuScenes — 카메라 탐지 평가 (Evaluate)

사진에 2D 탐지 모델(YOLOv8n)을 미리 돌려 두고, 그 결과를 정답(3D 박스를 사진에 투영한 사각형)과 대조합니다.
시험 채점에 비유하면 사진이 문제, 모델의 박스가 답안, nuScenes의 박스가 정답지입니다.

- **찾음 / 놓침 / 헛짚음 / 채점 제외** — 결과 목록, 사진 위의 정답(점선)과 모델 박스(실선), 3D 박스의 색이
  모두 같은 결과를 보여 줍니다. 결과를 고르면 "왜 그렇게 채점됐는지" 한 줄이 나옵니다
  (예: 모델이 그 자리에 박스를 냈지만 점수가 기준 아래)
- **놓친 물체의 3D 위치** — 정답 박스에는 LiDAR로 잰 실제 거리가 있어서, 모델이 놓친 물체가 3D 공간의
  어디에 있었는지와 거리별 탐지율을 볼 수 있습니다(2D 데이터셋만으로는 할 수 없는 분석입니다)
- **규칙을 화면에서 바꿔 보기** — 점수 기준(Min score) 슬라이더와 **겹침 기준(IoU) 0.3 / 0.5** 고르기.
  패널에는 항상 조건 한 줄이 함께 나옵니다: `yolov8n · no fine-tuning · input 1280 · score ≥ 0.25 · IoU ≥ 0.3`
- **보고서 창(Report)** — 전체 장면의 숫자를 한 화면에: 조건, Precision / Recall, 주행 단위 표,
  같은 거리끼리의 낮/밤, 확인되지 않은 헛짚음의 수. 숫자와 한계는 아래 [카메라 탐지 평가 결과](#카메라-탐지-평가-결과-nuscenes-mini-전체)에 있습니다
- **헛짚음 표본 검수(Sample check)** — "근처에 정답이 없는 헛짚음"은 모델이 틀린 것일 수도, 정답이 빠진 실제
  물체일 수도 있습니다. 그런 박스에서 **무작위 표본**(다시 열어도 같은 박스)을 뽑아 한 장씩 판정하고
  (`A` 진짜 물체인데 정답 빠짐 / `R` 모델이 틀림 / `U` 애매함), 결과를 "100개 중 N개 → 전체의 약 X~Y%"처럼
  **표본 크기와 범위가 붙은 추정**으로 보여 줍니다. 판정은 파일로 내보낼 수 있습니다

### nuScenes — 장면 탐색 (Explore)

- **조건으로 프레임 찾기** — "보행자가 20m 안에 5명 이상", "LiDAR 점이 없는 박스 10개 이상", "밤 장면",
  "모델이 15개 이상 놓친 프레임", "근처에 정답 없는 헛짚음 3개 이상". 조건은 여러 개를 함께 걸 수 있습니다
- **찾은 이유가 화면에 보입니다** — 조건이 센 박스만 3D에서 색을 유지하고, 목록의 숫자 / 패널의 숫자 /
  색칠된 박스 수가 같은 함수에서 나옵니다. `J` `K`로 결과를 넘기면 장면이 바뀌어도 따라갑니다
- 미리 만든 색인 없이, 메모리에 올라온 박스를 화면과 같은 함수로 훑습니다(조건 하나에 404프레임 약 0.5ms,
  Node에서 잰 값)

### 3D 뷰어 인터랙션

- **점구름 깊이 색상 인코딩** — 각 점을 z(깊이)로 색칠해 평면 회색 덩어리가 아닌 입체로 읽힘
- **3D 호버 강조** — bbox 위에 마우스를 올리면 강조 + 커서 `pointer` 피드백
- **`<Html>` 앵커 라벨** — 객체에 매달려 카메라 회전/줌을 따라다니는 정보 말풍선(클래스 + confidence)

## 카메라 탐지 평가 결과 (nuScenes-mini 전체)

> **읽기 전에.** 아래 숫자는 "이 조건으로 이 데이터를 채점했을 때 관찰된 값"입니다. **모델의 성능 수치가 아닙니다.**
> 조건과 한계를 숫자와 함께 적었고, 화면의 보고서 창(Evaluate → Report)에도 같은 내용이 나옵니다.
> 모든 숫자는 앱의 채점 코드가 저장소의 파일로 계산한 값이며 단위 테스트가 고정하고 있습니다(2026-11-27 기준).

### 조건

| 항목 | 값 |
|---|---|
| 모델 | YOLOv8n (Ultralytics 8.4.51의 공개 가중치 `yolov8n.pt`. COCO로 학습된 것을 그대로 썼고 **nuScenes로 추가 학습하지 않았습니다**) |
| 입력 | 원본 사진 1600×900을 긴 변 1280으로 줄여 입력(`imgsz=1280`. YOLO의 기본값은 640) |
| 데이터 | nuScenes-mini 전체: 장면 10개, 키프레임 404개, 카메라 6대 → 사진 2,424장 |
| 정답 | nuScenes의 3D 박스를 각 사진에 **투영한** 2D 사각형. 사람이 사진에 그린 2D 박스가 아니며 물체보다 헐겁습니다 |
| 채점 단위 | 사진 한 장. 두 카메라에 찍힌 물체는 두 번 셉니다 |
| "찾음"의 기준 | 같은 클래스, 모델 점수 0.25 이상, 겹침(IoU) **0.3** 이상. 표준 기준인 0.5의 숫자도 함께 적습니다 |
| 평가 클래스 | 사람, 자전거, 차, 오토바이, 버스, 트럭 (모델과 데이터셋이 둘 다 말할 수 있는 것) |
| 채점 제외 | 가시성 0~40%인 정답 5,278개(찾아도 놓쳐도 세지 않음), 자전거 거치대 안의 자전거·오토바이 모델 박스 209개(IoU 0.3 기준) |

### 전체

| 겹침 기준 | 찾음 | 놓침 | 헛짚음 | Precision | Recall |
|---|---|---|---|---|---|
| **IoU 0.3 (이 도구의 기본)** | 6,726 | 5,292 | 3,514 | **65.7%** | **56.0%** |
| IoU 0.5 (표준 기준) | 5,462 | 6,556 | 5,231 | 51.1% | 45.4% |

- **기준 하나로 전체 숫자가 10~15%p 움직입니다.** 정답이 헐거운 사각형이라 0.5에서는 맞게 찾은 것 일부가
  "놓침 1개 + 헛짚음 1개"로 세어집니다. 그래서 기본을 0.3으로 두었고, 화면에서 두 값을 오갈 수 있습니다.
- 채점한 정답 12,018개는 **서로 다른 물체 654개**가 되풀이해 찍힌 것입니다(프레임 간격 0.5초).
  서로 독립인 자료는 프레임 404개가 아니라 **주행 8번**입니다.
- 놓침 5,292개를 정답 쪽에서 보면(IoU 0.3): 모델이 그 자리에 박스를 냈지만 점수가 0.25 아래 2,031(38%),
  근처에 모델 박스가 없음 1,563(30%), 다른 클래스로 부름 1,253(24%), 겹침 부족 225, 다른 정답에 배정됨 220.
- 헛짚음 3,514개를 모델 박스 쪽에서 보면(IoU 0.3): **근처에 어떤 정답도 없음 1,452(41%)**, 다른 클래스의 정답 위 794,
  같은 클래스인데 겹침 부족 786, 이미 짝지어진 정답에 박스가 하나 더 482.
  (놓침의 구성과 헛짚음의 구성은 세는 방향이 달라 서로 더하거나 1:1로 대응시킬 수 없습니다.)

  32.7%에서 33.9%가 될 뿐입니다. 즉 **두 값의 차이 31.4%p 가운데 거리 분포로 설명되는 것은 1.2%p**입니다.

  주행 한 번입니다. 같은 지역의 낮 장면은 mini에 없습니다.
- 그래서 이것은 "YOLOv8n은 밤에 성능이 절반이 된다"는 말이 아닙니다. **원인은 이 자료로 밝혀지지 않습니다.**
  그 주행의 장소, 교통, 카메라 노출, 물체 구성이 모두 함께 들어 있습니다(예: 밤 장면에는 채점된 트럭 정답이 하나도 없습니다).
- 낮/밤은 nuScenes의 항목이 아니라 장면 설명 글("Night, …")에서 읽은 것입니다.

### 확인되지 않은 헛짚음과 표본 검수

"근처에 어떤 정답도 없는" 헛짚음 1,452개(헛짚음의 41%)는 모델이 틀린 것일 수도 있고, **nuScenes에 정답이 빠진
실제 물체**일 수도 있습니다. 뒤쪽이라면 그것은 데이터의 누락이고, 위의 Precision은 실제보다 낮게 계산된 것입니다.
눈으로 봐야만 가릴 수 있어서 도구를 만들었습니다.

- **방법.** 1,452개(점수 0.25 이상. IoU 0.3과 0.5에서 같은 박스들입니다)를 정해진 순서로 늘어놓고 고정 시드로 한 번
  섞은 뒤 앞에서부터 100개를 표본으로 씁니다(단순 무작위, 비복원). 다시 열어도 같은 박스가 같은 순서로 나옵니다.
- **판정.** `A` 박스 안에 실제 차량(또는 사람)이 있는데 정답이 빠짐 / `R` 모델이 틀림 / `U` 사진으로는 가릴 수 없음.
  `A`는 "모델이 세부 클래스까지 맞혔다"는 뜻이 아닙니다(트럭을 차라고 한 것도 `A`입니다).
- **결과를 쓰는 방식.** "100개 중 N개"와 95% 범위(Wilson 구간, 모집단 1,452개에 대한 보정)를 함께 적습니다.
  표본 100개에서 40%가 나오면 전체의 범위는 약 31~50%입니다(±9%p). 전체를 센 것처럼 쓰지 않습니다.
- **한계.** 한 사람이 960×540으로 줄인 사진으로 판정합니다. 같은 물체가 다음 프레임에 또 잡힌 박스가 섞여 있어
  실제 불확실성은 범위보다 조금 더 큽니다. 판정 결과로 Precision을 다시 계산하지는 않습니다(정답이 빠진 물체 중
  모델이 **놓친** 것은 셀 수 없어서, 한쪽만 고치면 치우친 숫자가 됩니다).
- **판정 결과 (2026-11-27, 표본 100개를 모두 판정).** 100개 중 **83개**에 실제 차량이나 사람이 있었고 그 사진에
  정답 박스가 없었습니다(`A`). 5개는 모델이 틀렸고(`R`), 12개는 사진으로 가릴 수 없었습니다(`U`).
  1,452개 전체로 넓히면 "정답 박스가 없는 실제 물체"는 **약 75~89%로 추정**됩니다(95% 범위. 표본에서 얻은 추정이고
  1,452개를 센 값이 아닙니다). "모델이 틀림"은 약 2~11%로 추정됩니다.
  - 판정한 사람은 저자 한 명이고, 판정 파일은
    [docs/evaluation/false-alarm-sample_20261127-1018.json](docs/evaluation/false-alarm-sample_20261127-1018.json)에
    있습니다(박스마다 장면, 프레임, 카메라, 좌표, 판정).
  - `A` 83개 중 62개는 높이 50px 미만(원본 1600×900 기준)의 작은 박스였습니다.
  - "정답 박스가 없다"는 이 프로젝트가 쓰는 정답(nuScenes 3D 박스를 사진에 투영한 것)이 그 사진에 없다는 뜻입니다.
    nuScenes에 그 물체의 라벨이 아예 없는 것인지, 투영에서 빠진 것인지(아래 한계 8)는 가리지 않았습니다.

### 한계

1. **독립인 자료는 주행 8번입니다.** 한 장면의 프레임은 0.5초 간격이라 같은 물체가 되풀이해 나옵니다. 밤은 주행 1번입니다.
2. **정답 2D 박스는 3D 박스를 투영한 헐거운 사각형입니다.** 그래서 겹침 기준이 표준(0.5)이 아니라 0.3이고,
   기준에 따라 전체 숫자가 10~15%p 달라집니다.
3. **Precision과 Recall은 점수 기준 0.25 한 점에서의 값입니다.** 기준을 내리면 Recall이 오르고 Precision이 내려갑니다.
   기준을 훑어 하나로 요약하는 값(AP)은 계산하지 않았습니다.
4. **이름만 다른 경우가 두 번 틀린 것으로 세어집니다.** 모델이 물체를 봤지만 다른 클래스로 부르면(트럭 ↔ 차 등)
   놓침 1개와 헛짚음 1개가 됩니다.
5. **헛짚음의 41%(근처에 정답이 없는 1,452개)는 표본 100개만 눈으로 확인했습니다**(위의 표본 검수). 나머지는 추정이고,
   그 결과로 Precision을 고쳐 계산하지 않았습니다.
6. **가시성 0~40% 제외는 물체 전체에 대한 값입니다.** nuScenes의 가시성은 카메라 6대를 합쳐 매긴 것이라, 사진 한 장에서
   잘려 보이는 물체가 채점에 들어갈 수 있습니다.
7. **입력 크기 1280은 고른 조건입니다.** 기본값 640에서는 Recall이 더 낮았습니다(앞 카메라 사진 10장으로 잰 값:
   640에서 43%, 1280에서 52%. 지금의 2,424장으로는 640을 돌려 보지 않았습니다).
8. **카메라 평면에 걸친 박스는 그 사진에 정답이 없습니다.** 차 바로 옆의 큰 물체가 그렇습니다. 찾음도 놓침도 아니게 되고,
   그 위의 모델 박스는 헛짚음으로 세어집니다.
9. **거치대 규칙은 이 프로젝트가 정한 구현입니다**(모델 박스의 중심이 거치대 사각형 안이면 뺍니다).
10. **nuScenes-mini는 공식 평가용 묶음이 아니라 맛보기 묶음입니다.** 가장 작은 YOLO를 추가 학습 없이 돌렸습니다.

### nuScenes 공식 평가와의 관계

nuScenes의 공식 탐지 과제는 **3D 박스**를 대상으로 하고, 겹침(IoU)이 아니라 **지면 위에서 본 두 박스 중심 사이의 거리**
(0.5 / 1 / 2 / 4m)로 예측과 정답을 짝짓습니다
([nuscenes-devkit의 탐지 평가 문서](https://github.com/nutonomy/nuscenes-devkit/blob/master/python-sdk/nuscenes/eval/detection/README.md),
2026-11-27 확인). 이 도구는 사진 위의 **2D** 박스를 IoU로 짝짓습니다. 대상과 방법이 모두 다르므로
**위 숫자는 공식 순위표의 수치와 나란히 놓을 수 없습니다.**

같은 문서에 따르면 공식 평가는 그 밖에도 다릅니다: 클래스마다 거리 한도가 있고(차 50m, 보행자 40m 등. 이 도구는
한도를 두지 않습니다), LiDAR / 레이더 점이 하나도 없는 정답을 빼며, 거치대 안의 자전거·오토바이를 정답과 예측
양쪽에서 뺍니다(이 도구는 예측 쪽만 뺍니다).

## 프로젝트 목적과 계기

자율주행 데이터를 시각화하는 프론트엔드 직무 공고를 접하면서 시작한 학습용 포트폴리오입니다.
**해당 공고는 이미 종료되었지만**, 직무에서 요구한 역량(3D 시각화, AI 데이터 도메인, 멀티뷰 동기화)을
실제로 구현해보는 것 자체가 목적으로 남았습니다.

기존 포트폴리오(호텔 예약, 쇼핑몰)에서는 다루지 못했던 **3D 렌더링**과 **AI 데이터 포맷 처리**를
직접 만져보면서, 프론트엔드의 영역을 한 단계 넓히는 것이 핵심 동기입니다.

처음에는 자율주행 데이터 전체(LiDAR / 센서 동기화 / 좌표계 변환)를 한 번에 다루기 어렵다고 판단해,
**범용 AI 데이터(COCO Object Detection)의 2D bbox에서 3D를 *추정*하는 것**으로 범위를 좁혀 MVP를
완성했습니다.

이후 MVP의 가장 큰 약점이었던 *"3D가 실제 측정값이 아닌 추정값"*이라는 꼬리표를 떼기 위해,
**nuScenes(자율주행 데이터셋)의 실측 3D 박스와 실측 LiDAR 점구름**을 추가했습니다.
COCO를 대체하지 않고 **데이터셋 스위처로 공존**시켜, "추정 → 실측"으로 나아간 과정 자체를
보여주는 것이 현재 프로젝트의 서사입니다.

## 기술 선택 시 고민했던 부분

### 1. Three.js 직접 사용 vs React Three Fiber

Three.js를 직접 쓰면 React 렌더링 루프 충돌, 메모리 수동 관리, Zustand 동기화 코드를 별도로
작성해야 합니다. R3F는 이 셋을 React 방식으로 흡수합니다.

**채택: R3F.** 단순한 타협이 아니라 React + 3D 조합에서 합리적인 선택이며, R3F를 배우면서
geometry / material / camera / lighting 같은 Three.js 핵심 개념도 자연스럽게 학습할 수 있다고 판단했습니다.

### 2. TanStack Query 미도입

데이터 소스가 정적 JSON입니다. 캐싱 / 무효화 / 재시도가 필요 없는 환경에서 라이브러리를
들이는 것은 명백한 오버스펙이라고 판단해 `useEffect + fetch + AbortController` 패턴만 사용했습니다.

### 3. Recharts 미도입

분석 패널의 confidence 히스토그램과 클래스 카운트 바를 처음에는 Recharts로 만들 계획이었지만,
프레임당 객체 ≤10개 / 차트 요소 ≤5개 규모에서는 **직접 작성한 SVG / CSS**로 충분했고,
의존성 / 번들 사이즈가 늘지 않는다는 이점이 컸습니다. 핸드-롤된 차트는 confidence 슬라이더와의
threshold 오버레이도 자유롭게 그릴 수 있었습니다.

### 4. 코어 로직과 React의 분리

COCO/nuScenes 파싱, 2D→3D·3D→2D 좌표 변환, 셀렉터는 모두 `lib/` 아래의 순수 함수입니다.
React 컴포넌트와 Zustand store는 이 함수들의 호출자일 뿐, 도메인 로직을 직접 들고 있지 않습니다.
이 경계 덕분에 386개 테스트의 대부분이 React 환경 없이도 빠르게 돌아갑니다.

### 5. nuScenes 선택 (KITTI / Waymo 대신)

실측 3D 데이터셋 후보로 KITTI / Waymo / nuScenes를 비교했습니다. **nuScenes를 채택한 이유**는
(1) 어노테이션이 웹친화적인 JSON 관계형 테이블이라 기존 DB 경험을 활용하기 좋고,
(2) 360°·현대적 센서 구성이라 시각화 임팩트가 크며, (3) mini 셋이 가벼워 정적 번들에 적합하기
때문입니다. KITTI는 라벨 구조와 좌표계를 익히는 *학습용 디딤돌*로만 사용하고 실제 연동은 하지 않았습니다.

### 6. 오프라인 prep → 정적 JSON, 좌표 변환은 lib/ TS

nuScenes는 KITTI Level 1 같은 "무변환 경로"가 없습니다 — 어노테이션이 global 좌표라 박스만 그려도
`global→ego` 변환과 축 관례(z-up→y-up)가 필요합니다. 이를 **런타임 백엔드 없이** 처리하기 위해,
빌드타임 Python 스크립트가 관계형 테이블을 평탄화해 **원시 값만 담은 정적 JSON**으로 내보내고(좌표
계산 없음), **모든 좌표 변환·투영은 브라우저의 `lib/` TS 순수 함수**가 담당해 Vitest로 검증합니다.
덕분에 Vercel 정적 서빙 정체성을 그대로 유지합니다. (Immutable Rule #3)

### 7. 교체가 아닌 공존 (데이터셋 스위처)

nuScenes 실측 3D를 추가하면서 COCO를 *대체*할 수도 있었지만, 그러면 YOLO confidence /
히스토그램 / 추정 3D 같은 기존 작업이 사라집니다. 대신 **데이터셋 스위처로 공존**시켜 "추정 vs 실측"을
나란히 비교할 수 있게 했고, 한쪽 작업을 버리지 않으면서 서사를 강화했습니다.

## 실행 방법

### 요구 사항

- Node.js 20+
- npm
- (선택) Python 3.13 + Pillow(+ 예측을 다시 만들려면 ultralytics) — nuScenes 샘플 데이터를 직접
  재생성할 때만 필요. 생성된 파일은 이미 저장소에 포함되어 있어 앱 실행에는 불필요합니다.

### 로컬 개발

```bash
# 1. 저장소 클론 후 루트에서 의존성 설치
npm install

# 2. 개발 서버 실행 (Nx CLI 사용)
npx nx dev ai_detection_viewer_client
# → http://localhost:3000

# 3. 테스트 (Vitest, 989개)
npx nx test ai_detection_viewer_client
# 또는 앱 디렉토리에서
cd apps/ai_detection_viewer_client && npm test
```

### 프로덕션 빌드

```bash
npx nx build ai_detection_viewer_client
```

### (선택) nuScenes 샘플 데이터 재생성

```bash
# nuScenes-mini를 로컬에 받아둔 경우에만 (저장소 루트에서 실행).
# 1) 장면 10개 전부: 목차 + 장면별 박스 파일 + 프레임별 LiDAR 점 파일 + 줄인 사진(960×540 WebP)
python scripts/prep_nuscenes.py --dataroot C:\data\sets\nuscenes
# 2) 원본 사진(1600×900)에 YOLOv8n을 돌려 장면별 예측 파일을 만든다 (CPU로 약 5분)
python scripts/predict_nuscenes.py --dataroot C:\data\sets\nuscenes
# → apps/ai_detection_viewer_client/public/sample-data/nuscenes/scenes.json + scenes/<장면>/…
#   (같은 입력으로 다시 돌리면 같은 파일이 나온다. 장면 하나만: --scenes scene-0916)
```

## 현 프로젝트의 한계점

### 1. COCO 프레임의 3D는 추정값입니다 (nuScenes는 실측)

COCO에는 깊이(depth) 정보가 없으므로, COCO 프레임의 3D 좌표는 2D bbox의 중심과 면적으로부터
추정한 값입니다. **실제 LiDAR 측정값이 아닙니다.** 반면 **nuScenes 프레임은 실측 3D**라 이 한계가
없으며, 각 프레임은 `Estimated` / `Measured` 배지로 출처를 명시합니다. 두 데이터셋을 스위처로
나란히 비교할 수 있으므로, 한계 자체가 "추정 vs 실측"을 보여주는 장치가 됩니다.

### 2. nuScenes는 맛보기 묶음(mini)이고, 키프레임과 카메라·LiDAR만 씁니다

nuScenes-mini 전체(장면 10개, 키프레임 404개, 카메라 6대)를 싣지만, 전체 데이터(장면 850개)의 일부입니다.
키프레임 사이의 스윕, 레이더, 지도는 쓰지 않습니다. 밤 장면은 3개이고 모두 한 번의 주행에서 나왔습니다.

### 2-0. 평가 숫자는 조건이 붙은 관찰입니다

카메라 탐지 평가의 숫자는 모델의 성능 수치가 아닙니다. 정답이 3D 박스를 투영한 근사이고, 독립인 자료는 주행 8번이며,
헛짚음의 41%는 정체를 확인하지 않았습니다. 자세한 한계는 [카메라 탐지 평가 결과](#카메라-탐지-평가-결과-nuscenes-mini-전체)의
"한계"에 있습니다. 3D 탐지 모델을 돌리거나 3D로 채점하지는 않습니다.

### 2-1. 검수는 1인용이고, 기록은 브라우저에만 있습니다

백엔드가 없으므로 검수 기록은 그 브라우저의 localStorage에만 저장됩니다. 다른 기기나 다른 사람과
공유되지 않으며, 보관하려면 JSON / CSV로 내보내야 합니다. 작업 배정, 권한, 여러 사람의 동시 검수는
범위 밖입니다. 사진으로도 LiDAR 점으로도 판단하기 어려운 박스는 "판단 불가"로 남기도록 했습니다.
화면에 그리는 LiDAR 점은 솎아낸 것이어서(0.6m 간격) 작은 물체는 박스 안에 점이 몇 개만 보입니다.
헛짚음 표본 검수의 판정도 같은 방식으로 그 브라우저에만 저장됩니다.

### 3. 자동재생 중 박스는 보간, LiDAR 점구름은 스냅

자동재생 시 박스는 키프레임 사이를 lerp/slerp로 부드럽게 보간하지만, LiDAR 점구름은 키프레임
단위로 스냅합니다(박스는 미끄럽고 점은 튀는 부조화). 보간된 중간값은 측정값이 아니므로,
**재생 중에만** 보간하고 일시정지/스크럽 시에는 실측 키프레임을 그대로 보여줍니다 — 깊이 출처를
오인시키지 않기 위한 의도된 선택입니다(Immutable Rule #6).

### 4. COCO 프레임마다 letterbox / pillarbox 크기가 다릅니다

COCO val2017은 다양한 aspect ratio를 포함합니다. COCO의 카메라 칸은 4:3 고정이고 이미지를
contain 방식으로 맞추므로 프레임마다 위/아래 또는 좌/우 여백 크기가 달라 보입니다(세로 사진은
칸의 절반 폭만 채웁니다). 이미지와 bbox는 동일한 viewBox 좌표계로 정렬되므로 **bbox 정확도는
무손실**입니다.

### 5. 작업 화면에서 카메라 이미지는 작게 보입니다

한 화면에 모든 영역을 넣으면서 3D 뷰를 가장 크게 두었기 때문에, 카메라 이미지는 1440×900에서
400×225, 1280×720에서 360×203 크기입니다(이전 배치의 510×287보다 작음). 먼 객체의 2D 박스는
사진 위에서 십여 픽셀 크기라 사진만으로 확인하기 어렵습니다.

## 트러블슈팅

프로젝트에서 직접 겪고 해결한 사례들입니다. root cause / 대안 분석은
[`docs/edgecases/`](docs/edgecases/) 문서에 자세히 남겨두었습니다.

### 1. 3D 깊이 반전 — 큰 객체가 화면 뒤로 밀려나던 문제

- **문제**: estimator는 z를 "카메라까지의 거리"로 인코딩(작은 z = 가까움)하지만,
  카메라가 `+z` 쪽에 있어 `-z` 방향을 응시하고 있어 깊이 의미가 정반대로 나타남.
- **해결**: 카메라 위치를 `[0, 0, +14]` → `[0, 0, -10]`로 옮겨 `+z` 방향을 응시하게 함.
  estimator·tests·spec 한 줄도 건드리지 않고 한 줄만 변경.
- **코드**: [`Viewer3D.tsx#L65`](https://github.com/ansm0403/AI_Object_Detection_Viewer/blob/982dbd8b14f403e100c4581dbd4324237fb5036e/apps/ai_detection_viewer_client/src/components/viewer-3d/Viewer3D.tsx#L65)
  (COCO 카메라. nuScenes는 같은 줄에서 실측 박스에 맞춘 위치를 씀)
  · 상세: `docs/edgecases/Edge_#4.md` Case 2

### 2. 겹친 2D bbox 클릭 우선순위 불일치

- **문제**: SVG는 CSS `z-index`를 무시하고 paint order(배열 순서)대로 hit-test 하므로,
  COCO `annotations` 배열 순서에 따라 시각적으로 앞에 있는 큰 객체를 클릭해도 가려진
  작은 객체가 선택되는 경우 발생.
- **해결**: detection 목록을 bbox 면적 오름차순으로 정렬해 큰 bbox가 마지막에 paint되어
  hit-test 스택 최상단을 차지하게 함. COCO(추정 3D)에서는 3D estimator도 "큰 면적 = 가까운 z"를
  쓰므로 두 뷰의 앞뒤 판단이 일치함. nuScenes는 3D가 실측 위치라 2D 정렬만 면적 근사.
- **한계**: 면적은 깊이의 근사라, 큰 박스 안에 완전히 들어간 작은 박스는 2D에서 클릭되지 않고
  객체 리스트로 선택함.
- **코드**: [`Viewer2D.tsx#L26-L35`](https://github.com/ansm0403/AI_Object_Detection_Viewer/blob/982dbd8b14f403e100c4581dbd4324237fb5036e/apps/ai_detection_viewer_client/src/components/viewer-2d/Viewer2D.tsx#L26-L35)
  · 상세: `docs/edgecases/Edge_#2.md` Case 1

### 3. drei `<Grid>` raycast가 "빈 공간 deselect" 깨뜨림

- **문제**: R3F의 `<Canvas onPointerMissed>`는 raycast가 *아무것도* 맞히지 않을 때만
  발화. UI 다듬기에서 추가한 drei `<Grid infiniteGrid>`는 시각적으로는 페이드되지만
  실제로는 거대한 plane mesh라 거의 모든 클릭이 grid를 맞춰 `onPointerMissed`가 발화하지
  않음 → "빈 공간 클릭 = 선택 해제" 계약이 시각적 회귀 없이 조용히 깨짐.
- **해결**: `useRef`로 grid mesh를 잡고 mount 직후 `useEffect`에서 해당 mesh의 `raycast`
  메소드를 no-op으로 덮어씀. 시각은 유지하면서 raycaster에는 "보이지 않게" 만들어
  deselect 계약을 복구.
- **코드**: [`Scene.tsx#L65-L72`](https://github.com/ansm0403/AI_Object_Detection_Viewer/blob/982dbd8b14f403e100c4581dbd4324237fb5036e/apps/ai_detection_viewer_client/src/components/viewer-3d/Scene.tsx#L65-L72)
  · 상세: `docs/edgecases/Edge_#9.5.md` Case A

### 4. nuScenes 점구름이 COCO용 카메라/fog에 가려짐

- **문제**: COCO 추정 씬에 맞춰 튜닝한 카메라(`-z` 응시)와 fog `[10, 28]`이, 수십 미터 밖
  `-z` 방향에 펼쳐진 실측 nuScenes 박스 클라우드를 **등지거나 안개로 완전히 가림** → 렌더해보니
  ~2개 박스만 보임. (rendering으로 검증해서 발견)
- **해결**: 데이터셋별 카메라 framing. nuScenes는 박스 클라우드에 맞춰 카메라를 fit(뒤+위에서
  전방 응시)하고 `far`를 600으로 넓히며 fog를 끔. COCO는 기존 튜닝을 유지(`source`로 분기).
- **코드**: `lib/geometry/camera-framing.ts` · 상세: `docs/edgecases/Edge_F#2.md` Case 3

### 5. LiDAR 점구름이 박스와 어긋남

- **문제**: 점은 **LiDAR 센서 프레임**에서 태어나고 박스는 **CAM_FRONT ego 프레임**에 있는데,
  두 센서의 촬영 시점 사이에 차가 몇 cm 움직여 단순 정렬 시 점과 박스가 어긋남.
- **해결**: `sensor → GLOBAL → cam-ego`를 경유해 정렬. GLOBAL을 거치면서 ego_pose 타임스탬프
  불일치를 흡수. (LiDAR 동심원 링이 센서 원점을 중심으로 박스를 감싸는지로 렌더 검증)
- **코드**: `lib/geometry/transforms.ts` `sensorToGlobal` · 상세: `docs/edgecases/Edge_F#2.md` Case 4

### 6. 깊이 색상 그라데이션이 안 보임

- **문제**: estimator가 COCO 객체를 z∈[7, 8]로 압축해, 고정 `[1, 8]` 색 램프의 상위 ~15%만
  사용 → 거의 단색으로 보임.
- **해결**: 프레임별 실제 z 범위로 램프를 fit(`depthRange`). "모두 비슷한 깊이"인 프레임도
  전체 램프를 채우게 됨. (트레이드오프: 같은 객체가 프레임마다 다르게 칠해질 수 있음 — 깊이는
  추정값이라 수용)
- **코드**: `lib/geometry/depth-color.ts` · 상세: `docs/edgecases/Edge_F#1.md` Case 1

nuScenes를 기본 진입으로 바꾼 뒤(F2-A) 첫 화면이 실측 이미지와 LiDAR JSON을 받게 되어 LCP가 0.8s → 5.6s로 커졌습니다.
LCP 요소는 2D 뷰어의 CAM_FRONT `<image>`, TBT는 평균 1.5s(CPU 4배 감속 기준)입니다. 두 수치는 측정 시점과 진입 화면이 다르므로 항상 함께 인용합니다.
**그 뒤 데이터를 나눠 받게 바꾸고 사진을 960×540 WebP로 줄였지만(위 표), Lighthouse는 다시 재지 않았습니다.** 지금 배포본의 점수는 이 표에 없습니다.

## 배운 점

- **좌표계 변환 파이프라인** — nuScenes의 global 좌표를 `global → ego → three`로 옮기고,
  z-up→y-up 축 관례와 쿼터니언 회전을 다루면서, 3D 데이터는 "어느 프레임의 좌표인가"가
  값 자체만큼 중요하다는 것을 익혔습니다. 변환을 전부 `lib/` 순수 함수로 가두고 Vitest로 검증한
  덕에, 눈으로 안 보이는 좌표 버그를 테스트로 먼저 잡을 수 있었습니다.
- **3D→2D 투영** — 카메라 intrinsic(K 행렬)으로 3D 박스를 이미지 평면에 투영해 2D 박스를
  만들면서, 2D와 3D가 별개 데이터가 아니라 같은 객체의 두 표현임을 코드로 체감했습니다
  (같은 `instance` → 같은 id).
- **LiDAR 바이너리 + 오프라인 파이프라인** — 헤더 없는 `.pcd.bin`(점당 5×float32)을 stdlib만으로
  디코드하고 voxel-grid로 데시메이션하면서, "무거운 원시 데이터를 빌드타임에 정적 자원으로
  전처리"하는 설계 감각을 얻었습니다. 관계형 nuScenes 테이블을 평탄 JSON으로 내보내는 과정도
  DB 경험과 맞닿아 있었습니다.
- **프레임레이트 디커플링** — 씬은 ~60fps로 그려지지만 키프레임은 ~2Hz로 갱신됩니다. 이 간극을
  `useFrame`의 시간 기반 보간(lerp/slerp)으로 메우는 패턴은 처음 다뤄본 개념이었습니다.
- **WebGL 메모리 모델** — three.js 렌더러는 `dispose()` 전까지 `BufferGeometry`·`EdgesGeometry`의 GPU 버퍼를 붙잡아 GC로 회수되지 않습니다.
  `useEffect` cleanup에서 명시적으로 `.dispose()`를 호출해야 한다는 것을 메모리 누수
  audit으로 직접 확인하며 익혔습니다.
- **순수 함수와 React의 경계** — 도메인 로직을 `lib/`에 가두니 테스트 작성 비용이 크게
  줄었습니다. React 컴포넌트는 props 받는 입출력 노드로만 남았고, 통합 테스트도 store +
  selector만 검증하는 패턴이 자연스러워졌습니다.
- **선택 상태의 단일 source of truth** — 처음에는 2D / 3D 각각 selection 상태를 두려 했지만
  곧 동기화 지옥이 되리라 깨달았습니다. `selectedObjectId` 하나로 통일한 결정이 후속 작업
  (객체 리스트, 필터, 분석 패널, nuScenes 추적)에서 모두 자연스럽게 확장된 점이 가장 큰
  학습이었습니다.
- **SVG paint order = z-order** — 겹친 2D bbox의 클릭 순서를 3D 추정기의 "큰 면적 → 가까운 z"에
  맞춰 정한 경험은, 2D와 3D를 동시에 다룰 때 좌표 변환만큼이나 **렌더 순서**가 중요하다는 것을
  보여주었습니다.

## 향후 개선 방향

- **위에서 본 화면에서 3D 박스 수정** — 검수에서 반려한 박스를 직접 고칩니다. 위에서 내려다보면 3D 박스는
  회전된 사각형이라, 위치·크기·방향을 2D 편집으로 고치고 높이만 숫자로 받는 방식입니다(다음 작업).
- **평가를 더 갖추기** — 점수 기준을 훑은 PR 곡선과 AP, 클래스를 무시한 짝짓기와 혼동행렬, 채점 규칙 보완
  (평가하지 않는 클래스를 제외 영역으로, 사진 안에 들어온 비율, 카메라 평면에 걸친 박스).
- **다른 주행의 밤 장면** — "밤의 근거는 주행 한 번"이라는 약점에 직접 답하는 것은 데이터를 더하는 일뿐입니다.
- **radar** — 지금은 카메라 6대와 LiDAR만 씁니다.
- **카메라 follow의 거리 추적** — 현재 Follow 모드는 `target`(응시점)만 객체를 따라가고 카메라
  위치는 고정이라, 멀어지는 객체는 점점 작아집니다. 위치까지 따라가는 모드가 다음 후보입니다.
- **백엔드 API 미연동** — 현재는 정적 JSON. Nest.js로 frame API 서버를 만들고 TanStack
  Query를 도입하면 풀스택 경험이 자연스럽게 추가됩니다.
- **COCO 프레임 간 추적 없음** — COCO는 `Detection.id`의 프레임 간 연속성을 보장하지 않습니다.
  휴리스틱으로 흉내내는 것은 포트폴리오에서 오히려 신뢰를 깎는다고 판단해 의도적으로 제외했습니다
  (nuScenes는 `instance` 토큰으로 실제 추적 제공).
