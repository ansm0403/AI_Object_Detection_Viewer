# F4 — 3D 박스 검수

- **상태:** 임시 승인 (2026-11-25). 결정 1은 사용자가 직접 골랐고, 나머지 결정 2~16은 시안을 본 뒤
  **추천안 그대로 진행**하기로 했다. 사용자의 말: "3D 분석을 다뤄본 적이 없어 좋고 나쁨을 판단하기 어렵다.
  우선은 그대로 진행하자." 따라서 최종 결정이 아니라 **만들어서 보여주고 조정하는 출발점**이다. 조정한 내용은
  체크리스트의 완료 기록에 남긴다.
- **작성일:** 2026-11-25
- **로드맵:** `.claude/docs/post-mvp-checklist.md` → "Roadmap — F3+ direction"
- **시안과 캡처:** [assets/F4/compare.html](assets/F4/compare.html) (브라우저로 열면 "지금 ↔ 시안"을 같은 자리에서 바꿔 볼 수 있다)

## 1. 목표

> nuScenes의 3D 정답 박스를 하나씩 보면서 **승인 / 반려 / 판단 불가**를 남기고, 반려한 이유를 적고,
> 브라우저를 닫았다 열어도 **이어서** 하고, 결과를 **파일로 내보낸다.**

지금 앱은 둘러보기만 할 수 있는 뷰어다. F4가 끝나면 사용자가 **결과물(검수 기록)** 을 들고 나갈 수 있는
도구가 된다. 로드맵의 두 기둥 중 "라벨 품질(정답이 맞나)"에 해당한다.

**용어 (이 문서에서 쓰는 뜻)**

| 용어 | 뜻 |
|---|---|
| 검수 | 사람이 그린 정답 박스가 맞는지 다른 사람이 확인하는 일. F5 비유로는 "정답지에 오타가 없는지 보는 일" |
| 판정 | 박스 하나에 대한 검수 결과. 승인(맞다) / 반려(틀렸다) / 판단 불가(봤지만 이 화면으로는 알 수 없다) |
| 대기열 | 지금 검수할 박스들의 순서. `J`를 누르면 대기열의 다음 박스로 간다 |
| 투영 | 3D 공간의 점을 "카메라 사진의 어느 픽셀에 찍히는가"로 바꾸는 계산. F2에서 이미 만들었다 |
| LiDAR 점 개수 | 그 박스 안에 LiDAR(레이저 거리 센서)의 점이 몇 개 들어 있었는지. nuScenes가 박스마다 적어 둔 값 |

## 2. 지금의 문제

2026-11-25에 코드를 읽고, 원본 데이터(`C:\data\sets\nuscenes`)를 조사하고, 실제 화면을 세 가지 창 크기로
캡처해 확인한 사실이다.

### 2.1 도구에 "남는 것"이 없다

| # | 사실 | 근거 (코드) |
|---|---|---|
| 1 | 판정을 기록할 곳이 없다 | `store/viewer-store.ts`에는 선택, 필터 값만 있다. 저장(persist) 기능도 없다 |
| 2 | 키보드로 할 수 있는 일이 없다 | `src/` 전체에 `keydown` 처리가 한 곳도 없다 |
| 3 | 박스를 프레임별로 구분할 ID가 없다 | 객체 ID는 `instanceToken`이다. 같은 차는 10개 프레임에서 같은 ID를 갖는다. 그런데 박스는 프레임마다 따로 그려진 것이다. `scripts/prep_nuscenes.py`는 박스 고유 ID(`sample_annotation.token`)를 내보내지 않는다 |

### 2.2 지금 화면으로는 박스가 맞는지 판단하기 어렵다

| # | 사실 | 근거 |
|---|---|---|
| 4 | 카메라 사진에서 박스가 너무 작다 | 카메라 칸은 400×225(1280×720 창에서는 360×203). 첫 프레임에서 카메라에 보이는 13개는 모두 보행자이고, 2D 박스가 **폭 13~22px, 높이 19~36px**이다(1440×900 실측) |
| 5 | 카메라에는 3D 박스가 아니라 **감싸는 사각형**만 그려진다 | `lib/geometry/projection.ts`의 `projectCornersToBbox`가 꼭짓점 8개를 투영한 뒤 감싸는 사각형만 돌려준다. 박스의 방향이나 깊이 방향 크기가 맞는지는 이 사각형으로 알 수 없다 |
| 6 | 화면의 LiDAR 점이 성기다 | 화면용 점은 0.6m 간격으로 솎아낸 것이다(`prep_nuscenes.py`의 `DEFAULT_VOXEL_SIZE = 0.6`). 사람 크기 박스(0.6×0.6×1.7m) 안에는 화면상 점이 몇 개뿐이다 |
| 7 | 카메라에 안 보이는 박스가 더 많다 | 10개 프레임의 박스 583개 중 앞 카메라에 보이는 것은 200개다. 프레임별로 13/40, 19/44, 19/49, 22/52, 23/58, 25/61, 26/66, 21/70, 17/72, 15/71 |
| 8 | 정보 패널에 버튼을 넣을 자리가 좁다 | 사용자 노트북 창(1536×700)에서 정보 패널은 400×275인데 "Selected" 정보만 229px다. 패널 내용 전체는 542px라 이미 패널 안에서 스크롤된다 |

### 2.3 "검수할 것이 없다"는 걱정에 대해 확인한 것

nuScenes 원본의 박스에는 지금 내보내지 않는 값이 두 가지 더 있다.

| 값 | 뜻 | 10개 프레임 583개 박스의 분포 |
|---|---|---|
| `num_lidar_pts` | 박스 안 LiDAR 점 개수 (솎아내기 전 원본 기준) | **0개: 72** · 1~4개: 164 · 5~19개: 233 · 20~99개: 89 · 100개 이상: 25 |
| `visibility` | 카메라 6대의 사진을 통틀어 물체가 얼마나 보이는가 (4단계) | 0~40%: 155 · 40~60%: 78 · 60~80%: 164 · 80~100%: 186 |

- 점이 0개인 박스는 **틀린 박스가 아니다.** 작업자가 앞뒤 프레임을 보고 위치를 이어 그린 박스다. 다만 센서
  근거가 없으므로 검수자가 가장 먼저 들여다볼 대상이다.
- 첫 프레임에는 0개짜리가 없고 1~4개짜리가 19개 있다. 5번 프레임에는 0개짜리가 14개다.
- `visibility`는 **앞 카메라 한 대가 아니라 6대 전체 기준**이다(nuScenes 스키마 설명 기준. **확인 필요:** 구현할
  때 nuScenes 문서 원문을 다시 확인한다). 화면에는 그렇게 적는다.

### 2.4 그 밖에 확인한 것

- 서로 다른 객체는 73개이고, 그중 38개는 10개 프레임 모두에 나온다. 박스 고유 ID 583개는 모두 다르다.
- 테스트 213개 통과, `tsc --noEmit` 오류 0개 (2026-11-25, F4 시작 시점).
- `nuscenes.json`은 1,443,306바이트(약 1.4MB)다. HANDOFF 7장의 "약 2.9MB"는 틀린 값이다(세션을 끝낼 때 고친다).
- zustand 5.0.13에는 저장 기능(`zustand/middleware`의 `persist`)이 들어 있다. 새 라이브러리가 필요 없다.

## 3. 바뀐 뒤의 모습

### 3.1 검수자가 하는 일

```
박스 선택(목록 / 3D / 카메라 클릭, 또는 J)
   → 3D 뷰에서 위치와 주변을 본다
   → 카메라 칸에서 확대된 사진 위의 3D 박스 선을 본다 (카메라에 보이는 박스일 때)
   → 정보 패널에서 LiDAR 점 개수, 가려짐 단계를 본다
   → A 승인 / R 반려(+사유) / U 판단 불가
   → 다음 미검수 박스로 자동 이동
```

### 3.2 화면 (시안 기준)

F3의 배치는 그대로다. 영역을 새로 만들지 않고 **기존 영역 안에** 넣는다.

| 자리 | 들어가는 것 |
|---|---|
| 상단 바 오른쪽 | 전체 진행률("Reviewed 6 / 583" + 막대 + 반려 수), `Export` 버튼. 왼쪽 배지 옆에 `Practice` 토글 |
| 목록 제목 아래 (28px 한 줄) | 정렬 선택("Scene order" / "Fewest LiDAR pts" / "In camera first"), 남은 개수 |
| 목록 행 | LiDAR 근거 막대(주황 = 4개 이하), 맨 오른쪽에 검수 상태 아이콘 |
| 카메라 칸 | `Full / Zoom` 전환. Zoom이면 선택한 박스 주변을 확대하고 **3D 박스를 투영한 선**을 그린다. 카메라 밖 박스면 안내 문구 |
| 정보 패널 (제목 "Review") | 제목 줄 바로 아래 **스크롤 밖에 고정된** 판정 버튼 3개. 반려하면 사유 칩 6개와 메모 칸. 아래 "Selected"에 LiDAR, Visibility 줄 추가 |
| 타임라인 썸네일 배지 | "40" → "6/40" (검수한 수/전체) |
| 3D 뷰 | 변화 없음 (결정 15) |

시안에서 확인한 것:
- 1536×700, 1440×900, 1280×720 모두 **페이지 스크롤이 생기지 않는다**(시안 화면에서 판정식으로 확인).
- 카메라 확대 시 28m 거리 보행자가 14×24px → 약 54×94px로 보인다. 원본 사진이 1600×900이라 **이 이상은
  흐려질 뿐 더 선명해지지 않는다.**
- 1536×700에서 반려 상태가 되면 버튼 영역이 커져 "Selected" 정보는 패널 안에서 스크롤해야 보인다.

### 3.3 저장과 내보내기

- 판정은 누르는 즉시 브라우저 저장소(localStorage)에 저장된다. 새로고침하거나 창을 닫았다 열어도 남는다.
- `Export`를 누르면 JSON 또는 CSV 파일로 받는다(결정 12에 형식).

### 3.4 연습 모드 (마지막 단계, 뺄 수 있음)

`Practice`를 켜면 박스 일부가 일부러 어긋난 상태로 바뀐다. 상단 배지는 "Measured" 대신 주황색
"Practice · labels modified"가 되고, 검수하면 "심어 둔 오류 4개 중 3개를 찾음"처럼 채점된다. 원본 데이터
파일은 바뀌지 않는다(결정 13).

## 4. 범위

**포함**
- 판정 3종(승인 / 반려 / 판단 불가), 반려 사유, 메모.
- 검수 기록 저장(localStorage), 이어서 하기, 초기화.
- 진행률(전체, 프레임별), 목록의 상태 표시와 정렬.
- 단축키, 판정 후 자동 이동.
- 카메라 칸 확대와 3D 박스 투영 선, LiDAR 점 개수와 가려짐 단계 표시.
- 내보내기(JSON, CSV).
- 연습 모드(변형 데이터 + 채점). **F4-F 단계. 앞 단계가 끝난 뒤 진행하고, 시간이 부족하면 뺀다.**
- 준비 스크립트가 박스 고유 ID, LiDAR 점 개수, 가려짐 단계를 내보내도록 수정하고 `nuscenes.json`을 다시 만든다.

**범위 밖**
- 박스 수정(F8). F4는 "틀렸다"까지만 기록한다.
- 모델 평가(F5), 카메라 6대(F6), 장면 탐색(F7).
- 백엔드, DB, 로그인, 여러 사람이 함께 쓰는 기능, 작업자/검수자 역할 전환.
- COCO 모드의 검수(결정 14).
- 3D 뷰의 변화: 판정에 따라 박스 색 바꾸기, 선택한 박스로 카메라가 다가가기, 박스 근처 점을 촘촘하게 보여주기(결정 15).
- 새 라이브러리 설치. zustand에 들어 있는 `persist`만 쓴다.
- 패널 크기 조절, 카메라와 3D 자리 바꾸기(결정 9의 대안).

## 5. 작업 단계

단계가 끝날 때마다 실제 앱을 캡처해 보여주고, 확인받은 뒤 다음 단계로 간다. 매 단계에서 기존 동작(선택
동기화, 선택 해제, 3D 카메라 유지, 스크롤 없는 화면)을 다시 확인한다.

| 단계 | 내용 | 화면 변화 |
|---|---|---|
| **F4-A** 데이터와 로직 | 준비 스크립트에 값 3개 추가 → `nuscenes.json` 재생성. 타입, 파서 수정. `lib/review/`의 순수 함수(키, 진행률, 대기열, 다음 박스 찾기, 내보내기 형식, 저장값 검증)와 `store/review-store`(저장 포함). 모두 테스트 | 없음. 캡처로 "화면이 그대로임"을 확인한다 |
| **F4-B** 판정 화면 | 정보 패널의 판정 버튼, 사유 칩, 메모. 목록 행의 상태 아이콘과 LiDAR 막대. 상단 진행률. 타임라인 배지. 새로고침 후에도 판정이 남는지 확인 | 마우스로 검수가 된다 |
| **F4-C** 대기열과 단축키 | 목록 정렬, `J`/`K`, `A`/`R`/`U`/`C`, 숫자키 사유, 판정 후 자동 이동, 프레임을 다 끝냈을 때 안내, 재생 중 처리 | 키보드로 검수가 된다 |
| **F4-D** 카메라 확대와 근거 | 카메라 칸 `Full / Zoom`, 3D 박스 투영 선, 카메라 밖 안내, "Selected"의 LiDAR / Visibility 줄 | 판단 근거가 보인다 |
| **F4-E** 내보내기와 초기화 | `Export`(JSON, CSV), 검수 초기화, 저장 실패 시 안내 | 결과물이 나온다 |
| **F4-F** 연습 모드 | 변형 함수, 채점, `Practice` 토글과 표시 | 뺄 수 있는 단계 |

A를 먼저 하는 이유: B 이후의 화면은 모두 A의 값(LiDAR 점 개수, 검수 기록)을 그리는 것이다. A는 화면이
바뀌지 않으므로 문제가 생기면 원인이 데이터와 로직에만 있다.

### 검수 기록의 모양 (설계의 핵심)

```ts
type Verdict = 'approved' | 'rejected' | 'unsure';
type RejectReason =
  | 'wrong_class' | 'wrong_size' | 'wrong_position'
  | 'wrong_heading' | 'not_an_object' | 'other';

type ReviewRecord = {
  frameId: string;      // 프레임 ID (nuScenes sample token)
  objectId: string;     // 객체 ID (instance token) — selectedObjectId와 같은 값
  verdict: Verdict;
  reasons: RejectReason[];   // 반려일 때만 의미가 있다
  note: string;
  reviewedAt: string;   // ISO 시각
};

// 키는 `${frameId}/${objectId}`. 범위(원본 / 연습)별로 따로 보관한다.
type ReviewStore = {
  reviews: Record<'nuscenes' | 'nuscenes-practice', Record<string, ReviewRecord>>;
  // 동작: setVerdict, toggleReason, setNote, clearReview, resetScope
};
```

- **"지금 검수 중인 박스"라는 상태는 따로 두지 않는다.** 항상 `selectedFrameId` + `selectedObjectId`에서
  키를 만든다(규칙 #2).
- 진행률, 대기열, 다음 박스는 store에 저장하지 않고 `lib/review`의 순수 함수로 **그때그때 계산**한다(규칙 #3).

## 7. 결정이 필요한 항목

### 결정 1. 검수할 것이 적은 문제 — ✅ 확정 (2026-11-25)
- **확정: 실제 신호 + 연습 모드.** 원본 데이터에는 LiDAR 점 개수와 가려짐 단계를 붙여 "근거가 약한 박스부터"
  보게 하고, 마지막 단계로 연습 모드를 추가한다.
- 버린 대안: 그대로 두기 / 실제 신호만 / 연습 모드만.
- 대가: 작업량이 가장 크다. 그래서 연습 모드를 F4-F로 떼어 두었다.

### 결정 2. 검수 기록의 키
- **추천: (프레임 ID, 객체 ID) 쌍을 키로 쓰고, 박스 고유 ID는 내보내기 파일에 함께 적는다.**
  - 이유: 선택 상태가 이미 이 두 값이다. 같은 차라도 3번 프레임의 박스와 7번 프레임의 박스를 따로 판정할 수 있다.
    연습 모드처럼 박스 고유 ID가 의미 없는 데이터에서도 동작한다.
- 대안: 박스 고유 ID(`annotationToken`)를 키로. nuScenes 원본과 바로 대응되지만, 화면의 선택 상태에서 키를
  만들려면 매번 박스를 찾아야 하고 옛 데이터 파일에서는 동작하지 않는다.
- 대가: 준비 스크립트를 고치고 데이터 파일을 다시 만들어야 한다.

### 결정 3. 판정의 종류
- **추천: 승인 / 반려 / 판단 불가(Unsure) 세 가지.**
  - 이유: 2.2의 사실 7 때문이다. 카메라 한 대로는 박스의 약 3분의 2를 사진과 대조할 수 없고, 화면의 점도 성기다.
    "봤지만 알 수 없다"를 적을 방법이 없으면 검수자는 근거 없이 승인하거나, 미검수로 남겨 프레임이 영원히
    끝나지 않는다. 판단 불가로 남긴 박스는 F6(카메라 6대)에서 다시 볼 대상이 된다.
- 대안: 승인 / 반려 두 가지. 단순하지만 위 문제가 남는다.
- 대가: 버튼이 하나 늘고, 진행률에서 "판단 불가"를 따로 세야 한다. 판단 불가도 "검수함"으로 센다.

### 결정 4. 반려 사유
- **추천: 6가지 중 여러 개 선택, 메모는 선택 사항.** Wrong class / Wrong size / Wrong position /
  Wrong heading / Not an object / Other.
  - 사유 없이도 반려는 저장된다. 대신 패널에 "Add a reason" 안내를 띄우고, 내보낸 파일에는 사유가 빈 채로 드러난다.
- 대안 A: 사유를 반드시 골라야 반려가 저장된다. 데이터는 깔끔하지만 "반려를 눌렀는데 아직 반려가 아닌" 중간
  상태가 생겨 상태와 화면이 복잡해진다.
- 대안 B: 사유를 하나만 고른다. 단순하지만 "위치도 어긋나고 크기도 크다"를 적을 수 없다.
- 대가: 사유 없는 반려가 생길 수 있다.

### 결정 5. 어디에, 어떻게 저장할까
- **추천: 검수 전용 store(`review-store`)를 새로 만들고, zustand의 `persist`로 localStorage에 저장한다.**
  - 이유 1: 기록은 박스당 약 150바이트다. 583개를 다 검수해도 약 90KB로 localStorage 한도(보통 5MB)에 한참 못 미친다.
  - 이유 2: 기존 `viewer-store`에는 저장하면 안 되는 값(선택 상태)과 그대로는 저장되지 않는 값(`Set`)이 있다.
    store를 나누면 저장 설정이 검수 기록에만 걸린다.
  - 불러오기는 화면이 뜬 뒤에 한다(`skipHydration` + `rehydrate()`). 서버가 그린 화면과 브라우저의 첫 화면이
    달라지는 문제(hydration 불일치)를 피하기 위해서다.
  - 저장된 값은 믿지 않는다. 불러올 때 순수 함수로 검증하고, 모양이 틀린 기록은 `console.warn` 후 버린다.
- 대안 A: IndexedDB. 큰 데이터에 맞지만 비동기 처리 코드가 늘어난다. F8에서 박스 수정 내용까지 저장하게 되면
  그때 검토한다.
- 대안 B: `viewer-store`에 합친다. 파일은 하나지만 저장 대상만 골라내는 설정이 필요하고, 선택 상태와 검수
  기록의 책임이 섞인다.
- 대가: store가 두 개가 된다. 저장소를 지우거나 다른 브라우저를 쓰면 기록이 없다(백엔드가 없으므로 피할 수
  없다. 내보내기 파일이 유일한 보관 방법이다).

### 결정 6. 대기열과 필터의 관계
- **추천: 대기열 = 지금 프레임에서 필터를 통과한 박스(목록에서 흐리지 않은 행)를 목록 정렬 순서대로.**
  진행률의 분모는 필터와 상관없이 전체 박스 수.
  - 이유: 필터로 가려진 박스는 3D 뷰에 그려지지 않는다. 보이지 않는 박스로 넘어가면 판정할 수 없다.
    "보행자만 30m 안쪽"으로 좁혀 놓고 검수하는 흐름도 자연스럽게 된다.
  - 필터로 가려진 박스를 흐린 행을 눌러 직접 선택하면, 판정 버튼은 꺼지고 "Hidden by filters"를 보여준다.
- 대안: 필터를 무시하고 프레임의 모든 박스를 돈다. 단순하지만 3D에 안 보이는 박스에서 멈추게 된다.
- 대가: 필터를 건 채로는 프레임을 100% 끝낼 수 없다. 목록의 "N to review"는 대기열 기준, 상단 진행률은 전체 기준이라
  숫자가 두 가지다.

### 결정 7. 판정한 뒤 어디로 갈까
- **추천:** 승인과 판단 불가는 **다음 미검수 박스로 자동 이동**한다. 반려는 **그 자리에 머문다**(사유를 고르고
  `J`로 넘어간다). 프레임의 대기열을 다 끝내면 멈추고 "Frame done · Next frame (N)"을 보여준다.
  - 이유: 승인은 가장 흔한 판정이라 한 번의 키로 끝나야 한다. 반려는 사유를 적어야 하므로 넘어가면 안 된다.
    프레임이 사용자 모르게 바뀌면 3D 장면이 통째로 바뀌어 혼란스럽다.
- 대안: 프레임 끝에서 다음 프레임으로 자동으로 넘어간다. 더 빠르지만 화면이 예고 없이 바뀐다.
- 대가: 프레임마다 `N`을 한 번 눌러야 한다.

### 결정 9. 카메라 사진이 작은 문제 (화면 — 시안 A·B, F·G를 번갈아 볼 것)
- **추천: 카메라 칸 안에서 선택한 박스 주변을 확대하고(`Zoom`), 3D 박스를 사진에 투영한 선 12개를 그린다.**

  - 선택한 박스가 카메라에 없으면 사진 전체와 안내 문구를 보여준다.

- 대안: 카메라에 보이는 박스(583개 중 200개)만 검수 대상으로 한다. 판정의 근거는 더 탄탄하지만 "3D 박스 검수"라는

- 대가: 판단 불가가 많이 나올 수 있다. 이것은 숨기지 않고 진행률에 따로 센다. F6에서 풀린다.

### 결정 12. 내보내기 형식
- **추천: JSON과 CSV 두 가지. 검수한 박스만 담고, 맨 위에 요약을 둔다.**

  ```json
  {
    "format": "ai-detection-viewer/review@1",
    "exportedAt": "2026-11-25T10:40:00.000Z",
    "dataset": "nuscenes",
    "practice": false,
    "summary": { "totalBoxes": 583, "reviewed": 7, "approved": 4, "rejected": 2, "unsure": 1 },
    "reviews": [
      { "frameIndex": 1, "frameId": "b598…", "objectId": "c8fc…", "annotationToken": "…",
        "class": "person", "verdict": "rejected", "reasons": ["wrong_size"],
        "note": "box is taller than the person", "reviewedAt": "…" }
    ]
  }
  ```

  CSV는 `reviews`의 줄을 그대로 표로 만든 것이다(사유는 `;`로 이어 붙인다).
  - 이유: JSON은 다른 도구가 읽기 좋고, CSV는 엑셀로 바로 열린다. 내용을 만드는 일은 순수 함수가 하고,
    컴포넌트는 파일로 내려받게만 한다.
- 대안: 미검수 박스까지 모두 담는다. 완전하지만 파일 대부분이 "미검수" 줄이 된다.
- 대가: 미검수 박스가 무엇인지는 파일만 봐서는 알 수 없다(요약의 개수로만 알 수 있다).

### 결정 13. 연습 모드 (F4-F)
- **추천:**
  - **만드는 곳:** 별도 데이터 파일을 만들지 않는다. `lib/review/practice.ts`의 순수 함수가 원본 JSON을 받아
    일부 박스를 바꾼 사본과 정답표를 돌려준다. 파서가 그 사본을 읽으므로 3D 박스, 카메라의 투영, 2D 사각형이
    **모두 같은 변형 값에서** 나온다. 원본 파일은 바뀌지 않는다.
  - **무엇을 바꾸나:** 위치(바닥 면에서 약 1m 밀기), 크기(약 1.5배 또는 0.6배), 방향(약 30~60° 돌리기),
    클래스(car ↔ truck 등). 프레임마다 LiDAR 점이 5개 이상인 박스 중 약 10%. 시드(난수의 시작값)를 고정해
    항상 같은 박스가 같은 방식으로 바뀐다. 정확한 크기는 캡처로 보고 조정한다.
  - **표시(규칙 #6):** 켜져 있는 동안 상단 배지, 3D 이름표, 내보내기 파일(`"practice": true`)에 항상 표시한다.
    검수 기록도 원본과 **따로 보관**한다. 연습에서 한 판정이 원본 기록에 섞이지 않는다.
  - **채점:** 찾음(심은 오류를 반려) / 놓침(심은 오류를 승인) / 헛짚음(멀쩡한 박스를 반려). "Reveal answers"로
    정답을 볼 수 있다. F5에서 배울 TP / FN / FP와 같은 구조다.
- 대안: 스크립트로 변형된 데이터 파일을 따로 만든다. 브라우저 코드는 단순해지지만 좌표 계산이 Python
  스크립트에 들어가(지금 스크립트는 "좌표 계산을 하지 않는다"가 원칙이다) 테스트할 수 없고, 1.4MB 파일이 하나 더 생긴다.
- 대가: F4에서 가장 큰 단계다. 재생 중에는 변형된 프레임과 아닌 프레임 사이에서 박스가 튀어 보일 수 있다
  (연습 모드에서만).

### 결정 14. COCO 모드
- **추천: COCO에서는 검수 기능을 보이지 않는다.** 정보 패널은 지금처럼 "Analytics", 버튼과 진행률 없음.
  - 이유: 검수 대상은 실측 3D 박스다. COCO의 3D는 2D에서 추정한 값이라 "맞다 / 틀리다"를 판정할 대상이 아니다
    (규칙 #6). COCO의 객체 ID는 프레임이 바뀌면 의미가 없기도 하다.
- 이것이 F4 설계에서 COCO 모드가 걸리는 유일한 지점이다. COCO를 남길지 여부는 계속 보류로 둔다.
- 대가: 데이터셋에 따라 패널 모양이 달라진다(이미 필터 슬라이더와 차트가 그렇게 동작한다).

### 결정 15. 3D 뷰는 바꾸지 않는다
- **추천: F4에서는 3D 뷰를 그대로 둔다.**
  - 판정에 따라 3D 박스 색을 바꾸지 않는다. 박스 색은 클래스를 뜻하고, 선택은 흰색이다. 여기에 승인/반려 색을
    더하면 한 색이 두 가지 뜻을 갖는다.
  - 선택한 박스로 카메라가 자동으로 다가가지 않는다. F2-D에서 "클릭만으로는 카메라가 움직이지 않는다"로 정했고,
    기존의 Follow 버튼과 마우스 휠로 볼 수 있다.
- 대안: 선택할 때마다 박스 가까이로 카메라 이동. 검수는 편해지지만 고정 시점, Follow, 재생 중 보간과 얽혀
  검증할 것이 많다.
- 대가: 3D에서 박스를 자세히 보려면 사용자가 직접 확대해야 한다. 실제로 써 보고 불편하면 별도 항목으로 다룬다.

### 결정 16. 데이터 파일을 다시 만든다
- **추천: 준비 스크립트에 값 3개를 추가하고 `nuscenes.json`을 다시 만든다.** 다시 만든 뒤 스크립트로 옛 파일과
  비교해 **새 값 3개 말고는 달라진 것이 없는지** 확인한다.
- 대안: 새 값만 담은 작은 파일을 따로 만든다. 기존 파일은 안 바뀌지만 파일 두 개를 맞춰 읽는 코드가 생긴다.
- 대가: 1.4MB 파일이 커밋에서 통째로 바뀐 것으로 보인다(한 줄짜리 JSON이라 그렇다).

## 8. 완료 기준

**판정과 저장**
- [ ] nuScenes에서 박스를 선택하고 승인 / 반려 / 판단 불가를 남길 수 있다. 목록 행, 상단 진행률, 타임라인 배지가
      바로 바뀐다.
- [ ] 같은 객체라도 프레임이 다르면 판정이 따로다(1번 프레임에서 승인한 차가 2번 프레임에서는 미검수다).
- [ ] 반려하면 사유 6개와 메모 칸이 나타나고, 사유를 여러 개 고를 수 있다.
- [ ] 새로고침한 뒤에도 판정, 사유, 메모가 그대로다.
- [ ] 초기화하면 지금 범위(원본 또는 연습)의 기록만 지워진다.
- [ ] localStorage를 쓸 수 없는 환경에서도 앱이 죽지 않고, 저장되지 않는다는 안내가 보인다.

**흐름**
- [ ] 마우스 없이 `J`, `A`, `R`, `U`, `C`, `1`~`6`, `N`만으로 한 프레임을 끝까지 검수할 수 있다.
- [ ] 승인 / 판단 불가 뒤에는 다음 미검수 박스가 선택되고, 그 행이 목록 안에서 보이는 위치로 온다. 페이지는 움직이지 않는다.
- [ ] 메모 칸에 글을 쓰는 동안에는 단축키가 동작하지 않는다(`a`를 쳐도 승인되지 않는다).
- [ ] 자동 재생 중에는 판정 버튼과 판정 단축키가 꺼진다.
- [ ] 필터로 가려진 박스는 `J`/`K`와 자동 이동에서 건너뛴다.

**근거**
- [ ] 카메라에 보이는 박스를 선택하고 `Zoom`이면 사진이 박스 주변으로 확대되고 3D 박스의 선 12개가 그려진다.
- [ ] 카메라에 없는 박스를 선택하면 안내 문구가 보인다.
- [ ] 정보 패널에 LiDAR 점 개수와 가려짐 단계가 나오고, 점이 4개 이하면 목록과 패널에서 구분된다.

**내보내기**
- [ ] JSON과 CSV를 내려받을 수 있고, 요약의 개수가 화면의 진행률과 같다.

**연습 모드 (F4-F를 진행한 경우)**
- [ ] 켜져 있는 동안 상단 배지와 3D 이름표가 "변형됨"을 표시한다. "Measured"라고 쓰지 않는다.
- [ ] 같은 시드에서 항상 같은 박스가 같은 방식으로 바뀐다(테스트).
- [ ] 연습 모드의 판정이 원본의 기록과 섞이지 않는다.
- [ ] 채점 숫자가 판정과 맞는다(테스트).

**기존 동작 (바뀌면 안 되는 것)**
- [ ] 1440×900, 1280×720, 1536×700에서 페이지 스크롤이 없다. nuScenes와 COCO 모두, 반려 상태(버튼 영역이 가장 클 때)와 재생 중에도.
- [ ] 2D ↔ 3D ↔ 목록 선택 동기화. 선택 상태는 `selectedObjectId` 하나다.
- [ ] 3D 빈 공간, 2D 배경, 목록 빈 곳을 클릭하면 선택이 해제된다.
- [ ] nuScenes에서 프레임을 바꾸거나 재생해도 3D 카메라 시점이 유지된다. Follow가 동작한다.
- [ ] COCO 화면은 F3 완료 때와 같다(검수 UI 없음).
- [ ] 로딩 화면과 로딩 후 화면의 영역 위치가 같다.

**코드**
- [ ] 기존 테스트 213개 통과 + 새 테스트(`lib/review`, `store/review-store`, 파서, 투영).

- [ ] 계산(진행률, 대기열, 내보내기, 단축키 해석, 변형, 채점)이 컴포넌트와 store 밖에 있다.

## 9. 검증 방법

- **단위 테스트 (Vitest):** `lib/review/*`, `store/review-store`, `lib/nuscenes/parser`(새 값), `lib/geometry/projection`(꼭짓점).
  화면 렌더링은 테스트하지 않는다(Testing Policy).
- **화면 캡처 (Playwright):** 단계마다 1536×700, 1440×900, 1280×720에서 찍는다. 스크롤 유무는 판정식
  (`scrollHeight === clientHeight`)으로 확인한다. 단축키는 Playwright로 실제 키를 눌러 확인한다.
- **저장 확인:** 판정 → 새로고침 → 같은 상태인지 캡처로 비교한다.
- **데이터 확인:** 다시 만든 `nuscenes.json`과 옛 파일을 스크립트로 비교한다(새 값 3개 외에는 같아야 한다).
- **기록:** 캡처는 `docs/plan-feature/assets/F4/`에 날짜와 시각(KST)을 붙여 남긴다.

## 10. 불변 규칙과의 관계

| 규칙 | 영향 |
|---|---|
| #1 2D와 3D의 ID 동일 | 지킴. ID는 바꾸지 않는다. 검수 기록은 그 ID를 키의 일부로 쓴다. 연습 모드도 원본 JSON 단계에서 바꾸므로 3D와 2D가 같은 ID를 유지한다 |
| #2 `selectedObjectId` 하나만 사용 | 지킴. "검수 중인 박스" 상태를 만들지 않는다. 검수 store에는 기록만 있고 선택은 없다 |
| #3 변환 로직은 컴포넌트와 store 밖 | 지킴. 진행률, 대기열, 내보내기, 단축키 해석, 투영, 변형, 채점 모두 `lib/`의 순수 함수다. 준비 스크립트는 값을 복사만 한다 |
| #4 범위 확장은 승인 필요 | 이 문서가 승인 요청이다. 연습 모드와 "판단 불가" 판정은 HANDOFF에 없던 추가 항목이라 따로 표시했다 |
| #5 3D가 메인 | 지킴. 배치는 그대로다. 카메라는 확대해도 보조 확인용이다 |
| #6 3D 추정값 표시 | 적용 범위가 넓어진다. ① 재생 중의 보간된 위치로는 판정할 수 없게 한다. ② 연습 모드의 변형된 박스를 "Measured"로 표시하지 않는다. ③ 추정 3D인 COCO는 검수 대상이 아니다. ④ LiDAR 점 개수와 가려짐 단계는 nuScenes가 준 값임을 밝힌다 |
| #7 COCO는 2D 전용 | 영향 없음. COCO 경로를 건드리지 않는다 |

## 11. 위험 요소

| # | 위험 | 대응 |
|---|---|---|
| 1 | 준비 스크립트를 다시 돌리면 LiDAR 점이 달라질 수 있다(**확인 필요:** 솎아내기가 실행마다 같은 결과를 내는지 확인된 적이 없다) | 다시 만든 파일을 옛 파일과 비교한다. 다르면 원인을 먼저 보고, 점 배열은 옛 파일 것을 유지하는 방법을 검토한다 |
| 2 | 저장된 기록과 데이터가 어긋난다(데이터 파일을 바꾼 뒤 옛 기록이 남는 경우) | 지금 데이터에 없는 키의 기록은 진행률과 내보내기에서 세지 않는다. 지우지는 않는다(초기화로만 지운다) |
| 3 | localStorage를 못 쓰거나 가득 찼을 때의 `persist` 동작(**확인 필요**) | F4-E에서 실제로 막아 놓고 확인한다. 저장 접근을 감싸 예외가 앱을 죽이지 않게 한다 |
| 4 | 화면이 뜬 뒤에 기록을 불러오므로 진행률이 0에서 실제 값으로 한 번 바뀐다 | 데이터 로딩(스켈레톤) 중에 불러오기가 끝나므로 보통 보이지 않는다. 캡처로 확인한다 |
| 5 | 버튼에 포커스가 있을 때 `Space`/`Enter`가 그 버튼을 다시 누른다 | 단축키에 `Space`/`Enter`를 쓰지 않는다. 판정 버튼은 같은 판정을 다시 눌러도 결과가 같게 만든다 |
| 6 | 1536×700에서 반려 상태일 때 정보 패널이 좁다(시안 C) | 시안으로 판단한다. 부족하면 메모 칸을 접어 두거나 키 안내 줄을 뺀다 |
| 7 | 목록 폭 240px(1280×720)에서 행이 빽빽하다 | 시안으로 판단한다. 부족하면 좁은 폭에서 ID 칸을 숨긴다(전체 ID는 정보 패널에 있다) |
| 8 | 재생 중 선택한 객체가 그 프레임에 없을 수 있다(nuScenes는 프레임이 바뀌어도 선택을 유지한다) | 판정 버튼을 끄고 "Not in this frame"을 보여준다 |
| 9 | F4가 한 세션에 끝나지 않을 수 있다 | 단계마다 동작하는 상태로 끝낸다. F4-F는 뺄 수 있다. 남으면 HANDOFF에 어디까지 했는지 적는다 |
| 10 | 연습 모드의 변형이 너무 작으면 못 찾고, 너무 크면 장난처럼 보인다 | 캡처로 보고 크기를 조정한다. 값은 상수로 모아 둔다 |

## 12. 뒤 기능에 넘기는 것

| 기능 | 넘기는 것 |
|---|---|
| F5 평가 | 정보 패널이 nuScenes에서 "Review" 패널이 된다. 평가 요약이 들어갈 자리는 버튼 영역 아래의 스크롤 영역이다. 준비 스크립트가 `visibility`를 내보내게 되므로 F5의 "가려진 객체 제외"에 그대로 쓸 수 있다. 연습 모드 채점의 찾음/놓침/헛짚음이 TP/FN/FP의 예습이 된다 |
| F6 카메라 6대 | "판단 불가"로 남긴 박스가 F6에서 다시 볼 대상이다. 카메라 확대와 투영 선은 카메라 값을 받는 구조라 6대로 늘려도 쓸 수 있어야 한다. `Detection2D.corners`가 카메라별로 필요해진다 |
| F8 박스 수정 | 반려 기록(사유 포함)이 수정할 박스의 목록이 된다. 저장할 것이 커지면 그때 IndexedDB를 검토한다 |
