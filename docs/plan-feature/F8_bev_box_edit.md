## 1. 목표

F4에서 3D 정답 박스를 승인 / 반려 / 보류로 판정하게 됐다. 그런데 반려한 박스는 "틀렸다"는 기록만 남고 **고칠 방법이 없다.**
F8은 그 박스를 직접 고치는 기능이다.

3D 공간에서 박스를 잡아 끄는 것은 어렵다(마우스는 2차원인데 박스는 3차원이라, 어느 방향으로 끄는지 정하기 어렵다).
그래서 **위에서 내려다본 화면**에서 고친다. 위에서 보면 3D 박스는 **기울어진 사각형**이고, 위치, 가로세로 크기, 방향은
2차원 조작으로 충분하다. 높이만 숫자로 받는다.

여섯 가지를 만든다(받은 범위 그대로다).

| # | 만드는 것 |
|---|---|
| ① | 위에서 본 편집 화면: 고칠 박스(기울어진 사각형)와 그 주변의 LiDAR 점 |
| ② | 조작: 이동, 가로세로 크기, 방향. 높이는 숫자 |
| ③ | 원본을 고치지 않는다. 수정은 덮어쓰는 별도 기록. 화면에 "수정됨", 원래대로 되돌리기 |
| ④ | 실행 취소와 다시 실행 |
| ⑤ | 고치는 동안 카메라 사진(6대)과 3D 화면의 박스가 따라 바뀐다 |
| ⑥ | 내보내기에 수정 내용(원본에서 무엇이 달라졌는지). 형식 `review@2` → `review@3` |

**바꾸지 않는 것:** 채점 규칙, 평가 / 검색 / 표본 검수의 숫자(셋 다 원본 박스로 계산한다), 저장돼 있는 검수 기록.

**새 용어 (그 자리에서 풀어 쓴다. 용어집에 더한다)**
- **위에서 본 화면(BEV, bird's-eye view):** 하늘에서 수직으로 내려다본 지도. 높이가 사라지고 가로세로만 남는다.
- **yaw(요):** 위에서 봤을 때 박스가 향하는 방향의 각도. 나침반 바늘이 도는 방향의 회전이다. 박스가 앞뒤로
  숙여지는 회전(pitch)이나 옆으로 기우는 회전(roll)과 구분한다.
- **heading(방향):** 박스의 "앞"이 어느 쪽인가. yaw와 같은 것을 가리킨다. 화면에서는 heading이라고 쓴다.
- **바닥 사각형(footprint):** 3D 박스를 위에서 봤을 때의 사각형.
- **손잡이(handle):** 사각형의 모서리와 변에 붙은, 끌어서 크기나 방향을 바꾸는 작은 표시.
- **전역 좌표 / 차 좌표:** 전역 좌표는 지도에 고정된 좌표(nuScenes가 박스를 적는 방식), 차 좌표는 차를 원점으로 한 좌표
  (화면이 그리는 방식). 용어집의 global / ego와 같다.
- **덮어쓰는 기록(edit):** 원본 박스는 그대로 두고 "이 박스는 이렇게 고쳤다"만 따로 적은 것. 화면은 원본 위에 이것을 덮어
  그린다. 기록을 지우면 원본이 그대로 나온다.

## 2. 지금의 문제와 확인한 사실

추측하지 않고 재거나 코드에서 확인했다. 숫자에는 환경을 함께 적는다. 측정은 모두 2026-11-27, 이 컴퓨터에서 했다.

### 2.1 지금은 고칠 길이 없다

`review-store`의 기록(`ReviewRecord`)에는 판정, 사유, 메모, 시각만 있고 **좌표가 없다**(`lib/review/types.ts`). 박스의 값은
데이터 파일에서 파싱한 그대로이고, 화면 어디에도 박스의 값을 바꾸는 입력이 없다(시안 1).

### 2.2 3D 박스가 코드에 들어 있는 모양

| 자리 | 표현 |
|---|---|
| 원본 파일 (`frames.json`의 `annotations`) | **전역 좌표**의 중심 `[x, y, z]`, 크기 `[폭, 길이, 높이]`, 회전 쿼터니언 `[w, x, y, z]` |
| 앱 안 (`Detection3D.bbox3D`) | **화면(three.js) 좌표**의 중심, 크기 `[길이, 폭, 높이]`, 회전 쿼터니언 `[x, y, z, w]` |

파서(`lib/nuscenes/parser.ts`)가 전역 → 차 → 화면 좌표로 바꿔 넣는다. 쿼터니언은 회전을 숫자 4개로 적는 방법이다.

**실제 데이터로 확인한 것 (404프레임, 박스 18,538개 전부. Node 스크립트로 원본 파일을 읽음)**

| 확인한 것 | 결과 |
|---|---|
| nuScenes의 박스 회전에 yaw 말고 다른 회전이 섞여 있는가 | **없다.** 박스의 수직축이 전역 수직축에서 벗어난 각도는 최대 0.000001° |
| 차(차 좌표의 수직축)는 전역 수직축에서 얼마나 기울어 있는가 | 최대 **4.59°** (언덕길). 박스 18,538개 중 1,962개가 3° 이상 기운 프레임에 있다 |
| 프레임 하나의 박스가 가장 많은 곳 | scene-0061의 20번째 프레임, **156개** |
| 프레임 하나의 LiDAR 점 (앱에 실린, 솎아낸 점) | 2,880 ~ 7,638개 (평균 5,388개) |
| 박스의 크기 | 길이 0.31 ~ 14.47m (가운데 값 1.96m), 폭 0.21 ~ 4.74m, 높이 0.46 ~ 4.59m |

이 표에서 나오는 결론 두 가지:
- nuScenes의 박스는 **숫자 7개**(중심 x, y, z + 폭, 길이, 높이 + yaw)로 빠짐없이 적을 수 있다. 위에서 본 화면이 고치는 것이
  바로 이 7개 중 5개(x, y, 폭, 길이, yaw)이고, 나머지 2개(z, 높이)가 숫자 칸이다.
- 차가 기울어 있으므로 "어느 축으로 돌리느냐"를 정해야 한다(결정 5).

### 2.3 바꾸고 되돌리는 계산은 손실 없이 되는가

앱의 박스(화면 좌표) → nuScenes의 7개 숫자 → 다시 앱의 박스로 한 바퀴 돌려 봤다. 임시 테스트 파일로 앱의 변환 함수
(`lib/geometry`)를 실제 박스 18,538개에 돌렸고, 잰 뒤 지웠다.

| 비교 | 가장 큰 차이 |
|---|---|
| 되돌린 중심 대 원본 파일의 중심 | 0.0000000000002m (2.3×10⁻¹³) |
| 되돌린 크기 대 원본 파일의 크기 | 0 (완전히 같다) |
| 되돌린 회전 대 원본 파일의 회전 | 0.000006° (각도를 재는 계산 자체의 오차 수준) |
| 7개 숫자로 다시 만든 3D 박스 대 파서가 만든 3D 박스 | 중심 0.0000000000003m |
| 7개 숫자로 다시 만든 사진 위 사각형 대 파서가 만든 것 (카메라 6대, 사각형 22,081개) | 0.000000000005px. 생기고 안 생기고가 어긋난 것 **0개** |

**된다.** 그리고 고치지 않은 박스는 이 계산을 아예 지나지 않는다(덮어쓰는 기록이 있는 박스만 다시 만든다). 되돌리면 기록이
지워지고 원본 박스가 그대로 다시 나온다.

### 2.4 박스 하나만 다시 투영하는 함수를 파서에서 꺼낼 수 있는가

꺼낼 수 있다. `parser.ts`의 108~161줄이 "주석 하나 → 3D 박스 1개 + 카메라마다 2D 사각형"을 만드는 부분이고, 쓰는 함수는
모두 `lib/geometry`의 순수 함수다. 박스 하나를 카메라 6대에 다시 투영하는 데 **약 0.005ms**가 걸렸다(Node, 20,000번의 평균).
끄는 동안 매번 해도 된다.

**걸리는 것 하나:** 파싱이 끝난 `Frame`에는 투영에 필요한 값(프레임의 차 위치, 카메라마다의 차 위치·카메라 자세·렌즈 값)이
**남아 있지 않다.** 원본 파일도 메모리에 두지 않는다(`loadScene`이 파싱한 뒤 버린다). 그래서 이 값을 `Frame`에 남기는 길이
필요하다(결정 6).

### 2.5 사각형 156개와 점을 그리고 하나를 끄는 동안의 프레임 시간

임시 시험 페이지(위에서 본 화면만 그리는 React 페이지)를 만들어 **배포용 빌드**(3100번)에서 쟀고, 잰 뒤 지웠다.
scene-0061의 20번째 프레임(박스 156개, 점 5,659개), 화면 560×508px, 창 1536×700, 창 없는 Chromium. 박스 하나를 2초 동안
마우스로 240번 움직이며 화면이 새로 그려지는 간격을 쟀다. 60fps면 간격이 16.7ms다. 한 번씩 잰 값이다.

| 점을 그리는 방법 | 소프트웨어 렌더링: 가운데 값 / 가장 긴 간격 / 25ms 넘은 횟수 | 내장 GPU(Intel UHD): 같은 순서 | 움직임 한 번의 작업 시간 |
|---|---|---|---|
| 점 없음 (박스만) | 16.7 / 33.3ms / 427번 중 1번 | 16.7 / 16.8ms / 0번 | 2.2 ~ 3.3ms |
| **Canvas 2D** | 16.7 / 33.3ms / 400번 중 1번 | 16.7 / 16.8ms / 0번 | 2.3 ~ 2.8ms |
| SVG 선 하나에 점을 모두 넣기 | 16.7 / 33.4ms / 386번 중 1번 | 16.7 / 16.8ms / 0번 | 2.2 ~ 2.7ms |
| SVG 원 5,659개 | 16.7 / **116.7ms** / 445번 중 3번 | 16.7 / 16.8ms / 0번 | **6.3 ~ 7.6ms** |

표의 프레임 간격은 프레임 전체(가로 120m)가 보이게 한 화면의 값이다. 박스 주변(가로 30m)으로 당긴 화면도 쟀다: 25ms를 넘은
간격이 SVG 원에서만 나왔고(422번 중 3번, 가장 긴 간격 149.9ms), 나머지 셋은 0번이었다. "작업 시간"은 두 화면과 두 렌더링의
값을 합친 범위다.

- 박스 156개는 **SVG로 충분하다.** 끄는 동안 다시 그려지는 것은 고르는 박스 하나와 손잡이뿐이게 만들었다(나머지 155개와
  점은 그대로 둔다). 움직임 한 번의 자바스크립트 시간은 0.5 ~ 0.7ms였다.
- 점은 **Canvas 2D**가 맞다. 5,659개를 한 번 그리는 데 0.1 ~ 0.7ms였다. SVG 원으로 그리면 요소가 5,659개 생겨 움직임마다의
  작업 시간이 3배가 되고 긴 끊김이 나왔다. "SVG 선 하나"도 끄는 동안은 비슷했지만, 박스 안의 점만 다른 색으로 칠하려면
  Canvas가 단순하다.
- **이 측정이 말해 주지 않는 것:** 시험 페이지에는 3D 화면도 `page.tsx`도 없었다. 실제 앱에서는 끄는 동안 3D 화면과 사진의
  박스도 함께 다시 그린다. 그 비용은 단계 C에서 실제 앱으로 잰다(8장).

### 2.6 점이 아직 오지 않았을 때와 받지 못했을 때

점은 프레임을 열 때 따로 받는다(`useFramePoints`). 상태가 넷이다: `loading`(오는 중), `ready`, `failed`(받지 못함),
`inline`(프레임에 들어 있음. COCO와 옛 형식). F7의 측정으로는 첫 화면에서 박스보다 약 0.4초 늦게 온다(20Mbps). 점은 박스가
맞는지 보는 근거이므로, 점 없이 고치게 둘지를 정해야 한다(결정 12).

### 2.7 수정 기록을 어디에 둘 것인가

- `review-store`의 구역은 세 개이고, 구역 하나는 `ReviewRecord`의 모음이다. 저장값을 읽을 때 `sanitizeReviews`가 **판정이
  없는 기록을 버린다**(`lib/review/persisted.ts`). 수정 기록에는 판정이 없고 좌표가 있으므로 네 번째 "구역"으로는 들어갈 수
  없다. 넣으려면 같은 저장 키 안에 `reviews` 옆에 새 필드를 두어야 한다.
- 같은 키에 두면 생기는 일: 이 store는 바뀔 때마다 **전체를 다시 쓴다.** F8 이전의 코드로 열려 있던 탭이 저장하면
  `{ reviews }`만 써서 수정 기록이 통째로 사라진다. 반대로 별도의 키를 쓰면 옛 코드는 그 키를 건드리지 않고, 새 코드는
  지금의 키(`ai-detection-viewer.review`)를 지금과 똑같은 모양으로만 쓴다. **사용자의 브라우저에 있는 표본 판정 100개가 깨질
  길이 없다.**
- 기록 하나는 숫자 7개와 ID 2개, 시각 하나로 약 260바이트다(잰 값이 아니라 계산값). 1,000개를 고쳐도 약 0.26MB라
  localStorage(약 5MB)로 충분하다. IndexedDB는 필요 없다.

### 2.8 연습 모드의 구조를 쓸 수 있는가

`makePracticeSet`은 **원본 파일의 값**(전역 좌표)을 고친 뒤 파서를 통째로 다시 돌린다. 그래서 3D 박스, 투영, 2D 사각형이
같은 값에서 나오고 ID가 그대로다. 이 생각("원본의 표현에서 고치고, 파서와 같은 계산으로 다시 만든다")은 그대로 쓴다.
구조 자체는 그대로 쓸 수 없다: 장면의 원본 파일을 다시 받아 41프레임을 통째로 다시 파싱하므로(F4에서 잰 값: 전환에 약
0.55초) 끄는 동안 매번 할 수 없다. 그래서 2.4의 "박스 하나만 다시 만드는 함수"가 필요하다.

연습 모드가 주는 것이 하나 더 있다: 심어 둔 오류의 **바꾸기 전 진짜 라벨**을 앱이 알고 있다(연습 중에도 원래 장면이
메모리에 있다). 고친 결과를 채점할 수 있다는 뜻이다(후보 ③).

### 2.9 실행 취소: 직접 만들지, 라이브러리를 쓸지

`zundo`(Zustand용 실행 취소 미들웨어)의 최신판은 2.3.0이고, 요구하는 Zustand는 `^4.3.0 || ^5.0.0`이다(npm 등록 정보,
2026-11-27 조회). 이 프로젝트는 `zustand ^5.0.13`이므로 **버전은 맞는다.** 설치하지는 않았다. 비교는 결정 9.

## 3. 바뀐 뒤의 모습

시안 번호는 [compare.html](assets/F8/compare.html)의 번호다.

**들어가기 (시안 2).** 검수 모드에서 박스를 고르면 Review 패널 맨 아래 줄에 **Edit box [E]** 버튼이 있다. 판정을 내릴 수 있는
박스라면 어느 박스에나 나온다(반려한 박스만이 아니다).

**편집 화면 (시안 3, 4).** 화면 틀은 그대로이고 칸의 역할이 바뀐다(평가 모드, 표본 검수와 같은 방식).
- **위에서 본 화면이 목록과 3D 화면의 자리에 나타난다.** 보기가 둘이고 버튼(`V`)으로 오간다(결정 1).
  **집중 보기**(처음 상태): 두 칸을 모두 쓴다(1536×700에서 1112×508px. 시안 8). 3D 화면은 밑에 그대로 있고 가려진다.
  **함께 보기**: 반씩 나눠 3D 화면이 옆에 나온다(552×508px씩. 시안 3, 4). 목록은 어느 보기에서도 보이지 않는다.
  사진, 썸네일, 패널은 두 보기에서 같은 자리에 있다.
- **위에서 본 화면:** 차의 앞이 위쪽이다. 고르는 박스는 흰 사각형, **앞쪽 변이 하늘색**, 다른 박스들은 클래스 색의 가는 선.
  LiDAR 점은 하늘색, **박스 안에 들어온 점은 노란색.** 박스를 고친 뒤에는 **nuScenes의 원래 라벨이 회색 점선**으로 함께 보인다.
  차의 위치(작은 화살표), 차에서 10m마다의 점선 원, 눈금 막대가 있다. 휠로 확대하고 빈 곳을 끌어 옮긴다.
- **조작:** 박스 안을 끌면 이동, 변의 네모는 그 변만(반대쪽 변은 그 자리), 모서리의 네모는 가로세로를 함께(대각 모서리는
  그 자리), 앞쪽의 동그란 손잡이는 방향. 높이와 위아래 위치는 숫자 칸.
- **3D 화면과 사진:** 끄는 동안 큰 사진과 썸네일 6장 위의 그 박스가 함께 움직인다. 3D 화면의 그 박스도 함께 움직이고,
  함께 보기에서 보인다(집중 보기에서는 가려져 있다가, 보기를 바꾸거나 끝내면 고친 자리에 있다).
- **필터 줄 자리의 편집 줄:** `EDIT BOX · car 527702 · frame 9`, 3D 화면 함께 보기(`V`), Undo, Redo, Revert to label, Done.
- **정보 패널 자리의 Edit box 패널:** 숫자 칸 다섯(Length, Width, Height, Heading, Up/down), "Changed from the label: moved
  0.54 m · length +0.35 m · turned 6.0°", 지금의 판정.

**끝낸 뒤 (시안 10).** Done(또는 Esc)을 누르면 검수 화면으로 돌아온다. 고친 박스는 고친 자리에 그려지고, "수정됨"이 네
군데에 보인다: 목록의 그 줄, 3D 화면의 이름표(`· 1 box edited`), 맨 위 줄(`1 edited`), 패널의 버튼(`Edited · edit [E]`).
Selected 칸에 무엇이 달라졌는지와 Revert to label이 있다.

**내보내기.** Export의 JSON / CSV에 수정 내용이 들어간다: 원본 값, 고친 값, 차이(옮긴 거리, 크기 차이, 돌린 각도).

**평가, 검색, 표본 검수.** 달라지지 않는다. 세 화면은 nuScenes의 원본 박스를 그리고 원본으로 계산한다.

## 4. 범위와 범위 밖

**범위:** 1장의 ① ~ ⑥.

**후보 (7장에서 추천과 함께 묻는다)**
- ㉮ 반려한 박스를 차례로 넘기며 고치는 흐름(장면을 넘어서)
- ㉯ Explore의 조건 "반려한 박스가 있는 프레임"
- ㉰ 연습 모드에 심어 둔 오류를 고쳐 보고 진짜 라벨과 얼마나 가까워졌는지 보여 주기

**범위에 글자 그대로는 없는데 추천안에 넣은 것 (7장에서 묻는다)**
- 위아래 위치를 숫자로(범위는 "높이는 숫자"라고만 했다. 높이는 크기이고, 박스가 떠 있거나 묻혀 있는 것은 위치다)
- 화살표 키로 5cm씩 옮기기
- 박스 안에 들어온 점을 다른 색으로 칠하고 개수를 보여 주기

**범위 밖 (하지 않는다)**
- 3D 화면에서 박스를 직접 잡아 끄는 조작.
- 새 박스 만들기, 박스 지우기, 클래스 바꾸기.
- 모델의 박스(예측) 수정, 카메라 사진 위에서 2D 박스를 직접 고치기.
- 채점 규칙 변경. 고친 박스를 평가 / 검색 / 표본 검수에 넣기.
- 묶음 나(PR 곡선, 혼동행렬 등), 묶음 다(다른 주행의 밤 장면, 3D 예측 보기).
- 여러 박스를 한꺼번에 고치기, 고친 것을 다음 프레임의 같은 물체에 옮겨 적용하기(프레임마다 따로 고친다).
- 내보낸 파일을 다시 불러오기(지금도 없다).
- 화면의 한글화, 백엔드, DB, 인증. COCO(추정 3D는 고칠 대상이 아니다).

| **A + B (추천)** | 편집에 들어가면 **집중 보기**(B: 목록과 3D 칸을 모두 덮는다). 버튼 `V`로 **함께 보기**(A: 반씩, 3D 화면이 옆에)와 오간다. 고른 보기는 그 방문 동안 기억한다 | 고치는 데 집중하는 넓은 화면과, 3D에서 결과를 보는 화면을 둘 다 얻는다. 가장 좁은 창(1024px)에서 조작 화면이 316px가 아니라 640px다 | 처음 상태에서는 3D 화면이 가려져 있다(사진은 보인다). 확인할 화면이 창 크기마다 둘이 된다. 편집 줄에 버튼 하나, 단축키 하나가 는다 |
| A만 | 반씩 | 3D 화면이 늘 보인다 | 조작 화면이 늘 절반이다(1024px에서 316px) |
| B만 | 전체를 덮기 | 가장 단순하다 | 편집 중에는 3D 화면을 볼 수 없다 |
| C | 목록 칸에만 | 화면 틀을 바꾸지 않는다 | 조작 화면이 가장 작다 |

**코드가 얼마나 늘어나는가 (물은 것에 대한 답): 적다. A만 할 때보다 화면 틀의 입력 하나, 상태 하나, 버튼 하나가 더 든다.**
- 두 보기 모두 위에서 본 화면을 **이미 있는 "덮는 자리"에** 둔다(보고서 창이 쓰는 자리. F7.5). 집중 보기는 그 자리를 지금처럼
  목록과 3D 칸에 걸치고, 함께 보기는 목록 칸에만 걸치면서 두 칸의 폭을 같게 한다. 3D 화면은 두 보기 모두에서 화면 틀의 같은
  자리에 있으므로 캔버스를 다시 만들지 않는다.
- 위에서 본 화면이 어떤 크기에서도 그려져야 하는 것은 A만 할 때도 같다(창 크기를 바꿀 수 있으므로).
- 늘어나는 것은 주로 **확인**이다: 창 크기 넷 × 보기 둘에서 글자 겹침과 스크롤을 본다.

**집중 보기에서 정해 둘 것**
- 3D 화면은 가려진 채로도 계속 그려진다(보고서 창이 열려 있을 때와 같다). 끄는 동안 그 비용이 얼마인지는 단계 C에서 두 보기를
  번갈아 재고, 크면 가려진 동안 3D 그리기를 멈추는 방법을 재 본 뒤 정한다.
- **보기를 바꿀 때는 움직임을 넣지 않는다.** 3D 칸의 폭이 바뀌는 동안 매 순간 3D 그림을 새 크기로 다시 만들어야 한다.
- 범위 ⑤의 "3D 화면의 박스가 따라 바뀐다"는 함께 보기에서 확인한다. 집중 보기에서는 사진 6장이 따라 바뀌는 것이 보인다.

### 추천안으로 진행하고 캡처를 보며 조정할 것

**결정 5. 박스를 무엇으로 적고, 어느 축으로 돌리나**
- **추천:** 수정은 nuScenes가 쓰는 표현 그대로, **전역 좌표의 숫자 7개**(중심 x, y, z / 폭, 길이, 높이 / yaw)로 다룬다.
  **방향은 전역 수직축(중력 방향)으로 돌린다.** 이동은 화면의 평면(차의 바닥면) 위에서 한다.
- **이유:** nuScenes의 박스는 모두 yaw만 가진다(2.2). 전역 수직축으로 돌리면 고친 박스도 그 형식 그대로라 내보낸 값을
  데이터셋의 값과 바로 비교할 수 있다. 이동을 차의 바닥면에서 하는 것은 화면에서 끄는 방향과 정확히 같고, 언덕길에서
  박스가 길을 따라 움직인다.
- **대안:** ⓐ 앱의 박스(화면 좌표의 쿼터니언)를 직접 고친다: 변환이 없어 단순하지만 내보낼 때 결국 되돌려야 하고, 무엇을
  돌렸는지가 숫자 하나로 남지 않는다. ⓑ 차의 수직축으로 돌린다: 화면이 보는 방향과 정확히 같지만, 차가 기운 프레임에서는
  고친 박스가 nuScenes의 형식(yaw만)에서 벗어난다.
- **대가:** 차가 기운 프레임(최대 4.59°)에서는 위에서 본 화면의 회전이 화면의 축과 그만큼 어긋난다. 5m짜리 차를 90° 돌릴 때
  바닥 사각형의 모서리가 화면에서 최대 약 1.6cm 어긋나는 크기다(계산값: 5m × (1 − cos 4.59°)).

**결정 6. 박스 하나를 다시 만드는 함수와, 그것에 필요한 값**
- **추천:** 파서의 그 부분을 순수 함수로 꺼내 **파서와 편집이 같은 함수를 쓴다.** 필요한 값은 `Frame.egoPose`와
  `CameraView.calibration`으로 남긴다(선택 필드).
- **이유:** 계산이 한 곳에만 있으면 파서와 편집이 어긋날 수 없다. 2.3의 대조가 그대로 테스트가 된다.
- **대안:** ⓐ 연습 모드처럼 원본 파일을 고쳐 통째로 다시 파싱: 끄는 동안 쓸 수 없다(2.8). ⓑ 보정값을 `Frame` 밖의 표에
  따로 두기: 타입은 그대로지만 프레임과 그 표를 함께 들고 다녀야 한다.
- **대가:** `Frame`과 `CameraView`에 필드가 하나씩 는다(프레임당 숫자 약 150개, 404프레임에 약 6만 개. 계산값). 파서를
  건드린다(결과가 같다는 것은 기존 테스트가 잠근다).

**결정 7. 수정 기록을 어디에 두나**
- **추천:** 별도의 store `edit-store`, **별도의 저장 키.** 저장, 깨진 값 걸러내기, 탭 사이 맞추기, 저장 실패 알림은
  `review-store`와 같은 방식으로 만든다(`createSafeStorage`를 함께 쓴다).
- **이유:** 2.7. 지금의 키를 지금과 같은 모양으로만 쓰므로 기존 기록이 깨질 길이 없다. 기록의 모양이 다르다(판정이 없고
  좌표가 있다).
- **대안:** `review-store`에 필드를 더한다: 저장과 탭 맞추기를 한 번에 얻지만, 옛 코드로 열린 탭이 수정 기록을 지울 수 있고
  저장 형식의 버전을 올려야 한다.
- **대가:** store가 셋이 된다. 탭 맞추기가 키 둘을 듣는다. "Not saved" 표시가 두 store의 상태를 함께 본다.

**결정 8. 기록의 모양과 구역**

**결정 9. 실행 취소를 직접 만들지, 라이브러리를 쓸지**

  패널 버튼, Selected 칸의 Edit 줄. 화면의 말: 고친 박스는 **edited**, 원본은 **label**(the nuScenes label).
  "correct", "fixed", "ground truth"라고 쓰지 않는다. 버튼 이름도 "Fix"가 아니라 "Edit box"다.
- **대가:** 3D 화면 안에서는 고친 박스와 아닌 박스의 선 색이 같다(색은 클래스의 것이다). 구별은 이름표와 목록으로 한다.

**결정 17. 근거 줄의 LiDAR 점 개수**
- **추천:** nuScenes의 점 개수는 **원본 라벨**에 대해 센 값이다. 고친 박스에서는 "153 pts in the label"처럼 무엇의 값인지
  적는다. 연습 모드가 이미 같은 말을 하고 있다("LiDAR and visibility values still describe the original labels").

**결정 18. 내보내기 `review@3`**
- **추천:** 줄 하나 = **판정이 있거나 수정이 있는 박스.** 지금(`@2`)의 필드는 그대로 두고 `edit`를 더한다:
  `edit: null` 또는 `{ original: {translation, size, yaw, rotation}, edited: {…}, change: {movedMetres, sizeDelta: [폭, 길이, 높이], turnedDegrees}, editedAt }`.
  수정만 있고 판정이 없는 줄은 `verdict: null`이다. `summary`에 `edited`가 는다. CSV에는 열이 는다(`edited`, `moved_m`,
  `d_width_m`, `d_length_m`, `d_height_m`, `turned_deg`와 고친 값 7개). 값은 nuScenes의 표현(전역 좌표, 폭·길이·높이,
  쿼터니언 `[w, x, y, z]`)이다.
- **이유:** "원본에서 무엇이 달라졌는지"를 파일만 보고 알 수 있다. 원본 값도 함께 있어 데이터셋 없이 비교된다.
- **대안:** `reviews[]`는 그대로 두고 `edits[]`를 따로: `@2`를 읽던 코드가 `reviews`를 그대로 읽지만, 박스 하나의 판정과
  수정이 두 군데로 갈린다.
- **대가:** `verdict`가 `null`일 수 있게 된다(그래서 버전을 올린다). 원본 값은 앱의 박스를 되돌려 계산한 것이라 원본 파일의
  숫자와 0.0000000000003m 안에서 같다(2.3). 파일에는 소수 여섯 자리까지 적는다.
- 앱은 내보낸 파일을 다시 읽지 않으므로 "옛 형식 읽기"는 저장값의 일이고, 결정 7로 기존 저장값은 바뀌지 않는다.

**결정 19. 크기와 방향의 규칙**
- **추천:** 변의 손잡이는 반대쪽 변을, 모서리의 손잡이는 대각 모서리를 그 자리에 둔다(중심이 따라 움직인다). 가장 작은 크기는
  0.1m. Height 숫자를 바꾸면 **바닥은 그 자리**다(연습 모드의 크기 오류와 같은 규칙). Heading 숫자는 차의 앞을 0°로 한
  각도다. 각도를 일정한 간격으로 붙잡는 기능은 넣지 않는다.

**결정 20. 키**
- **추천:** `E` 들어가기, `Esc` 끝내기, `V` 집중 보기 / 함께 보기, `Ctrl+Z` 실행 취소, `Ctrl+Shift+Z`와 `Ctrl+Y` 다시 실행, 화살표 5cm(Shift 50cm).
  편집 중에는 `[` `]`(옆 카메라)와 `Z`(사진 확대)만 남고 **나머지 검수 키(A R U C J K 1~6 N)는 꺼진다.** 숫자 칸에 글자를
  넣는 동안에는 어느 단축키도 받지 않는다(지금의 `isTypingTarget`). 한글 입력 상태의 키는 지금 방식(`event.code`)을 따른다.
- **대가:** 편집 중에는 판정을 바꿀 수 없다(끝내고 바꾼다).

**결정 21. 편집 중의 큰 사진**
- **추천:** 끄는 동안에는 카메라를 바꾸지 않는다. **놓았을 때** 그 사진에 박스가 더 보이지 않으면 박스를 가장 잘 보는
  카메라로 바꾼다(`pickCamera`). 썸네일 6장의 박스 표시는 끄는 동안에도 따라 움직인다.

**결정 22. 빠른 연타 지킴**
- **추천:** 편집 대상이 바뀐 뒤 400ms 동안은 **키보드로 하는 변경**(화살표, 숫자 확정)을 받지 않는다(F7.5의 `MIN_LOOK_MS`와
  같은 값). 후보 ㉮의 "다음 반려 박스"로 넘어간 직후의 화살표 키가 아직 보지 않은 박스를 옮기지 않게 한다. 마우스 끌기는
  박스를 보고 잡아야 하므로 막지 않는다.

**결정 23. 편집을 막는 조건**
- **추천:** 판정을 막는 조건과 같다(`getReviewBlock`): 재생 중, 선택 없음, 이 프레임에 그 물체가 없음, 필터로 숨겨짐.
  들어갈 때 재생을 멈춘다. 막힌 이유를 화면에 적는다.

**결정 24. 편집 화면이 나타나는 움직임** (사용자의 제안. [움직임 데모](assets/F8/motion.html)에서 네 가지를 눌러 볼 수 있다)
- **추천: 짧게 넣는다(② 약 0.16초, 살짝 커지며 또렷해진다). 닫을 때는 바로 사라진다.**
- **이유:** 화면의 큰 부분이 한순간에 바뀌므로 "무엇이 어디에 나타났는지"를 눈이 따라가게 해 주는 값이 있다. 다만 이 화면은
  박스를 여러 개 고칠 때 **열 번, 스무 번 열고 닫는다.** 점에서 커지는 긴 움직임(③, ④ 약 0.32초)은 처음에는 멋있고 반복하면
  기다림이 된다. 데모에서 E → Esc를 열 번 눌러 보고 고르면 된다.
- **코드의 양은 네 가지가 거의 같다**(CSS 몇 줄. 어디에서 커지는지와 걸리는 시간만 다르다). 그래서 이것은 취향으로 골라도 된다.
- **대안:** ① 넣지 않는다 / ③ 누른 버튼에서 커진다 / ④ 목록의 그 줄에서 커진다.
- **어느 것이든 지킬 것:** 운영체제에서 "움직임 줄이기"를 켠 사람에게는 움직임 없이 바로 보여 준다
  (`prefers-reduced-motion`). 움직이는 동안에도 키와 마우스를 막지 않는다. 닫는 움직임은 넣지 않는다(닫힌 뒤에도 화면에
  남겨 두는 상태가 하나 더 필요해진다).
- **대가:** 확인 스크립트가 움직임이 끝나기를 기다려야 한다(스크립트에서는 움직임 줄이기를 켜고 돌린다).

## 8. 완료 기준과 검증 방법

실제 앱을 Playwright로 조작해 통과/실패로 확인한다(배포용 빌드, 3100번). 통과해도 캡처를 눈으로 본다.

**범위**
- ① 편집 화면에 고르는 박스가 사각형으로, 그 프레임의 LiDAR 점과 함께 보인다. 박스 156개 프레임에서도 열린다.
- ② 박스를 끌면 중심이, 변 / 모서리 손잡이를 끌면 폭 / 길이가, 동그란 손잡이를 끌면 방향이 바뀌고, 패널의 숫자가 같은 값을
  보인다. Height와 Up/down은 숫자로 바뀐다. 변을 끌 때 반대쪽 변의 화면 위치가 1px 안에서 그대로다.
- ③ 원본 데이터와 `review-store`의 저장값이 바뀌지 않는다. 새로 고쳐도 수정이 남는다. Revert to label 뒤의 박스가 원본과
  완전히 같다(같은 객체). 목록, 3D 이름표, 패널에 "edited"가 보이고 Revert 뒤 사라진다.
- ④ 끌기 세 번 → Ctrl+Z 세 번이면 원본이고, 다시 실행 세 번이면 세 번째 상태다. 끌기 한 번은 한 단계다.
- ⑤ 끄는 **동안**(놓기 전) 3D 화면의 그 박스의 위치와, 사진 위 그 박스의 사각형이 바뀐다(중간에 읽어 확인). 카메라 6대:
  고친 박스의 사각형이 여섯 사진 모두에서 "7개 숫자로 다시 만든 값"과 같다(순수 함수 테스트). 썸네일의 표시가 따라 움직인다.
- ⑥ 내려받은 JSON이 `review@3`이고, 고친 박스의 줄에 원본 / 고친 값 / 차이가 있으며, 화면의 "moved 0.54 m"와 같은 숫자다.
  판정만 있는 줄은 `@2` 때와 같은 값이다.

**그대로여야 하는 것**
- 테스트가 잠근 숫자 전부(scene-0916 첫 10프레임 91 / 83 / 13 / 26, 349 / 182 / 107 / 180, 6번 프레임 28 / 16 / 17,

## 9. 불변 규칙과의 관계

| 규칙 | 관계 |
|---|---|
| #1 2D와 3D의 ID가 같다 | 고친 박스의 3D 박스와 카메라 6대의 2D 사각형은 **같은 함수가 같은 ID로** 만든다. ID를 바꾸는 곳이 없다 |
| #2 선택은 `selectedObjectId` 하나 | "고치는 박스"라는 상태를 만들지 않는다. 편집 대상은 지금 프레임의 `selectedObjectId`다(결정 13) |
| #3 변환 로직은 컴포넌트와 store 밖 | 사각형의 계산, 손잡이 위치, 다시 투영, 덮어쓰기, 이력, 차이 계산 모두 `lib/editing`과 `lib/nuscenes`의 순수 함수이고 테스트한다. store는 결과를 넣기만 한다 |
| #4 범위를 넓히지 않는다 | 범위 밖의 것(새 박스, 삭제, 클래스 등)은 만들지 않는다. 범위에 글자 그대로 없는 세 가지는 결정 3에서 묻는다 |
| #5 3D 화면이 주 화면 | 위에서 본 화면은 **조작하는 도구**이고, 편집을 끝내면 3D 화면이 그대로 돌아온다. 집중 보기에서는 편집하는 동안 3D 화면이 가려진다. F7.5의 보고서 창이 같은 자리를 같은 방식으로 덮고 있고(사용자가 승인한 전례), 여기서는 키 하나(`V`)로 3D 화면을 옆에 꺼낼 수 있다. 3D 화면은 가려져 있어도 없어지지 않고(같은 캔버스), 고친 결과는 편집을 끝내는 순간 3D 화면에 있다. **이 규칙을 더 엄격하게 읽어 "처음 상태는 함께 보기"로 하고 싶으면 처음 상태만 바꾸면 된다**(코드는 같다) |
| #6 정직한 표시 | 고친 박스가 화면에 있으면 3D 이름표가 그렇게 말한다(`· N edited`). 고친 박스를 "정답"이라 부르지 않는다. nuScenes의 점 개수는 원본 라벨의 값이라고 적는다. 평가는 원본으로 한다 |
| #7 COCO는 2D뿐 | COCO에는 편집이 없다(추정 3D는 고칠 대상이 아니다. F4의 검수와 같다) |

## 10. 위험 요소

- **끄는 동안의 실제 비용을 아직 모른다.** 2.5의 측정에는 3D 화면과 페이지가 없었다. 끄는 동안 `page.tsx` 전체가 다시
  그려지면 느릴 수 있다. 대비: 끄는 중의 박스는 지금 프레임 하나에만 덮고(장면의 41프레임 전체를 다시 만들지 않는다),
  단계 C에서 먼저 잰다.
- **파서를 건드린다.** 108~161줄을 옮기는 것이 결과를 바꾸면 잠근 숫자가 전부 흔들린다. 대비: 옮기기 전에 "지금 파서의 결과와
  한 글자도 다르지 않다"를 실제 파일 테스트로 먼저 잠그고 옮긴다.
- **`page.tsx`가 다시 커진다.** 지금 2,175줄이다. 대비: 상태와 핸들러는 처음부터 `useBoxEditor`에 쓰고, 단계마다 줄 수를 알린다.
- **기존 확인 스크립트가 낡는다.** 검수 패널에 버튼이 하나 늘고 목록 줄에 표시가 생긴다. 실패가 나오면 화면을 찍어 가린다.
- **칸의 폭이 바뀔 때 3D 카메라의 구도.** 3D 칸이 좁아지면 같은 카메라가 좌우를 덜 보여 준다. 고르는 박스가 화면 밖으로
  나갈 수 있다. 대비: 단계 B의 캡처에서 보고, 필요하면 편집에 들어갈 때 Follow(고른 박스를 가운데에)를 켜는 것을 묻는다.
- **언덕길에서의 어긋남**(결정 5의 대가). 차가 가장 기운 프레임에서 캡처로 확인한다.
- **재지 못하는 것:** 사용자의 실제 브라우저와 RTX 4060. 측정은 창 없는 Chromium(소프트웨어 렌더링과 내장 GPU)이다.
