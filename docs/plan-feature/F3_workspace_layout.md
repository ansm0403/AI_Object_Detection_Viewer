# F3 — 스크롤 없는 작업 화면

- **상태:** 임시 승인 (2026-11-25). 7장의 결정 9개는 모두 **추천안으로 진행**한다. 사용자의 판단은
  "직접 보기 전에는 알 수 없다"였으므로, 결정 1~8은 최종 결정이 아니라 **만들어서 보여주고 조정하는 출발점**이다.
  결정 9에 따라 구현 전에 화면 시안을 먼저 만든다. 조정한 내용은 완료 기록에 남긴다.
- **작성일:** 2026-11-25
- **로드맵:** `.claude/docs/post-mvp-checklist.md` → "Roadmap — F3+ direction"

## 1. 목표

> 페이지를 위아래로 스크롤하지 않고, **객체 목록, 3D 뷰, 카메라 이미지, 정보 패널, 타임라인을 한 화면에서**
> 보며 작업할 수 있게 한다.

F3은 **화면 배치와 마감을 바꾸는 작업**이다. 새 기능(검수, 평가)은 넣지 않는다. 다만 뒤에 올 F4(검수)와
F5(평가)가 들어갈 자리를 미리 고려해서 배치한다.

## 2. 지금의 문제

2026-11-25에 실제 화면을 1440×900 크기로 캡처하고 코드를 확인한 결과다.

| # | 문제 | 원인 (코드) |
|---|---|---|
| 1 | 객체 목록과 분석 패널이 화면 아래에 있어서, "목록에서 클릭 → 3D에서 확인"에 스크롤이 필요하다 | `page.tsx`가 세로로 쌓는 12칸 그리드다. 뷰어 → 타임라인 → 목록/분석 순서로 내려간다 |
| 2 | 화면 양옆이 비어 있다 | `<main>`에 `max-w-screen-xl`(최대 1280px)이 걸려 있다 |
| 3 | 2D와 3D 패널의 모양이 다르다 | `Viewer2D`는 `bg-zinc-900 rounded-lg`에 테두리가 있고, `Viewer3D`는 `bg-neutral-950 rounded`에 테두리가 없다. 둘 다 `aspect-[4/3]` 고정이라 16:9인 nuScenes 사진은 위아래에 빈 띠가 생긴다 |
| 4 | 헤더는 "40 detections", 목록은 "OBJECTS (13)"이다 | 헤더는 `detections3D`(3D 박스 전체, 40개)를 세고, 목록·클래스 집계·타임라인 배지는 `detections2D`(카메라에 보이는 것, 13개)를 센다. 화면에는 이 차이에 대한 설명이 없다 |
| 5 | 목록의 ID가 32자 해시라 읽을 수 없다 | `ObjectList`가 `d.id`를 그대로 출력한다 |
| 6 | confidence 차트의 축 숫자만 유난히 크다 | `ConfidenceHistogram`의 SVG가 `viewBox="0 0 200 60"`에 `w-full`이다. 패널이 700px이면 그림 전체가 3.5배로 커지고, 8px 글자가 28px가 된다 |
| 7 | 3D 조작 안내만 한국어다 | `HintBox`의 문구("드래그 · 회전"). 나머지 UI는 영어다 |

## 3. 바뀐 뒤의 모습

### 3.1 배치 (넓은 화면, 가로 1024px 이상)

```
┌────────────────────────────────────────────────────────────────────────┐
│ 상단 바: 제목 · 데이터셋 전환 · MEASURED 배지 · 프레임/객체 수           │
├────────────────────────────────────────────────────────────────────────┤
│ 필터 바: 거리(또는 confidence) 슬라이더 · 클래스 칩 · 보이는 수 · Reset  │
├─────────────┬─────────────────────────────────────┬────────────────────┤
│             │                                     │  카메라 이미지 (2D) │
│  객체 목록   │                                     │  + 2D 박스          │
│             │         3D 뷰 (메인)                 ├────────────────────┤
│  (패널 안에서│                                     │  선택한 객체 정보   │
│   만 스크롤) │                                     │  클래스별 개수      │
│             │                                     │  confidence 차트    │
│             │                                     │  (패널 안에서만     │
│             │                                     │   스크롤)           │
├─────────────┴─────────────────────────────────────┴────────────────────┤
│ 타임라인: 프레임 썸네일 · Follow · Reset · Play                          │
└────────────────────────────────────────────────────────────────────────┘
```

**핵심 원칙:** 페이지 전체는 스크롤되지 않는다. 내용이 넘치는 패널(객체 목록, 정보 패널)만
**패널 안에서** 스크롤된다.

### 3.2 크기 (예상값. 구현하면서 실제 화면으로 확인하고 조정한다)

| 영역 | 1440×900 | 1280×720 | 지금 (1440×900) |
|---|---|---|---|
| 상단 바 + 필터 바 | 약 92px 높이 | 같음 | 약 120px |
| 객체 목록 (왼쪽) | 약 272px 폭 | 약 240px 폭 | 화면 아래, 스크롤 필요 |
| **3D 뷰 (가운데)** | **약 736×680** | **약 648×500** | 720×540 |
| 카메라 이미지 (오른쪽 위) | 약 400×225 | 약 360×203 | 510×287 (사진이 실제로 차지하는 크기) |
| 정보 패널 (오른쪽 아래) | 약 400×455 | 약 360×297 | 화면 아래, 스크롤 필요 |
| 타임라인 (아래) | 약 112px 높이 | 같음 | 약 115px |

- 3D 뷰는 넓이가 약 29% 커진다(388,800 → 약 500,480 픽셀). 불변 규칙 #5(3D가 메인)를 더 분명히 한다.
- **카메라 이미지는 지금보다 작아진다**(폭 510 → 400). 이 배치의 가장 큰 대가다. 7장의 결정 1, 5에서 다룬다.

### 3.3 좁은 화면 (가로 1024px 미만)

지금처럼 **세로로 쌓고 페이지를 스크롤**한다. 작업 화면은 데스크톱용으로 만들고, 모바일에서는 "볼 수는 있다"
수준을 유지한다. 순서는 3D 뷰가 먼저 오도록 조정할지 구현 때 화면을 보고 정한다.

세로가 아주 짧은 창(높이 640px 미만)에서는 화면 틀의 최소 높이를 640px로 두어, 패널이 찌그러지는 대신
페이지가 조금 스크롤되게 한다.

## 4. 범위

**포함**
- 화면 전체를 쓰는 고정 배치(넓은 화면)와 세로 쌓기 배치(좁은 화면).
- 2장의 문제 7가지 해결.
- 패널 모양 통일(배경색, 테두리, 모서리, 제목 줄 높이와 글자 크기).
- 로딩 중, 오류, 빈 데이터 화면도 같은 틀 안에서 보이게 하기. 데이터가 도착했을 때 화면이 밀리지 않게 한다.

**범위 밖**
- 검수 버튼, 단축키, 평가 표시 (F4, F5).
- 패널 크기를 마우스로 조절하는 기능, 패널 확대 버튼 (결정 5).
- 데이터를 서버에서 불러오는 구조로 바꾸기 (결정 6).
- 카메라 6대 (F6). 타임라인이 프레임 수백 개를 감당하게 하는 작업 (F7).
- COCO 모드를 남길지 정리할지. F3이 끝난 뒤 새 화면에서 COCO 탭을 보고 정한다.
- 새 라이브러리 설치. F3은 Tailwind와 CSS Grid만으로 한다.

## 5. 작업 단계

단계마다 실제 화면을 캡처해 확인하고, 단계별로 커밋한다.

| 단계 | 내용 | 코드 성격 |
|---|---|---|
| **F3-A** | 화면 틀 만들기. 기존 컴포넌트를 새 자리에 옮기고, 두 뷰어가 "부모 칸을 꽉 채우도록" 바꾼다. 로딩·오류 화면도 틀 안으로 옮긴다 | 배치만 변경. 동작 변화 없음 |
| **F3-B** | 목록과 개수의 기준 통일 (문제 4, 결정 4) | `lib/selectors` 변경 → 테스트 수정 필요 |
| **F3-C** | 작은 문제 수정: ID 줄이기(5), 차트 글자(6), 안내 문구(7) | 컴포넌트별 작은 수정 |
| **F3-D** | 패널 모양 통일과 마감 | 스타일만 변경 |

A를 먼저 하는 이유: B~D의 결과는 새 배치에서 봐야 판단할 수 있다. 예를 들어 차트 글자 크기 문제는
패널이 400px로 좁아지면 절반쯤 저절로 줄어든다.

(`Scene`, `BBox3D`, `PointCloud`).

### 뷰어 크기를 누가 정하나 (설계의 핵심)

지금은 **뷰어가 자기 크기를 스스로 정한다**(`aspect-[4/3]`). 바꾼 뒤에는 **화면 틀이 칸의 크기를 정하고,
뷰어는 받은 칸을 채우기만 한다.**

- 넓은 화면: 틀의 그리드가 칸 크기를 정한다.
- 좁은 화면: 틀이 뷰어 칸에 `aspect-[4/3]`를 준다. 지금과 같은 모습이 된다.

이렇게 하면 뷰어 컴포넌트는 배치를 몰라도 되고, 나중에 F6에서 카메라 칸을 6개로 늘릴 때도 뷰어를 고칠
필요가 없다.

`architecture.md`의 "2D Viewer SVG Contract"는 "고정 비율 틀이 타임라인 위치를 안정시킨다"고 적고 있다.
새 배치에서는 타임라인이 화면 아래에 고정되므로 같은 목적이 다른 방법으로 달성된다. 구현 후 이 문단을
고쳐 써야 한다.

## 7. 결정이 필요한 항목

2026-11-25에 사용자가 **모든 항목을 추천안대로 진행**하기로 했다. 결정 1~8은 실제 화면을 본 뒤 조정할 수 있다.

### 결정 1. 카메라 이미지를 어디에 둘까
- **추천: 오른쪽 위.** 3D 뷰가 가운데를 가장 크게 차지한다. F6에서 카메라가 6대가 되면 이 칸은
  "선택한 박스를 보고 있는 카메라 1대 + 작은 썸네일 6개"로 자연스럽게 확장된다.
- 대안: 가운데를 위아래로 나눠 3D 위, 카메라 아래. 카메라는 커지지만 3D 뷰의 높이가 약 440px로 줄고,
  16:9 사진 한 장 옆에 빈 공간이 남는다.
- 대가: 카메라 이미지가 지금보다 작아진다(폭 510 → 400).

### 결정 2. 필터를 어디에 둘까
- **추천: 상단 바 아래 한 줄.** 지금의 `Filters`가 이미 가로 한 줄 모양이라 그대로 옮기면 된다.
- 대안: 왼쪽 목록 위. 목록과 필터가 가까워지지만, 클래스 칩이 7개(nuScenes)라 272px 폭에서 3~4줄을
  차지해 목록이 짧아진다.

### 결정 3. 좁은 화면은 어떻게 할까
- **추천: 가로 1024px 미만은 지금처럼 세로로 쌓는다.**
- 대안: 모바일 전용 탭 화면(목록 / 3D / 카메라를 탭으로 전환). 작업량이 크고, 이 도구의 목표 사용 환경이
  아니다.

### 결정 4. 목록과 개수의 기준을 무엇으로 맞출까
- **추천: 3D 박스 전체(40개)를 기준으로 통일한다.** 목록에 40개를 모두 보여주고, 카메라에 안 보이는 박스는
  행에 표시를 붙인다(예: 흐린 카메라 아이콘). 클래스별 개수와 타임라인 배지도 같은 기준으로 맞춘다.
  - 이유 1: 이 도구는 3D가 메인이다(규칙 #5). 3D 뷰에는 40개가 그려져 있는데 목록에는 13개만 있으면,
    나머지 27개는 3D 뷰에서 직접 클릭하는 방법밖에 없다.
  - 이유 2: F4(3D 박스 검수)는 모든 3D 박스를 하나씩 넘기며 검수해야 한다. 목록이 13개만 보여주면 성립하지 않는다.
  - COCO는 2D와 3D가 항상 1:1이라 영향이 없다.
  - 선택한 박스가 카메라에 안 보일 때 정보 패널의 2D 줄은 지금처럼 "—"로 표시한다.
- 대안: 기준은 그대로 두고 문구만 고친다("13 in camera · 40 total"). 작업은 가장 작지만 F4에서 결국 바꿔야 한다.
- 비용: `selectClassCounts`와 그 테스트를 수정해야 한다. confidence 집계(`selectConfidenceBuckets`)는
  nuScenes에서 쓰이지 않으므로 그대로 두고 F5에서 다시 본다.

### 결정 5. 패널 크기 조절이나 확대 기능을 넣을까
- **추천: F3에서는 넣지 않는다(크기 고정).** 실제로 필요한지는 F4에서 카메라 이미지로 검수를 해봐야 알 수 있다.
  필요하다고 확인되면 F4에서 "카메라와 3D 자리 바꾸기" 같은 단순한 방식부터 검토한다.
- 대안: 지금 경계선을 끌어 크기를 바꾸는 기능을 넣는다. 새 라이브러리(`react-resizable-panels` 등)가 필요하고,
  3D 캔버스 크기가 바뀔 때의 동작을 추가로 검증해야 한다.

### 결정 6. 데이터 불러오기를 서버 쪽으로 옮기는 작업을 같이 할까
- **추천: F3에서는 하지 않는다.** 이유는 세 가지다.
  - F3을 배치 변경만으로 유지해야, 화면이 달라졌을 때 원인을 배치에서만 찾으면 된다.
  - 얻는 것이 불확실하다. 데이터셋 전환은 어차피 브라우저에서 일어나고, 2.9MB 데이터를 서버가 페이지에
    실어 보내면 첫 응답이 오히려 무거워질 수 있다.
  - 로드맵 원칙이 "먼저 재고, 느리면 바꾼다"이다. 지금은 잰 숫자가 없다.
- F3이 끝난 뒤 로딩 시간을 재서 별도 항목으로 판단한다.

### 결정 7. 객체 ID를 어떻게 보여줄까
- **추천: 앞 6자리만 고정폭 글꼴로 보여주고**(예: `c8fcea`), 전체 ID는 마우스를 올리면 뜨게 한다.
  nuScenes의 ID는 프레임이 바뀌어도 같은 객체면 유지되므로(추적), 줄인 ID로도 "아까 그 객체"를 알아볼 수 있다.
- 대안: 프레임 안 순번(`#07`). 읽기는 더 쉽지만 프레임마다 번호가 바뀌어 추적의 장점이 사라진다.
- COCO의 ID(`1-3` 형식)는 이미 짧으므로 그대로 둔다.

### 결정 8. UI 언어
- **추천: 영어로 통일한다.** 지금 UI가 거의 영어이고, 3D 조작 안내 한 곳만 한국어다.
- 대안: 한국어로 통일. 모든 문구를 바꿔야 한다.

### 결정 9. 구현 전에 화면 시안을 먼저 볼까
- **추천: 본다.** "깔끔한 디자인"은 글로 합의하기 어렵다. F3-A 전에 실제 색과 크기를 적용한 정적인 시안
  한 장을 만들어 확인하면, 구현한 뒤에 배치를 다시 바꾸는 일을 줄일 수 있다.
- 대안: 바로 F3-A를 구현하고 실제 화면 캡처로 확인한다.

## 8. 완료 기준

**스크롤**
- [ ] 1440×900과 1280×720에서 페이지 세로 스크롤이 없다. nuScenes와 COCO 모두, 객체를 선택한 상태와
      자동 재생 중에도 그렇다. (판정: `document.documentElement.scrollHeight === clientHeight`)
- [ ] 목록에서 객체를 선택해도 페이지가 움직이지 않는다. 목록 안에서만 스크롤된다(Edge_#9.5 Case C 유지).
- [ ] 390×844(모바일)에서는 세로로 쌓이고 페이지 스크롤로 모든 영역에 닿을 수 있다.

**배치**
- [ ] 넓은 화면에서 7개 영역이 동시에 보인다.
- [ ] 3D 뷰가 가장 큰 영역이다(규칙 #5).
- [ ] 로딩 중 화면과 데이터가 뜬 화면의 영역 위치가 같다. 데이터가 도착해도 화면이 밀리지 않는다.

**동작 유지 (바뀌면 안 되는 것)**
- [ ] 2D ↔ 3D ↔ 목록 선택 동기화.
- [ ] 2D 뷰의 빈 띠나 3D 뷰의 빈 공간을 클릭하면 선택이 해제된다(Edge_#9.5 Case A, B).
- [ ] nuScenes에서 프레임을 바꾸거나 자동 재생해도 3D 카메라가 튀지 않는다(Edge_F#2 Case 6).
- [ ] COCO에서 프레임을 바꾸면 3D 카메라가 초기 위치로 돌아간다(Edge_#4 Case 6).
- [ ] 창 크기를 바꾸면 3D 뷰가 찌그러지지 않고 따라온다.

**문제 해결**
- [ ] 헤더, 목록, 클래스 집계, 타임라인 배지의 개수가 같은 기준이다(결정 4).
- [ ] 목록의 ID가 한눈에 읽힌다(결정 7).
- [ ] 차트 축 글자가 주변 글자(10~12px)와 같은 크기다.
- [ ] UI 문구의 언어가 하나다(결정 8).
- [ ] 모든 패널의 배경색, 테두리, 모서리, 제목 줄이 같은 규칙을 따른다.

**코드**
- [ ] 기존 테스트 206개가 통과한다. 결정 4로 바뀐 테스트는 새 기준에 맞게 수정한다.
- [ ] `tsc --noEmit` 오류 0개.

## 9. 검증 방법

- **화면 캡처 (Playwright):** 화면 크기 3가지(1440×900, 1280×720, 390×844) × 데이터셋 2가지를 단계마다
  찍어 전후를 비교한다. 스크롤 유무는 위 판정식으로 자동 확인한다.
- **단위 테스트 (Vitest):** 결정 4로 바뀌는 `lib/selectors`만 해당한다. 배치와 스타일은 테스트하지 않는다
  (Testing Policy: UI 렌더링은 테스트하지 않음).
- **수동 확인:** 선택 해제, 카메라 유지, 자동 재생은 실제로 조작해서 본다.

## 10. 불변 규칙과의 관계

| 규칙 | 영향 |
|---|---|
| #1 2D와 3D의 ID 동일 | 영향 없음. ID 값은 그대로이고 **보여주는 글자만** 줄인다 |
| #2 `selectedObjectId` 하나만 사용 | 영향 없음. store를 건드리지 않는다 |
| #3 변환 로직은 컴포넌트와 store 밖 | 지킴. ID 줄이기 같은 작은 변환도 `lib/ui/`의 순수 함수로 둔다 |
| #4 범위 확장은 승인 필요 | 이 문서가 그 승인 요청이다 |
| #5 3D가 메인 | 더 강해진다. 3D 뷰가 가장 큰 영역이 되고 목록도 3D 기준이 된다 |
| #6 3D 추정값 표시 | 영향 없음. MEASURED / ESTIMATED 배지는 상단 바에 그대로 둔다 |
| #7 COCO는 2D 전용 | 영향 없음 |

## 11. 위험 요소

| 위험 | 대응 |
|---|---|
| 3D 카메라의 초기 위치가 4:3 화면에 맞춰 조정돼 있어, 칸 비율이 바뀌면 장면이 잘리거나 작게 보일 수 있다 | F3-A에서 두 데이터셋을 캡처해 확인하고, 필요하면 `Viewer3D`의 카메라 초기값만 조정한다 |
| 칸 크기가 바뀔 때 3D 캔버스가 다시 만들어지면 GPU 자원 정리 문제(Edge_#4 Case 4)가 재발할 수 있다 | 크기 변경은 캔버스를 다시 만들지 않고 처리된다(R3F 기본 동작). `key`를 추가하지 않는다. 창 크기를 여러 번 바꿔 확인한다 |
| COCO의 세로 사진은 400×225 칸에서 매우 작게 보인다(폭 약 169px) | 카메라 칸의 비율을 데이터셋에 따라 다르게 준다(nuScenes 16:9, COCO 4:3). 그래도 작으면 COCO 탭 판단 때 함께 본다 |
| nuScenes 클래스 칩 7개가 1280px 폭의 필터 바 한 줄에 안 들어갈 수 있다 | 줄바꿈 대신 가로 스크롤을 허용하거나 긴 이름(`static_object.bicycle_rack`)을 줄여 표시한다. 캡처로 확인 후 결정 |
| 카메라 이미지가 작아져 F4 검수에 부족할 수 있다 | 결정 5. F4 설계 때 실제 화면으로 판단한다 |
