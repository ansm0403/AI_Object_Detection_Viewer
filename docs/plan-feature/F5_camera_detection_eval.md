## 1. 목표

> nuScenes 카메라 사진에 2D 탐지 모델(YOLO)을 돌린 결과를 **정답 박스와 비교해 채점**하고,
> 모델이 **놓친 물체가 3D 공간의 어디에 있었는지**, **거리가 멀어질수록 얼마나 못 찾는지**를 보여준다.

로드맵의 두 기둥 중 "모델 품질(모델이 맞히나)"에 해당한다. F4가 "정답지에 오타가 없는지 보는 일"이었다면
F5는 "학생 답안을 채점하는 일"이다.

**용어 (이 문서와 화면에서 쓰는 뜻)**

시험 채점에 비유한다. **사진 = 문제, YOLO가 그린 박스 = 학생 답안, nuScenes 정답 박스 = 정답지.**

| 용어 | 쉬운 말 | 뜻 |
|---|---|---|
| 예측 (prediction) | 학생 답안 | 모델이 사진을 보고 "여기에 사람이 있다"고 그린 2D 박스. 점수가 붙는다 |
| 정답 / 라벨 (ground truth, label) | 정답지 | 사람이 만든 nuScenes 3D 박스. 사진 위에서는 그 박스를 비춘 2D 사각형으로 쓴다 |
| 점수 (confidence, score) | 답에 대한 자신감 | 모델이 예측마다 붙이는 0~1 사이 숫자. 0.9는 "거의 확실", 0.1은 "혹시 몰라서 적어 봄" |
| IoU | 두 박스가 겹친 정도 | 겹친 넓이 ÷ 둘이 덮은 전체 넓이. 색종이 두 장을 겹쳐 놓았을 때 "겹친 부분 / 둘이 덮은 전체". 0 = 안 겹침, 1 = 완전히 같음 |
| 찾음 (TP, true positive) | 맞은 답 | 정답지에 있는 물체를 모델도 찾았다 |
| 놓침 (FN, false negative) | 안 쓴 답 | 정답지에 있는데 모델이 못 찾았다 |
| 헛짚음 (FP, false positive) | 정답지에 없는 답 | 모델이 있다고 했는데 그 자리에 그 정답이 없다 |
| Precision (정밀도) | 쓴 답 중에 맞은 비율 | 찾음 ÷ (찾음 + 헛짚음). "모델이 있다고 한 것을 얼마나 믿을 수 있나" |
| Recall (재현율, 탐지율) | 정답 중에 맞힌 비율 | 찾음 ÷ (찾음 + 놓침). "실제로 있는 것 중 얼마나 찾았나" |
| 채점 제외 (not scored) | 채점하지 않는 문제 | 거의 가려진 물체처럼 찾지 못해도 모델 탓이라 하기 어려운 정답. 맞혀도 틀려도 점수에 넣지 않는다 |

**F4 연습 모드와 같은 구조다.** 연습 모드는 "심어 둔 오류를 **검수자가** 찾았나"를 찾음 / 놓침 / 헛짚음으로
채점했다(`lib/review/practice.ts`의 `scorePractice`). F5는 "실제 물체를 **모델이** 찾았나"를 같은 세 칸으로 채점한다.
채점 대상이 사람에서 모델로 바뀌었을 뿐이다.

**Precision과 Recall은 서로 당긴다.** 자신 있는 답만 적으면(점수 기준을 올리면) 헛짚음은 줄지만 놓침이 늘고,
아무거나 다 적으면 놓침은 줄지만 헛짚음이 는다. 그래서 점수 슬라이더를 움직이며 둘이 어떻게 바뀌는지 보는 것이
평가 도구의 기본 동작이다(2.2절 표에 실제 숫자).

### 2.2 YOLO를 실제로 돌려 본 결과

**실행 환경 (설치할 것 없음).** Python 3.13.3, `ultralytics` 8.4.51, `torch` 2.12.0(CPU 전용), `opencv-python` 4.13이
이미 있다. 모델 파일 `yolov8n.pt`(6.5MB)는 저장소 루트에 있고 git이 추적한다. CPU로 사진 한 장에 약 0.14초
(입력 1280), 0.05초(입력 640)가 걸렸다.

**채점 조건.** 아래 숫자는 7장의 추천안대로 채점한 것이다: 입력 크기 1280, 점수 0.25 이상, 같은 클래스끼리,
IoU 0.3 이상, 가시성 0~40%인 정답은 채점 제외.

| 항목 | 값 |
|---|---|
| 앞 카메라에 보이는 정답 박스 (10개 프레임) | 200개 = 보행자 120, 오토바이 58, 차 22 |
| 그중 채점 제외(가시성 0~40%) | 26개 (오토바이 18, 보행자 8) |
| 채점한 정답 | 174개 |
| **찾음 / 놓침 / 헛짚음** | **91 / 83 / 13** |
| **Precision / Recall** | **88% / 52%** |
| 클래스별 Recall | 차 18/22 (82%) · 보행자 73/112 (65%) · **오토바이 0/40 (0%)** |
| 거리별 Recall | 10~20m 36/64 (56%) · 20~30m 45/87 (52%) · 30~40m 10/23 (43%) |
| 프레임별 놓침 | 10, 8, 8, 8, 10, 10, 9, 6, 6, 8 |

- 앞 카메라에 보이는 정답은 모두 10~40m 사이에 있다. 10m 안쪽과 40m 바깥은 표본이 없다.
- **이 장면의 실제 특징은 "주차된 오토바이"다.** 버스 정류장 뒤에 오토바이가 줄지어 서 있는데, 모델은 채점 대상
  40개 중 하나도 찾지 못했다. 점수 기준을 0.05까지 내려도 오토바이라고 답한 예측은 10장 전체에서 15개뿐이다.
  ([캡처](assets/F5/2026-11-25_probe/yolo_vs_label_frame06.jpg): 빨강 = 놓친 정답, 초록 = 찾은 정답, 하늘색 = 모델 박스)
- **헛짚음 13건을 사진으로 확인했다.** 오토바이를 사람이나 차로 답한 것 3건(클래스를 틀림), 길가의 안전봉을
  사람으로 답한 것 4건, 정류장에 모인 사람들 사이에서 박스가 겹친 것 3건, 사진으로는 실제 차로 보이는 것 3건

## 3. 바뀐 뒤의 모습

### 3.1 화면을 나누는 방법: 평가 모드

상단 바에 **`Review | Evaluate`** 전환을 둔다. 화면 틀(영역 7곳)은 그대로이고 **칸마다 역할만 바뀐다**(결정 1).

| 자리 | 검수 모드 (지금 그대로) | 평가 모드 |
|---|---|---|
| 상단 바 왼쪽 | 데이터셋, 배지, `Practice` | 같고, `Review \| Evaluate` 전환이 생긴다. 평가 모드에서는 `Practice`를 숨긴다 |
| 상단 바 오른쪽 | 검수 진행률, `Export` | 모델 이름, 전체 Precision / Recall |
| 필터 바 | 거리 슬라이더, 클래스 칩 | **최소 점수(Min score) 슬라이더**, 클래스 칩 |
| 왼쪽 목록 | 3D 박스 전체 + 검수 상태 | **이 프레임의 채점 결과** (놓침 → 헛짚음 → 찾음 → 채점 제외 순) |
| 3D 뷰 | 클래스 색 | **결과 색**: 찾음 초록, 놓침 빨강, 평가하지 않은 박스 회색 |
| 카메라 칸 | 정답 사각형, 확대 시 투영한 3D 박스 | **정답(점선) + 모델(실선)** 을 결과 색으로 겹쳐 그린다. 확대는 둘을 함께 감싼다 |
| 정보 패널 | 근거 한 줄, 판정 버튼, Selected … | 제목 "Evaluation". 선택한 결과 한 줄(스크롤 밖 고정) + 전체 점수 + 거리별·클래스별 Recall |
| 타임라인 배지 | "검수한 수/전체" | "N missed" (그 프레임에서 놓친 개수) |

### 3.2 평가자가 하는 일

```
Evaluate로 전환
   → 패널에서 전체 점수와 "거리별 탐지율"을 본다
   → 타임라인에서 놓침이 많은 프레임으로 간다
   → 목록 맨 위의 "놓침"을 누른다 (또는 J / K)
        → 3D 뷰: 그 물체가 흰색으로 강조된다. 빨간 박스가 어디에 몰려 있는지 보인다
        → 카메라 칸: 그 물체의 정답 박스(빨간 점선)를 확대해 보여준다. 모델 박스가 없거나 어긋나 있다
        → 패널: "가장 가까운 모델 박스는 person 0.15, IoU 0.46 — 점수가 기준보다 낮음" 같은 한 줄
   → Min score 슬라이더를 움직인다 → 모든 숫자, 목록, 색이 바로 바뀐다
   → 의심스러운 정답을 발견하면 Review로 전환한다 (선택이 유지되어 바로 판정할 수 있다)
```

### 3.3 시안에서 확인한 것

- 1536×700과 1024×768에서 **페이지 스크롤이 생기지 않는다**(시안 화면에서 판정식으로 확인).
- 1024px에서 전환 버튼을 넣어도 상단 바가 한 줄이다(왼쪽과 오른쪽 묶음 사이 189px). 평가 모드에서 `Practice`를
  숨기고 오른쪽 내용을 줄였기 때문이다. **검수 모드 + 연습 배지 상태는 시안으로 확인하지 못했다(위험 1).**
- 1536×700에서 정보 패널은 "선택한 결과 한 줄 + 점수 두 줄 + 프레임 개수 + 거리별 Recall 3줄"까지 보이고,
  클래스별 Recall과 안내 문구는 패널 안에서 스크롤해야 보인다(넘치는 높이 약 120px).
- 시안의 3D 박스 색은 실제 three.js 장면의 색을 바꿔 찍은 것이다. 평가 대상(앞쪽 15~35m)이 기본 시점에서는
  작게 보인다. 가까이 보려면 지금처럼 마우스 휠이나 `Follow`를 쓴다.
- 1024px에서는 목록 폭이 240px이라 시안의 클래스 이름이 잘린다. 구현에서 칸 폭을 조정한다.

## 4. 범위

**포함**
- YOLO 실행 스크립트와 그 결과 파일(예측).
- 채점 로직(IoU, 짝짓기, 지표)을 `lib/`의 순수 함수로 만들고 Vitest로 테스트.
- 평가 모드 화면(3.1절 표).
- 데이터 요청 실패 시 오류 문구 수정(사용자가 이번 세션에 넣기로 정함. 별도 `fix:` 커밋).

**범위 밖**
- 카메라 6대(F6), 장면 탐색(F7), 박스 수정(F8), 3D 탐지 모델 평가, 백엔드·DB·로그인.
- **자전거 거치대 규칙.** 지금 데이터로는 검증할 수 없다(2.3절 1번). F6에서 다룬다.
- **예측에 대한 사람의 판정과 저장, 평가 결과 내보내기.** "이 헛짚음은 사실 라벨 누락이다" 같은 기록은 쓸모가
  있지만 새 저장 범위와 화면이 필요하다. 이번에는 보기만 한다.
- **mAP, PR 곡선, IoU 기준 조절 슬라이더.** 표본이 10장이라 곡선을 그릴 만큼의 의미가 없다.
- **더 큰 모델이나 여러 모델 비교.** 모델 파일을 새로 받아야 한다. 구조는 모델 이름을 파일에 기록해 두는 데까지만.
- **three.js 상시 비용.** 사용자가 별도 세션으로 정함.
- **COCO 모드.** 보류 그대로. COCO에는 평가 UI를 그리지 않는다(검수 UI와 같은 처리).
- **연습 모드에서의 평가.** 연습 모드는 정답을 일부러 바꾼 상태라 채점 기준이 될 수 없다.

## 5. 작업 단계

단계가 끝날 때마다 실제 앱을 조작해 확인하고(캡처 + 통과/실패 스크립트), 사용자 확인 뒤 다음으로 간다.

| 단계 | 내용 | 화면 변화 |
|---|---|---|
| **F5-0** | 오류 문구 수정: 불러오기에서 `response.ok` 확인. 별도 `fix:` 커밋 | 요청 실패 시 문구만 |
| **F5-A** | **데이터와 로직.** `scripts/predict_nuscenes.py`, `predictions.json` 생성, `lib/evaluation/`(타입, 파서, IoU, 클래스 대응, 짝짓기, 지표)과 테스트 | 없음 |
| **F5-B** | **모드 전환과 요약.** 상단 바 전환, 예측 파일 불러오기, 평가 패널(점수, 거리별·클래스별 Recall), Min score 슬라이더, 타임라인 배지 | 평가 모드의 숫자가 보인다 |
| **F5-C** | **사진과 목록.** 카메라 칸의 정답·모델 겹쳐 그리기와 확대, 결과 목록, 예측 선택, 선택한 결과 한 줄, `J` / `K` | 결과를 하나씩 볼 수 있다 |
| **F5-D** | **3D와 마무리.** 3D 박스 결과 색과 범례, 1024px 확인, 예측 파일이 없거나 깨졌을 때의 화면, 연습 모드와의 관계 | 3D에서 놓친 위치가 보인다 |
| 검증 | 엣지 케이스 검증(HANDOFF 6장), 문서 갱신 | |

F5-D(3D 색)는 떼어 낼 수 있다. 시간이 부족하면 A~C만으로도 "채점하고, 놓친 물체를 선택하면 3D에서 강조된다"까지는 된다.

## 7. 결정이 필요한 항목

결정 1이 가장 크다. 2~4는 화면, 5~8은 채점 규칙, 9~13은 구조다. 채점 규칙은 2장의 실측을 근거로 추천했다.

### 화면

**결정 1. "검수 / 평가"를 어떻게 나눌까** — 시안 A1 ↔ B1

| | 방식 | 좋은 점 | 대가 |
|---|---|---|---|
| **추천 A** | **상단 바의 `Review \| Evaluate` 전환.** 틀은 같고 칸의 역할이 바뀐다 | 헛짚음을 목록에 넣을 수 있다. 3D 뷰에 놓친 위치가 색으로 보인다. 검수 버튼과 평가 화면이 섞이지 않는다. 선택이 유지돼 두 모드를 오가며 볼 수 있다 | 고칠 곳이 많다(칸 5곳). 상단 바 폭을 1024px에서 다시 맞춰야 한다. 평가 모드에서는 3D의 클래스 색이 사라진다 |
| 대안 B | 정보 패널 안에만 탭을 둔다. 나머지는 검수 화면 그대로 | 만들 것이 적다. 화면이 덜 바뀐다 | 헛짚음은 3D 박스가 없어 **목록에 넣을 자리가 없다.** 3D는 클래스 색 그대로라 이 기능의 핵심("놓친 객체가 3D 어디에 있나")이 보이지 않는다. 검수 아이콘과 평가 결과가 한 화면에 섞인다 |
| 대안 C | 평가 전용 페이지를 따로 만든다 | 차트를 크게 그릴 수 있다 | 3D 뷰와 선택 동기화를 다시 만들거나 포기해야 한다. 이 프로젝트의 중심(규칙 #5)에서 벗어난다 |

**결정 2. 평가 모드의 3D 뷰** — 시안 A1

- **추천: 박스 색을 결과로 바꾼다**(찾음 초록, 놓침 빨강, 평가하지 않은 박스 회색). 왼쪽 위에 범례를 둔다.
- 이유: "놓친 물체가 3D 공간의 어디에 있었나"가 COCO로는 못 하는, 이 평가의 차별점이다(HANDOFF 3.5).
- 대안: F4처럼 3D는 그대로 두고 선택한 물체만 강조. 만들 것은 줄지만 차별점이 화면에 나타나지 않는다.
- 대가: F4에서 "3D 뷰는 그대로"로 지킨 `viewer-3d/` 내부를 처음 고친다(색 덮어쓰기 값 하나). 평가 모드에서는
  클래스 색이 3D에서 사라지고 목록의 색 점과 이름표에만 남는다. 박스의 3분의 2가 회색이 된다(앞 카메라 밖).

**결정 3. 카메라 칸에 무엇을 그릴까** — 시안 A2, A3

- **추천: 정답은 점선, 모델은 실선, 색은 결과.** 확대는 정답 박스와 모델 박스를 함께 감싸는 영역으로 한다.
  평가 모드에서는 F4의 "투영한 3D 박스 선"을 그리지 않는다(비교 대상이 2D 사각형끼리이기 때문).
  범례에 **"label · approx. (projected 3D box)"** 를 항상 표시한다(규칙 #6).
- 대안: 모델 박스만 그린다. 깔끔하지만 왜 "찾음"이고 왜 "놓침"인지 눈으로 확인할 수 없다.
- 대가: 사람이 몰린 곳에서는 선이 많이 겹친다(시안 A2). 확대와 "선택하지 않은 박스는 흐리게"로 줄인다.

**결정 4. 목록과 선택한 결과 설명** — 시안 A1, A4

- **추천: 목록은 이 프레임의 채점 결과**(놓침 → 헛짚음 → 찾음 → 채점 제외). 결과 종류별 개수 칩으로 걸러 볼 수 있다.
  앞 카메라 밖의 박스는 목록에 넣지 않고 "N개는 평가하지 않음" 한 줄로 알린다.
- **선택한 결과에는 "왜"를 알 수 있는 재료를 한 줄로 보여준다.** 놓침: 가장 많이 겹친 모델 박스의 클래스, 점수, IoU
  (예: "person 0.15, IoU 0.46 — 점수가 기준보다 낮음"). 헛짚음: 가장 많이 겹친 정답의 클래스와 IoU
  (예: "motorcycle 정답과 IoU 0.53"). 2.2절에서 헛짚음 13건을 손으로 분류해 보니 이 정보가 판단의 전부였다.
- 대안: 결과 종류만 보여준다. 만들 것은 줄지만 "왜 틀렸나"를 보려면 사진을 일일이 들여다봐야 한다.
- 대가: 짝짓기 함수가 결과마다 "가장 가까운 상대"를 한 번 더 계산한다(프레임당 정답 26개 × 예측 60개 이하라 가볍다).
  "점수가 낮음 / 클래스가 다름 / 이미 다른 물체와 짝" 같은 말은 **사실을 옮긴 것이지 원인 진단이 아니다.**

### 채점 규칙

**결정 5. 짝짓기 규칙**

- **추천: 점수가 높은 예측부터, 같은 클래스의 아직 짝이 없는 정답 중 IoU가 가장 큰 것과 짝짓는다. IoU 0.3 이상이어야 한다.**
  정답 하나는 예측 하나와만 짝이 된다. 이 순서와 방식은 업계 표준(COCO, PASCAL VOC)과 같고 기준값만 다르다.
- 이유: 정답 박스가 3D 상자를 비춘 근사치라 물체보다 헐렁하다. 표준값 0.5를 쓰면 제대로 찾은 28쌍이
  "헛짚음 + 놓침"으로 두 번 집계된다(2.3절 3번).
- 대안 1: 표준값 0.5. 다른 자료와 비교하기 쉽지만 여기서는 정답 박스의 헐렁함을 모델 탓으로 돌리게 된다.
- 대안 2: 박스 중심 사이의 거리로 짝짓기. 헐렁함에는 강하지만 설명하기 어렵고 검증할 것이 는다.
- 대가: 0.3은 표준보다 느슨하다. **화면과 문서에 기준값을 적고, 포트폴리오에도 "IoU 0.3 기준"이라고 쓴다.**

**결정 6. 가려진 물체**

- **추천: nuScenes 가시성이 0~40%인 정답은 "채점 제외".** 못 찾아도 놓침이 아니고, 모델이 찾았어도 찾음이나
  헛짚음으로 세지 않는다. 화면에는 회색으로 남기고 개수를 따로 보여준다.
- 이유: 이 단계의 Recall이 3/26이다. 거의 안 보이는 물체를 못 찾았다고 모델 점수를 깎으면 "모델이 어디서 약한가"가 흐려진다.
- 대안: 40~60%까지 제외. Recall은 더 좋아 보이지만 이 단계는 9/16으로 절반 넘게 찾는다. 빼면 숫자를 꾸미는 일이 된다.
- 대가: nuScenes의 가시성은 **카메라 6대 전체 기준**이다. 앞 카메라에서는 가려졌는데 옆 카메라에 잘 보여 높은
  단계로 적힌 물체가 있을 수 있다. 화면의 안내 문구에 이 기준을 적는다. 더 정확한 기준은 지금 데이터로 만들 수 없다.

**결정 7. 클래스 대응표**

- **추천:** 모델의 `person` / `bicycle` / `car` / `motorcycle` / `bus` / `truck`을 이 앱의 같은 이름 클래스와 맞춘다
  (nuScenes 쪽 이름 바꾸기는 `lib/nuscenes/parser.ts`의 `CATEGORY_MAP`에 이미 있다). 그 밖의 정답(자전거 거치대 등)과
  그 밖의 예측(신호등, 가방 등)은 평가에 넣지 않는다.
- **짝짓기는 같은 클래스끼리만.** 오토바이를 "사람"이라고 답하면 헛짚음 1개 + 놓침 1개가 된다.
- 대안: 클래스를 무시하고 위치만 본다. Recall이 52% → 54%로 조금 오르지만 "무엇인지 맞혔나"를 평가하지 않게 된다.
- 대가: 클래스를 틀린 경우가 두 번 집계된다. 결정 4의 설명 한 줄이 "실은 클래스를 틀린 것"임을 알려준다.
- 대응표는 `lib/evaluation/classes.ts`에 두고 테스트한다. 스크립트는 걸러내지 않고 모델 출력을 모두 적는다.

**결정 8. YOLO를 어떻게 돌릴까**

- **추천: 지금 있는 `yolov8n.pt`, 입력 크기 1280, 점수 0.05 이상을 모두 저장, 화면 슬라이더 기본값 0.25.**
- 이유: 입력 640이면 1600×900 사진의 먼 사람이 몇 픽셀로 줄어 Recall이 43%로 떨어진다(1280은 52%).
  낮은 점수까지 저장해야 슬라이더로 Precision과 Recall이 서로 당기는 모습을 볼 수 있다. 0.25는 YOLO의 기본값이다.
- 대안: 더 큰 모델(yolov8s, yolov8m). 점수는 오르겠지만 모델 파일을 새로 받아야 한다. 그리고 이 도구의 목적은
  좋은 점수가 아니라 **모델이 틀리는 곳을 보여주는 것**이라, 작은 모델이 보여줄 것이 더 많다.
- 대가: 숫자가 낮게 나온다(Recall 52%, 오토바이 0%). "가장 작은 YOLO를 추가 학습 없이 돌린 결과"임을 화면의
  모델 이름과 문서로 밝힌다. 모델이 나쁘다는 주장이 아니다.

### 구조

**결정 9. 예측 박스를 어디에 두고 ID를 어떻게 붙일까 (규칙 #1, #2)**

- **추천: 예측은 `Frame` 안에 넣지 않는다.** 별도 타입 `Prediction2D`(점수 필드 이름은 `score`)로 만들어 프레임 ID별로
  따로 들고 있고, 채점 함수가 프레임과 예측을 함께 받는다. ID는 **`pred:<프레임 ID>:<번호>`**.
- 이유: `detections2D`와 `detections3D`는 "같은 객체의 2D·3D 짝"이라는 약속(규칙 #1)으로 묶여 있다. 예측은 3D 짝이
  없고 짝지어진 정답과도 다른 객체다. 타입을 나누면 섞일 수가 없다. nuScenes 객체 ID는 16진수 32자라 `:`가 들어간
  ID와 겹칠 수 없다. 프레임 ID를 넣는 이유는, nuScenes에서는 프레임을 넘겨도 선택이 유지되므로 번호만 쓰면
  다음 프레임의 다른 예측이 선택된 것처럼 보이기 때문이다.
- **선택은 계속 `selectedObjectId` 하나다(규칙 #2).** 정답을 고르면 객체 ID, 헛짚음을 고르면 예측 ID가 들어간다.
  찾음 결과는 정답의 객체 ID로 선택한다(그래야 3D와 목록이 함께 강조된다). 예측 ID가 선택된 채 프레임이나 모드가
  바뀌면 선택을 해제한다.
- 대안: HANDOFF의 처음 생각대로 `Frame.predictions2D` 필드. 한곳에 모이지만 `Frame`과 nuScenes 파서가 바뀌고,
  연습 모드(파서를 다시 돌림)와 F6(프레임 구조 변경)가 예측까지 신경 써야 한다.
- 대가: 프레임과 예측을 묶는 일이 page에 하나 더 생긴다. 훅 하나로 모은다(위험 3).

**결정 10. 예측 파일과 불러오기**

- **추천: `predictions.json`을 따로 두고, nuScenes를 열 때 함께 받는다.** 예측 파일이 실패해도 **검수는 그대로 되고**
  평가 모드에서만 "예측을 불러오지 못했다"를 보여준다. 예측에는 있는데 지금 데이터에 없는 프레임은 무시하고,
  예측이 없는 프레임은 "예측 없음"으로 표시한다(0개로 채점하지 않는다).
- 이유: `nuscenes.json`과 파서, 기존 테스트가 영향을 받지 않는다(HANDOFF의 생각 그대로). 약 50KB라 미리 받아도 가볍다.
- 대안: `nuscenes.json`에 합친다. 요청은 하나지만 정답 파일이 모델 실행 결과에 따라 바뀌게 된다.
- 대가: 요청이 둘이 되어 실패 경우가 늘어난다. F5-0의 오류 문구 수정이 여기서 필요해진다.

**결정 11. 점수 표시와 슬라이더 (F2-E와의 충돌)**

- **추천: `frameHasConfidence`는 바꾸지 않는다.** 결정 9로 예측이 다른 타입이 되므로, 정답을 그리는 곳은 지금처럼
  점수를 숨기고 예측을 그리는 곳만 `score`를 보여준다. "한 프레임 안에 점수 있는 박스와 없는 박스가 섞이는" 문제는
  타입이 갈라 준다. HANDOFF는 "기준을 객체 단위로 바꿔야 한다"고 했는데, 그 목적이 이렇게 채워진다.
- **슬라이더는 store에 이미 있는 `confidenceThreshold`를 쓴다.** 평가 모드에 들어가면 0.25로, 나오면 0으로 둔다.
  채점은 selector 단계에서 한다: `(프레임, 예측, 점수 기준) → 결과`. 파일을 읽을 때 걸러내지 않는다(CLAUDE.md 규칙).
- **클래스 칩은 "보이기"만 바꾼다.** 칩을 꺼도 Precision / Recall 숫자는 전체 기준 그대로다(클래스별 숫자는 패널에 따로 있다).
  F4의 "대기열은 필터를 따르고 진행률 분모는 전체"와 같은 원칙이다. 평가 모드에서는 거리 슬라이더가 없으므로 거리 필터도 적용하지 않는다.
- 대안: 평가용 점수 기준을 store에 새 값으로 둔다. 분리는 깔끔하지만 같은 뜻의 값이 둘이 된다.
- 대가: 값 하나를 모드에 따라 0과 0.25로 바꾸는 코드가 page에 생긴다.

**결정 12. 지표와 표본 수**

- **추천:** 전체(10개 프레임) Precision과 Recall, 지금 프레임의 찾음 / 놓침 / 헛짚음 / 제외 개수, 거리 10m 구간별 Recall,
  클래스별 Recall. **모든 비율 옆에 "36/64"처럼 개수를 함께 적고** "small sample"을 표시한다.
  분모가 0이면 0%가 아니라 "—"를 보여준다.
- 거리별 지표는 Recall만 있다. 헛짚음은 짝지어진 정답이 없어 거리를 알 수 없기 때문이다.
- 대가: 이 숫자들은 10장, 카메라 1대, 장면 하나의 것이다. **포트폴리오에 "모델 성능"으로 쓰지 않는다.**
  "분석이 동작한다"까지가 F5의 주장이고, 숫자를 쓰는 것은 F6·F7 이후다(HANDOFF 4장 9번).

**결정 13. 연습 모드와 단축키**

- **추천: 연습 모드가 켜져 있으면 `Evaluate`를 누를 수 없게 하고 이유를 툴팁으로 알린다**("연습 모드는 라벨이 바뀐 상태").
  평가 모드에서는 `Practice` 버튼을 숨긴다.
- **단축키는 새로 만들지 않는다.** 평가 모드에서는 `J` / `K`(목록 이동)와 `Z`(확대)만 동작하고, 판정 키
  (`A` `R` `U` `C` `1`~`6` `N`)는 동작하지 않는다. 키 해석은 `lib/review/shortcuts.ts`의 `resolveShortcut`을 그대로 쓴다.
- 대안: 전환 시 연습 모드를 자동으로 끈다. 클릭은 줄지만 데이터가 말없이 다시 불러와진다.
- 대가: 연습 중인 사용자는 `Practice`를 끄고 `Evaluate`를 눌러야 한다(두 번 클릭).

## 8. 완료 기준과 검증 방법

모두 실제 앱을 조작하는 스크립트(통과/실패 출력)와 캡처로 확인한다. 로직은 Vitest로 확인한다.

**채점 로직 (Vitest)**
- IoU: 안 겹침 0, 같은 박스 1, 한쪽이 다른 쪽을 포함, 넓이 0인 박스에서 0(오류 없음).
- 짝짓기: 점수 높은 예측이 먼저 고른다. 정답 하나에 예측 하나. 다른 클래스와는 짝이 되지 않는다. IoU가 정확히 기준값이면 짝이 된다.
  채점 제외 정답은 놓침도 찾음도 아니고, 그 위의 예측은 헛짚음이 아니다. 점수 기준보다 낮은 예측은 없는 것으로 친다.
  정답이 없거나 예측이 없는 프레임에서 오류가 나지 않는다.
- 지표: 분모가 0이면 `null`. 거리 구간의 경계값이 어느 구간에 들어가는지 고정.
- 파서: 형식이 틀린 파일은 빈 결과, 값이 빠진 예측은 경고 후 건너뜀, 같은 입력에 같은 ID.
- **실제 데이터로 2.2절의 표가 다시 나온다:** 점수 0.25에서 찾음 91, 놓침 83, 헛짚음 13, 채점 제외 26.

**화면**
- 평가 모드에서 전체 Precision 88%, Recall 52%가 보이고, Min score를 0.40으로 올리면 100% / 41%로 바뀐다.
- 슬라이더를 움직이면 패널, 목록, 카메라 칸, 3D 색, 타임라인 배지가 함께 바뀐다.
- 목록에서 놓침을 누르면 3D에서 그 박스가 강조되고 카메라 칸이 그 정답을 확대한다. 3D나 사진에서 눌러도 목록의 같은 행이 선택된다.
- 헛짚음을 누르면 사진에서 그 박스가 강조되고, 3D에는 선택 표시가 없으며 패널이 이유를 알려준다.
- 정답 박스에는 점수가 표시되지 않고(F2-E 유지) 예측 박스에만 점수가 나온다. 카메라 칸에 "approx." 범례가 항상 있다.
- 평가 모드 ↔ 검수 모드를 오가도 선택한 정답 박스가 유지된다. 헛짚음을 선택한 채 검수 모드로 가면 선택이 해제된다.
- 예측 파일 요청이 실패하면 검수 모드는 정상이고 평가 모드에 안내가 보인다. 데이터 요청이 500이면 오류 문구에 상태 코드가 나온다(F5-0).
- 연습 모드에서는 `Evaluate`가 비활성이다. COCO에는 전환 버튼이 없다.
- 1536×700, 1440×900, 1280×720, 1024×768에서 페이지 스크롤이 없고 상단 바가 한 줄이다(검수 모드 + 연습 배지 포함).

**기존 동작이 깨지지 않았는지 (매 단계)**
- 선택 동기화(목록 ↔ 3D ↔ 카메라), 빈 곳 클릭으로 선택 해제, 프레임 전환과 재생 중 3D 카메라 유지(캔버스가 다시 만들어지지 않음).
- F4 검수 흐름: 판정과 자동 이동, 단축키 전부, 새로고침 뒤 유지, 카메라 확대와 투영한 3D 박스, 연습 모드와 채점, 내보내기.
- COCO 화면이 F4 이후와 같다.
- 기존 테스트 386개 통과, `tsc --noEmit` 오류 0개, 린트 오류 0개
  (`npx nx run @ai-detection-viewer/ai_detection_viewer_client:lint`), 배포용 빌드 성공.

**스크립트**
- `predict_nuscenes.py`를 두 번 돌려 결과 파일이 같은지 확인한다. **확인 필요**(아직 해 보지 않았다).

## 9. 불변 규칙과의 관계

| 규칙 | 관계 |
|---|---|
| #1 2D와 3D의 ID가 같다 | **지킨다.** 예측은 `detections2D`에 넣지 않고 다른 타입으로 둔다. ID는 `pred:` 접두어라 객체 ID와 겹칠 수 없다(결정 9). 정답의 2D·3D ID는 손대지 않는다 |
| #2 선택 상태는 `selectedObjectId` 하나 | **지킨다.** 정답이면 객체 ID, 헛짚음이면 예측 ID가 같은 자리에 들어간다. "선택한 예측" 같은 상태를 따로 만들지 않는다. 모드는 선택이 아니라 화면 설정이다 |
| #3 파싱과 좌표 계산은 컴포넌트와 store 밖 | **지킨다.** IoU, 짝짓기, 지표, 예측 파일 읽기, 그릴 사각형 계산이 모두 `lib/evaluation/`의 순수 함수이고 테스트한다 |
| #4 범위를 승인 없이 넓히지 않는다 | 이 문서의 승인을 받고 시작한다. 4장의 "범위 밖"을 지킨다 |
| #5 3D가 메인 | **강화한다.** 평가 결과가 3D 뷰의 색으로 나타나고, 놓친 물체를 3D에서 찾는 것이 중심 동작이다 |
| #6 추정값을 실측처럼 말하지 않는다 | **가장 조심할 규칙.** ① 정답 2D 박스는 3D 박스를 비춘 근사치임을 범례와 안내 문구에 적는다. ② 예측의 2D 박스에는 3D 위치가 없다고 화면에서 말한다(3D에 가짜 위치를 그리지 않는다). ③ 정답에는 점수를 보이지 않는다. ④ 숫자 옆에 표본 수와 기준(IoU 0.3, 점수 기준, 모델 이름)을 둔다. ⑤ 연습 모드에서는 평가하지 않는다 |
| #7 COCO JSON에서 3D를 읽지 않는다 | 관계 없음. COCO 경로를 건드리지 않는다 |

**CLAUDE.md의 다른 규칙**
- "점수 필터는 파싱 때가 아니라 selector에서": 지킨다(결정 11).
- "값이 빠진 탐지는 경고 후 건너뛴다": 예측 파서도 같은 방식.
- "Recharts는 쓰지 않는다": 막대는 지금처럼 직접 만든 CSS. 새 라이브러리 없음.
- 테스트는 `lib/`와 `store/`만. 화면은 캡처와 조작 스크립트로 확인.
