# 기능 설계 문서 (plan-feature)

Post-MVP 기능을 **구현하기 전에** 쓰는 설계 문서 모음이다. 기능 하나에 문서 하나를 쓴다.

**새 세션은 [HANDOFF.md](HANDOFF.md)부터 읽는다.** 큰 기능 하나를 세션 하나에서 진행하므로, 지금 어디까지
왔는지, 방향이 왜 그렇게 정해졌는지, 다음 기능의 설계 문서를 어떻게 써야 하는지가 거기에 있다.

## 이 폴더의 역할

| 문서 | 역할 | 언제 쓰나 |
|---|---|---|
| `.claude/docs/post-mvp-checklist.md` | 로드맵과 진행 기록 | 방향을 정할 때, 기능이 끝났을 때 |
| **`docs/plan-feature/F#_*.md` (이 폴더)** | **기능 하나의 설계: 무엇을, 왜, 어떻게, 어디까지** | **구현 시작 전, 승인받기 위해** |
| `.claude/docs/architecture.md` | 지금 코드의 실제 구조 | 기능이 구현된 뒤 갱신 |
| `docs/edgecases/Edge_F#N.md` | 구현 중 발견한 경계 사례 | 사례가 실제로 나왔을 때 |

설계 문서는 **승인 전의 제안**이다. 구현이 끝나면 실제 결과는 `architecture.md`와
`post-mvp-checklist.md`에 기록하고, 설계 문서는 "당시 무엇을 계획했는가"의 기록으로 남긴다.
구현하면서 계획과 달라진 점은 설계 문서를 고쳐 쓰지 않고 체크리스트의 완료 기록에 적는다.

## 문서 상태

| 상태 | 뜻 |
|---|---|
| 초안 (승인 대기) | 작성됨. 결정 항목에 대한 답을 기다리는 중. 구현 시작 불가 |
| 임시 승인 | 추천안으로 일단 만들고, 실제 화면을 보며 조정하기로 함. 구현 시작 가능 |
| 승인됨 | 결정 항목이 확정됨. 구현 시작 가능 |
| 구현 완료 | 구현이 끝남. 결과는 체크리스트 참고 |

**F4 이후 문서를 지금 쓰지 않는 이유:** 뒤 기능의 설계는 앞 기능의 결과에 달려 있다.
예를 들어 F4의 검수 버튼이 어디에 놓일지는 F3의 화면 배치가 확정돼야 정할 수 있다. 미리 쓰면
추측으로 채운 문서가 되고, 앞 기능이 바뀔 때마다 고쳐야 한다. 각 문서는 해당 기능을 시작하기
직전에 쓴다. F4~F8에서 미리 알려진 설계 질문은 로드맵의 "Questions each plan must settle"에 모아 두었다.

## 문서 형식

각 설계 문서는 아래 순서를 따른다.

1. 상태와 목표
2. 지금의 문제 (측정하거나 코드에서 확인한 사실)
3. 바뀐 뒤의 모습
4. 범위와 범위 밖
5. 작업 단계
6. 바뀌는 코드
7. 결정이 필요한 항목 (추천안과 대안)
8. 완료 기준과 검증 방법
9. 불변 규칙과의 관계
10. 위험 요소
11. 끝난 뒤 갱신할 문서
