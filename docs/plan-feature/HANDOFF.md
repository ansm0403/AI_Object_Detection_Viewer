# 인수인계 문서 (F3 ~ F8)

큰 기능(F) 하나를 세션 하나에서 진행한다. 세션이 바뀌면 이전 대화 내용은 사라지므로, 다음 세션이 이어서
일할 수 있도록 **무엇을 왜 그렇게 정했는지**를 여기에 남긴다.

- **읽는 사람:** 새 세션의 Claude, 그리고 사용자.
- **최초 작성:** 2026-11-25 (방향을 정하고 F3 설계 문서를 쓴 세션).
- **갱신 규칙:** 세션을 끝낼 때마다 1장(현재 상태)과 9장(세션 기록)을 고친다. 4장의 기능별 내용은
  그 기능을 실제로 진행하면서 달라진 점이 생기면 고친다.

---

## 0. 세션을 시작할 때

아래 순서로 읽는다. 다 읽기 전에는 코드를 고치지 않는다.

1. `CLAUDE.md` (자동으로 읽힘): 불변 규칙, 작업 규칙.
2. **이 문서의 1장**: 지금 어디까지 왔고 다음에 할 일이 무엇인지.
3. 이 문서의 2장, 3장: 사용자와 일하는 방식, 방향이 정해진 이유.
4. 이 문서의 4장에서 **이번 세션에서 할 기능** 부분.
5. `.claude/docs/post-mvp-checklist.md`의 "Roadmap — F3+ direction"과 직전 기능의 완료 기록.
6. 이번 기능의 설계 문서(`docs/plan-feature/F#_*.md`). 없으면 5장을 따라 먼저 쓴다.
7. `.claude/docs/architecture.md`: 구조를 바꾸는 작업이면 반드시.

그다음 사용자에게 "이번 세션에서 할 일"을 짧게 확인받고 시작한다.

## 2. 사용자와 일하는 방식

**사용자**
- 신입 프론트엔드 개발자. React, Next.js, TypeScript는 익숙하다.
- **3D(Three.js, R3F), AI 데이터(탐지, 박스, 포인트클라우드), Zustand는 처음 배우는 영역이다.**
- 이 프로젝트의 목적은 포트폴리오다. 목표 직무는 자율주행·로봇 데이터를 다루는 프론트엔드다.

**설명할 때**
- 사용자가 "설명이 어렵다"고 말한 적이 있다. 전문용어는 그 자리에서 풀어 쓰고, 비유를 먼저 든다.
- 새 용어를 도입하면 `.claude/docs/domain-glossary.md`에 바로 추가한다.
- 답변은 "지침에 의거하여 답변할게"로 시작한다(CLAUDE.md 필수조건).

**일할 때**
- 여러 파일을 고치거나 구조를 바꾸기 전에는 계획을 보여주고 승인을 받는다.
- **화면에 관한 판단은 추측하지 않는다.** 앱을 띄워 캡처한 뒤 말한다(8장에 방법).
- 사용자는 "직접 보기 전에는 판단할 수 없다"고 했다. 화면 관련 결정은 **일단 추천안으로 만들어 보여주고
  조정하는 방식**으로 진행한다. 글로 길게 묻지 않는다.
- 확인하지 않은 것을 사실처럼 말하지 않는다. 이 세션에서 빈 명령 파일을 확인하지 않고 "`/plan-feature`로
  하자"고 여러 번 말한 실수가 있었다.
- 커밋은 요청받았을 때만 한다. 형식은 `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`.

**문서 언어**
- `.claude/docs/`의 영어 문서: 영어 본문을 쓰고, 바로 아래에 한국어 번역을 HTML 주석 블록
  (`<!-- KO (move to a localized file) ... -->`)으로 넣는다.
- `docs/plan-feature/`: 한국어로 쓴다. 사용자가 직접 읽고 승인하는 문서이기 때문이다.
- `docs/PROJECT_DESIGN.md`와 `.claude/docs/mvp-checklist.md`는 **절대 고치지 않는다.**

**포트폴리오에 쓰는 말은 정확해야 한다**
- "실무 도구를 만들었다"가 아니라 "실무 도구의 핵심 흐름을 재현했다"고 쓴다.
- "3D 플랫폼을 만들었으니 2D 플랫폼 경험도 있다"고 쓰지 않는다. 해본 것과 응용할 수 있는 것을 구분한다.
- 측정하지 않은 숫자는 쓰지 않는다.

## 3. 방향이 정해진 과정

2026-11-25 세션에서 논의한 순서대로 적는다. **이미 정한 것을 다음 세션에서 다시 논쟁하지 않기 위한 기록이다.**

### 3.1 출발점: 지금 앱의 문제
- 화면을 캡처해 보니, 앱은 **읽기 전용 뷰어**였다. 둘러보고 거르고 클릭할 수는 있지만 사용자에게 남는
  결과물이 없다.
- 사용자가 먼저 떠올린 문제의식: "실무 데이터 도구는 스크롤 없이 쓴다." 이것이 F3의 출발점이다.

### 3.2 도구의 종류 세 가지를 비교했다

| 종류 | 사용자가 하는 일 | 판단 |
|---|---|---|
| 라벨 검수 | 정답 박스가 맞는지 승인/반려 | **채택 (F4).** 라벨링 회사 제품과 직접 연결되고 프론트엔드 실력이 가장 많이 드러난다 |
| 모델 오류 검수 | 모델이 어디서 틀렸는지 찾기 | **채택 (F5).** AI 평가 개념을 이해한다는 차별점 |
| 데이터 탐색 | 조건에 맞는 장면 찾기 | **뒤로 (F7).** 데이터가 10프레임뿐이면 설득력이 없다. 데이터를 늘린 뒤에 한다 |

### 3.3 2D 중심 계획을 세웠다가 3D 중심으로 바꿨다
- 처음에는 COCO(2D 사진) 중심으로 계획했다: 정답 vs 예측 비교, 2D 박스 수정.
- 사용자가 "원래 자율주행 데이터 직무를 보고 시작한 프로젝트"라고 알려줬다. `PROJECT_DESIGN.md` 1장에 당시
  공고의 요구 역량이 있다: AI 데이터 플랫폼, 멀티모달 데이터, 3D 시각화, 어노테이션, 데이터 탐색 UI.
- 이 기준으로 보면 2D 중심 계획은 **프로젝트의 가장 강한 부분(F2: 실측 3D, LiDAR, 좌표계)을 키우지 않고**
  일반 2D 라벨링 도구 쪽으로 기울어 있었다. 불변 규칙 #5(3D가 메인)와도 어긋난다.
- 그래서 **nuScenes(3D) 중심**으로 바꿨다. 사용자의 표현으로는 "선회가 아니라 확장"이다. 플랫폼 역량(화면,
  검수 흐름, 상태, 성능, 탐색)의 대부분은 2D든 3D든 같기 때문이다.

### 3.4 세 가지 방향 중 B를 골랐다

| 방향 | 내용 | 판단 |
|---|---|---|
| A | 2D AI 데이터 플랫폼 (COCO 라벨 검수·수정) | 3D 강점이 묻힌다 |
| **B** | **3D AI 데이터 플랫폼 (3D 라벨 검수 + 모델 평가 + 장면 탐색)** | **채택** |
| C | 3D 데이터 분석 앱 (주행 기록 재생·디버깅, Foxglove나 Rerun 같은 것) | GPS·IMU 같은 새 센서 데이터가 필요해 범위가 가장 크다 |

### 3.5 평가를 COCO가 아니라 nuScenes 카메라 이미지에서 하기로 했다
- 걱정: 3D 검수와 2D 모델 평가를 한 프로젝트에 넣으면 중구난방으로 보이지 않을까.
- 해결: 평가를 **nuScenes의 카메라 사진 위에서** 한다. 사진에 YOLO(2D 모델)를 돌리고, 3D 정답 박스를 사진에
  투영한 것과 비교한다.
- 이렇게 하면 COCO로는 불가능한 분석이 생긴다: **"모델이 놓친 객체는 3D 공간에서 어디에 있었나"**, 그리고
  **거리별 탐지율**. 정답 박스에 LiDAR로 잰 실제 거리가 있기 때문이다.
- 두 기능은 "데이터 품질"의 양면으로 묶인다. 라벨 품질(정답이 맞나)과 모델 품질(모델이 맞히나).
- 사용자가 이 장점 때문에 평가를 넣기로 확정했다.

### 3.6 하지 않기로 한 것과 이유

| 항목 | 이유 |
|---|---|
| 3D 탐지 모델 실행 | NVIDIA GPU와 까다로운 설치 환경이 필요하고 Windows 지원이 약하다. 입력 준비가 복잡하다(여러 스캔을 겹쳐야 하고, 지금 데이터는 화면용으로 점을 솎아낸 것이라 원본부터 다시 처리해야 한다). 회전된 3D 박스의 판정도 따로 공부해야 한다 |
| 백엔드, DB, 로그인, 다중 사용자 | CLAUDE.md에서 금지. 풀려면 사용자의 명시적 결정이 필요하다 |
| WebGPU 렌더러 전환, 실시간 스트리밍 | 지금 목표와 거리가 멀다 |
| 2D 전용 라벨 유형(폴리곤, 마스크, 키포인트) | 3D 중심 초점을 흐린다 |

### 3.7 기술 고도화는 "먼저 재고, 느리면 바꾼다"
- 서버 컴포넌트 전환, `useTransition`, 포인트클라우드 바이너리 전환, Web Worker는 **독립 기능으로 하지 않는다.**
  필요가 측정으로 확인될 때 끼워 넣고, 전후 숫자를 기록한다.
- 서버 컴포넌트 전환은 처음에 "초급 1순위"로 추천했다가 코드를 본 뒤 뒤로 미뤘다. 데이터셋 전환이 어차피
  브라우저에서 일어나고, 2.9MB 데이터를 서버가 페이지에 실어 보내면 오히려 무거워질 수 있기 때문이다.
- 사용자에게 강조한 원칙: 신입 포트폴리오에서는 "바꿨다"보다 **"왜 바꿨고 얼마나 좋아졌는지"**가 중요하다.

### 3.8 현업 도구와의 거리 (솔직한 평가)
- 이 계획으로 갈 수 있는 곳: **현업 도구와 비슷하게 동작하는 1인용 검수 도구.**
- 갈 수 없는 곳: 현업에서 그대로 쓰는 도구. 다중 사용자, 작업 배정, 권한, 서버 저장이 없다.
- 사용자에게 권한 것: 계획을 확정하기 전에 **CVAT나 Label Studio를 1시간 써보기.** 실제로 써봤는지는
  확인되지 않았다. F4 세션을 시작할 때 물어볼 것.

## 4. 기능별 인수인계

각 기능의 "설계 방향"은 이 세션에서 정리한 **현재 생각**이다. 확정이 아니며, 그 기능의 설계 문서를 쓸 때
코드를 다시 확인하고 사용자와 정한다. "확인 필요"라고 적힌 것은 이 세션에서 확인하지 못한 것이다.

### F3 — 스크롤 없는 작업 화면

**✅ 완료 (2026-11-25).** 자세한 결과는 `post-mvp-checklist.md`의 F3 항목. 여기에는 다음 기능에 필요한 것만 적는다.

- 설계 문서: [F3_workspace_layout.md](F3_workspace_layout.md). 계획 당시의 기록으로 두고 고치지 않았다.
- **진행 방식이 잘 맞았다:** 시안(정적 HTML, 실제 색·크기, 지금 화면 캡처와 나란히) → 사용자 승인 → 단계별
  구현 → 단계마다 캡처 페이지를 열어 보여주고 확인. 사용자는 시안을 보고 바로 방향을 정했다. F4의 화면 작업도
  같은 방식을 권한다.
- **화면 틀:** `components/workspace/WorkspaceShell.tsx`가 영역 7곳의 위치와 크기를 정하고, 뷰어는 받은 칸을
  채우기만 한다. 공통 패널 모양은 `components/workspace/Panel.tsx`(`PANEL_CLASS`, `PanelHeader`,
  `ViewerLabel` 등). 새 패널을 만들면 이것을 쓴다.
- **결정 4(목록을 3D 박스 전체 기준으로) 완료.** F4의 전제 조건이 갖춰졌다. 목록에는 40개 전부, 카메라에
  보이는지 아이콘, 자차 거리(m), 6자리 ID가 나온다.
- **카메라 이미지 크기(F4 판단 재료):** 1440×900에서 400×225, 1280×720에서 360×203(이전 510×287). 먼
  보행자의 2D 박스는 사진 위에서 약 13~14px다. 사용자의 노트북 브라우저 창은 약 1536×700이고, 이때 3D는
  832×508, 카메라는 400×225다. 검수에 부족하면 F4에서 "카메라와 3D 자리 바꾸기" 같은 단순한 방식부터 검토한다(결정 5).
- 3D 칸이 4:3보다 세로로 길면(1440×900) 장면 위쪽이 빈다. 사용자 화면에서는 생기지 않아 그대로 두었다(Edge_F#3 Case 3).

### F4 — 3D 박스 검수

**무엇:** nuScenes의 3D 정답 박스를 하나씩 보며 승인 또는 반려하고, 사유를 남기고, 나중에 이어서 하고,
결과를 내보낸다.

**왜 3D 박스인가:** 모델 없이 지금 있는 정답 박스만으로 시작할 수 있고, 목표 직무(자율주행 데이터)와 맞다.
3D 박스가 맞는지는 3D만 봐서는 판단하기 어려우므로 **카메라 사진 위의 투영과 대조**한다. 이미 만든 투영
기능(`lib/geometry/projection.ts`)을 그대로 쓴다.

**설계 문서에서 반드시 다룰 것**

1. **검수할 것이 거의 없을 수 있다 (가장 먼저 사용자와 정할 것).**
   nuScenes의 정답은 품질이 높다. 실제로 검수해 보면 거의 전부 "승인"일 것이다. 그러면 시연할 때 도구가
   하는 일이 없어 보인다. 선택지:
   - (가) 그대로 둔다. 도구의 가치는 "흐름"에 있다고 설명한다.
   - (나) 일부 박스를 일부러 어긋나게 만든 **연습용 데이터**를 스크립트로 만들고, 화면에 "연습용(변형된
     데이터)"이라고 분명히 표시한다. 정답을 알고 있으므로 "검수자가 오류를 몇 개 찾았는지"도 계산할 수 있다.
   - 어느 쪽이든 변형된 데이터를 원본인 것처럼 보여주면 안 된다(규칙 #6과 같은 태도).

2. **검수의 단위.** 지금 객체 ID는 `instanceToken`이다. 같은 차가 여러 프레임에 걸쳐 같은 ID를 갖는다.
   하지만 박스는 **프레임마다 따로 그려진 것**이다. 3번 프레임의 박스는 맞고 7번 프레임의 박스는 틀릴 수
   있다. 그러므로 검수 기록의 키는 **(프레임 ID, 객체 ID)** 쌍이어야 한다.
   - 확인된 사실: 준비 스크립트(`scripts/prep_nuscenes.py`)는 지금 박스마다 `instanceToken`, `category`,
     `translation`, `size`, `rotation`만 내보낸다. nuScenes 원본의 박스 고유 ID(`sample_annotation.token`)는
     내보내지 않는다.

3. **카메라에 안 보이는 박스.** 첫 프레임 기준으로 40개 중 13개만 앞 카메라에 보인다(Edge_F#2 Case 2).
   나머지 27개는 사진과 대조할 수 없다. 선택지:
   - 카메라에 보이는 박스만 검수 대상으로 한다.
   - 전부 검수하되 "이 카메라에서는 확인 불가"를 표시하고, LiDAR 점이 박스 안에 얼마나 들어 있는지를
     보조 근거로 보여준다. nuScenes 원본에 박스별 LiDAR 점 개수(`num_lidar_pts`)가 있다. 지금은 내보내지 않는다.
   - 이 문제는 F6(카메라 6대)에서 대부분 풀린다.

4. **상태를 어디에 둘까.** 검수 기록은 Zustand store에 둔다. 선택 상태는 계속 `selectedObjectId` 하나만
   쓴다(규칙 #2). "진행률 계산", "다음 미검수 박스 찾기", "내보내기 형식 만들기"는 `lib/`의 순수 함수로 두고
   Vitest로 테스트한다(규칙 #3).

5. **저장 방식.** 이 세션에서 사용자에게 "IndexedDB가 적합하다"고 말했는데, **다시 판단할 필요가 있다.**
   검수 기록은 많아야 수천 건의 작은 데이터라 localStorage로도 충분하고, Zustand의 `persist` 기능으로 더
   간단히 할 수 있다. IndexedDB는 F8에서 박스 수정 내용까지 저장하게 되면 그때 검토해도 된다. Next.js에서는
   저장된 값을 불러올 때 서버가 그린 화면과 브라우저 화면이 달라지는 문제(hydration 불일치)를 조심해야 한다.
   지금 store에는 저장 기능이 없다.

6. **내보내기 형식.** 2D 계획 때는 "COCO JSON으로 내보내기"라고 했다. 3D 검수에서는 맞지 않는다.
   검수 결과 목록(프레임, 객체, 판정, 사유)을 JSON으로 내보내는 것이 자연스럽다. CSV도 고려한다.

7. **반려 사유 목록(안).** 클래스가 틀림 / 박스가 큼·작음 / 위치가 어긋남 / 방향이 틀림 / 객체가 아님 / 기타.

8. **단축키(안).** `A` 승인, `R` 반려, `J`·`K` 다음·이전. 입력란에 글을 쓰는 중에는 동작하지 않게 한다.
   3D 뷰의 마우스 조작(OrbitControls)과 충돌하지 않는지 확인한다.

9. **검수 편의.** 판정하면 다음 미검수 박스로 자동 이동. 선택한 박스로 카메라가 따라가는 기능은 이미
   있다(F2-D의 Follow 모드).

**F3에서 받을 것:** 버튼과 진행률이 들어갈 자리(F3 설계 문서 12장). 실제 배치는 F3 결과를 캡처해 보고 정한다.
F3 결과(2026-11-25) 기준으로 자리는 이렇다:
- 승인/반려 버튼: 정보 패널(`AnalyticsPanel`, 오른쪽 아래, 1440×900에서 400×475) 맨 위. 이 패널은 이미
  "Selected / Confidence / Classes"로 차 있고 패널 안에서 스크롤되므로, 버튼은 스크롤 밖(제목 줄 바로 아래)에
  고정하는 것을 먼저 검토한다.
- 진행률: 상단 바(`Header`, 44px) 오른쪽. 지금 "Frame 1/10 · 40 detections"가 있는 자리.
- 행별 검수 상태: 목록 행 오른쪽. 행은 지금 `[색 점][클래스][카메라 아이콘][거리][ID 6자리]`이고 272px
  폭(1280에서는 240px)이라 여유가 적다. 아이콘 하나 크기로 설계해야 한다.
- 목록 행 높이는 32px, 1440×900에서 약 20줄이 한 번에 보인다. J/K로 넘길 때 선택 행이 보이도록 목록 안에서만
  스크롤하는 코드가 이미 있다(`ObjectList`의 `scrollTop` 조정, Edge_#9.5 Case C).
- 목록이 보여주는 박스 = 3D 필터를 통과한 박스(흐림 처리 기준). F4의 "다음 미검수 박스" 계산 범위를 필터와
  맞출지 정해야 한다.

**선택 사항으로 논의했던 것:** 로그인 없이 화면에서 "작업자 모드 / 검수자 모드"를 전환해 역할 분리를 흉내
내는 것. 사용자가 원할 때만.

### F5 — 카메라 탐지 평가

**무엇:** nuScenes 카메라 사진에 2D 탐지 모델(YOLO)을 돌린 결과를 정답과 비교해 맞힘(TP), 잘못 찾음(FP),
놓침(FN)을 보여준다. 놓친 객체를 클릭하면 3D 뷰에서 위치를 보여주고, 거리별 탐지율을 계산한다.

**쉬운 설명 (사용자에게 통했던 비유):** 시험 채점이다. 사진은 문제, YOLO의 예측은 학생 답안, nuScenes
정답 박스는 정답지다. F5는 답안을 채점하는 일이고, F4는 정답지에 오타가 없는지 확인하는 일이다.

**처리 흐름**
```
카메라 사진 ──▶ YOLO (scripts/에서 오프라인 실행) ──▶ 예측 2D 박스 (confidence 있음, 거리 없음)
3D 정답 박스 ──▶ 카메라에 투영 (이미 구현됨)      ──▶ 정답 2D 박스 (거리 있음)
                                  └──▶ lib/에서 IoU로 짝짓기 ──▶ TP / FP / FN
```

**확인된 사실**
- `scripts/generate_predictions.py`가 COCO 사진에 YOLOv8n을 돌리는 스크립트다. 같은 방식으로 nuScenes 사진에
  돌리면 된다. 모델 파일 `yolov8n.pt`는 저장소 루트에 있다.
- nuScenes 원본 데이터는 `C:\data\sets\nuscenes`에 있다(저장소 밖).
- nuScenes의 가시성 정보는 4단계다: 0~40%, 40~60%, 60~80%, 80~100%. 지금 준비 스크립트는 이 값을 내보내지 않는다.

**설계 문서에서 반드시 다룰 것**

1. **예측 박스의 ID (규칙 #1).** 모델 예측은 3D 짝이 없는 2D 전용 객체다. 짝지어진 정답 박스와도 다른
   객체다. `detections2D`에 섞어 넣으면 "2D와 3D의 ID가 같다"는 규칙이 깨진다.
   현재 생각: `Frame`에 예측용 배열을 따로 두고(예: `predictions2D`), ID에 겹칠 수 없는 접두어를 붙인다.
   선택은 계속 `selectedObjectId` 하나로 한다(규칙 #2).

2. **정답 2D 박스를 만드는 방법.** nuScenes에는 사람이 사진에 그린 2D 박스가 없다.
   - 지금 방식: 3D 박스의 꼭짓점 8개를 투영해 감싸는 사각형. 실제 물체보다 헐렁해서 IoU가 전반적으로 낮게 나온다.
   - 개선안: 박스 안의 LiDAR 점만 투영해 감싸는 사각형. 물체에 더 가깝다. 단 **먼 물체는 점이 몇 개뿐이라
     부정확해진다.** 거리별 분석에서 중요한 먼 물체에서 오차가 커진다는 뜻이다. 화면용 포인트클라우드는
     점을 솎아낸 것이므로 이 계산은 준비 스크립트에서 원본 점으로 해야 한다.
   - 어느 쪽이든 **근사치임을 화면에 표시한다.** 완전히 고칠 수 없는 한계다.

3. **짝짓기 규칙.** 표준 방식은 "confidence가 높은 예측부터, IoU가 가장 큰 정답과 짝짓는다"이다. 헐렁한
   정답 박스 때문에 IoU 기준을 낮추거나 중심점 거리를 함께 쓸지 정한다.

4. **가려진 객체.** 버스 뒤에 완전히 가려진 보행자도 정답에 들어 있다. 가시성 값을 준비 스크립트에서
   가져와 낮은 단계는 평가에서 뺀다. 어느 단계부터 뺄지 정한다.

5. **클래스 대응표.** YOLO의 `person`, `car`, `bicycle` 등과 nuScenes의 카테고리를 맞춘다. 교통 콘, 방호벽처럼
   YOLO가 출력할 수 없는 클래스는 평가에서 뺀다.
   - **확인 필요 (함정일 수 있음):** 지금 쓰는 장면(scene-0916)의 설명은 "Parking lot, bicycle rack, parked
     bicycles, ..."이다. nuScenes는 자전거 거치대를 **거치대 하나의 박스**로 표시한다. YOLO는 거치대에 세워진
     자전거를 하나하나 `bicycle`로 찾을 것이고, 짝지을 정답이 없어 전부 "잘못 찾음(FP)"으로 집계될 수 있다.
     실제로 그런지 확인하고, 그렇다면 거치대 영역의 예측을 평가에서 제외하는 규칙이 필요하다.

6. **confidence 표시 규칙의 충돌 (F2-E).** F2-E에서 nuScenes 프레임의 confidence 숫자를 모두 숨겼다.
   기준은 프레임 단위다(`frameHasConfidence`가 `Frame.source`를 본다). F5에서는 한 프레임 안에 confidence가
   없는 정답 박스와 실제 confidence가 있는 예측 박스가 함께 있다. 기준을 **객체 단위**로 바꿔야 한다.

7. **confidence 슬라이더.** 예측에는 실제 점수가 있으므로 슬라이더가 다시 의미를 갖는다. 슬라이더를 움직이면
   평가 결과가 바로 바뀌어야 한다. 계산은 selector 단계에서 한다(CLAUDE.md: 필터는 파싱 때가 아니라 selector에서).

8. **지표.** Precision, Recall, 거리 구간별 Recall. "잘못 찾음(FP)"은 짝지어진 정답이 없어 거리를 알 수
   없으므로 거리별 지표는 Recall만 가능하다.

9. **표본 크기.** 지금은 키프레임 10개에 카메라 1대다. 거리 구간으로 나누면 구간당 박스가 몇 개뿐이다.
   F5는 "분석이 동작한다"까지가 목표이고, 숫자를 포트폴리오에 쓰는 것은 F6·F7 이후다. 화면에도 표본 수를 함께 보여준다.

10. **파일 구조.** 현재 생각: 예측 결과는 `nuscenes.json`에 섞지 않고 별도 파일로 둔다. 정답 데이터 파일이
    바뀌지 않아 기존 파서와 테스트가 영향을 받지 않는다.

**하지 않는 것:** 3D 탐지 평가. 평가 대상은 2D 카메라 모델이다. 포트폴리오에도 그렇게 쓴다.

**사용자가 공부하면 좋은 개념:** IoU, TP/FP/FN, Precision/Recall. 용어집에 아직 없다.

### F6 — 카메라 6대

**무엇:** nuScenes 차량의 카메라 6대(`CAM_FRONT`, `CAM_FRONT_LEFT`, `CAM_FRONT_RIGHT`, `CAM_BACK`,
`CAM_BACK_LEFT`, `CAM_BACK_RIGHT`)를 모두 쓴다. 선택한 3D 박스를 어느 카메라가 보고 있는지 자동으로 찾아 보여준다.

**왜:** 공고의 "멀티모달 데이터"에 직접 답한다. F4에서 확인할 수 없던 박스(옆과 뒤)를 확인할 수 있게 되고,
F5의 평가 표본도 늘어난다.

**설계 문서에서 다룰 것**
- **데이터 구조가 크게 바뀐다.** 지금 `Frame`은 사진 한 장(`imageUrl`)과 2D 박스 한 묶음(`detections2D`)을
  갖는다. 카메라가 6대면 사진, 카메라 보정값, 2D 박스가 카메라별로 필요하다. `architecture.md`를 먼저 읽고
  기존 COCO 경로가 깨지지 않는 방법을 설계한다.
- 한 3D 박스가 카메라 두 대에 동시에 보일 수 있다(시야가 겹침). ID는 같게 유지한다(규칙 #1).
- "어느 카메라가 보는가"는 `lib/`의 순수 함수로 만들고 테스트한다. 투영 함수(`egoToCamera`,
  `cameraToPixel`)는 카메라 값을 인자로 받는 구조라 재사용할 수 있다.
- 준비 스크립트는 지금 `CAMERA = "CAM_FRONT"`로 고정돼 있다. 6대분의 사진과 보정값을 내보내도록 고친다.
- 사진 용량: 지금 사진은 장당 약 120~130KB다. 키프레임 10개 × 6대 = 60장이면 약 7~8MB다. F7에서 프레임을
  늘리면 훨씬 커진다. 지연 로딩이 필요하다.
- F5의 YOLO를 6대분 사진에 다시 돌린다.
- 화면: F3에서 정한 오른쪽 위 카메라 칸을 "큰 사진 1장 + 썸네일 6개"로 바꾸는 것이 출발점이다.

### F7 — 장면 탐색

**무엇:** 훨씬 많은 키프레임을 넣고, 조건으로 장면을 찾는다. 예: "보행자가 20m 안에 5명 이상", "모델이 놓친
객체가 있는 장면".

**확인된 사실:** nuScenes-mini에는 장면 10개, 키프레임 404개가 있다. 지금은 장면 하나(scene-0916, 키프레임
41개 중 10개)만 쓴다. 장면마다 영어 설명 텍스트가 있다.

**왜:** 공고의 "데이터 탐색 UI"에 답한다. F5의 평가 결과와 만나면 "모델이 틀리는 장면을 모아 다음 학습에
쓴다"는 현업의 작업이 된다. 데이터가 커지면서 **기술 고도화가 실제로 필요해지는 지점**이기도 하다.

**설계 문서에서 다룰 것**
- **데이터를 나눠서 불러오기.** 지금은 `nuscenes.json` 하나(2.9MB)에 모든 것이 들어 있다. 40배로 늘리면
  한 번에 받을 수 없다. 현재 생각: 가벼운 **목록 파일**(프레임별 요약: 클래스별 개수, 거리 분포, 평가 요약)을
  먼저 받고, 무거운 데이터(포인트클라우드, 사진)는 프레임을 열 때 받는다. 검색은 목록 파일만으로 한다.
- **포인트클라우드 바이너리 전환.** 지금은 JSON 안에 숫자가 글자로 들어 있다. `Float32Array` 그대로 `.bin`으로
  저장하면 파일이 작아지고 해석이 빨라진다. **바꾸기 전에 반드시 지금 수치를 잰다**(파일 크기, 받는 시간,
  해석 시간). 필요하면 Web Worker도 검토한다.
- **호스팅 용량.** Vercel에 올릴 수 있는 정적 파일의 한도를 확인한다. **확인 필요.**
- **타임라인 재설계.** 썸네일을 한 줄로 늘어놓는 지금 방식은 수백 프레임을 감당하지 못한다.
- **목록 성능.** 검색 결과가 수백 건이면 화면에 보이는 줄만 그리는 방식(가상 스크롤)을 검토한다. 먼저 재본다.
- 검색 조건 계산은 `lib/selectors`의 순수 함수로 만들고 테스트한다. 백엔드는 없다.
- **확인 필요:** 준비 스크립트의 점 솎아내기가 실행할 때마다 같은 결과를 내는지. 아니라면 다시 돌릴 때
  기존 데이터 파일이 통째로 바뀐다.

### F8 (도전) — 위에서 본 화면에서 3D 박스 수정

**무엇:** F4에서 반려한 박스를 직접 고친다.

**왜 "위에서 본 화면"인가:** 3D 공간에서 박스를 직접 잡아 고치는 것은 매우 어렵다. 위에서 내려다보면
3D 박스는 **회전된 사각형**으로 보인다. 위치, 가로세로 크기, 방향은 이 2D 편집으로 고치고 높이만 숫자로
입력받으면, 자율주행 라벨링의 핵심을 현실적인 난이도로 다룰 수 있다. 이 화면을 BEV(Bird's Eye View)라고 한다.

**설계 문서에서 다룰 것**
- 편집 화면을 무엇으로 그릴지. 현재 생각: SVG. 포인터 좌표 계산이 단순하고, 이미 2D 박스를 SVG로 그리고 있다.
- 회전된 사각형의 조작 방식: 이동, 모서리로 크기 조절, 회전 손잡이.
- **원본을 고치지 않는다.** 수정 내용은 원본 위에 덮어쓰는 별도 기록으로 저장하고, 화면에는 "수정됨"을
  표시한다. 내보낼 때는 무엇이 바뀌었는지 알 수 있게 한다.
- 실행 취소: 수정 이력을 쌓는 방식(커맨드 패턴)을 직접 만들지, 라이브러리(`zundo` 등)를 쓸지. 라이브러리를
  쓰면 지금의 Zustand 버전과 맞는지 먼저 확인한다.
- 박스를 고치면 카메라 사진 위의 투영이 실시간으로 따라 바뀐다. 기존 투영 함수를 그대로 쓴다.
- 저장: 이 시점에 저장할 데이터가 커지면 IndexedDB를 검토한다.

**이 기능은 "도전"이다.** 시간이 부족하면 하지 않아도 로드맵은 성립한다.

## 5. 설계 문서를 쓰는 방법

기능을 시작하는 세션의 첫 작업이다. 형식은 [README.md](README.md)의 "문서 형식"과 F3 문서를 따른다.

1. **코드를 먼저 읽는다.** 이 문서와 로드맵에 적힌 내용은 작성 당시의 생각이다. 직전 기능이 구현되면서
   달라졌을 수 있다. 관련 파일과 `architecture.md`를 읽고 사실을 다시 확인한다.
2. **화면에 관한 내용은 앱을 띄워 캡처한 뒤 쓴다.**
3. **"지금의 문제"에는 확인한 사실만 쓴다.** 어느 파일의 무엇 때문인지 함께 적는다.
4. **결정이 필요한 항목마다 추천안, 대안, 이유, 대가를 쓴다.** 좋은 점만 쓰지 않는다. F3 문서가 "카메라
   이미지가 작아진다"를 대가로 밝힌 것처럼 쓴다.
5. **완료 기준은 확인할 수 있는 문장으로 쓴다.** "깔끔하다"가 아니라 "1440×900에서 페이지 스크롤이 없다".
6. **불변 규칙 7개와의 관계를 하나씩 적는다.** 특히 #1(ID), #2(선택 상태 하나), #3(로직 위치), #6(정직한 표시).
7. **범위 밖을 분명히 적는다.** 다음 기능으로 넘길 것을 이번 기능에 넣지 않는다.
8. **확인하지 못한 것은 "확인 필요"로 표시한다.**
9. 사용자가 읽는 문서다. 쉬운 말로 쓰고, 새 용어는 그 자리에서 푼다.
10. 다 쓰면 사용자에게 요약과 결정 항목을 보여주고 승인을 받는다. 승인 전에는 구현하지 않는다.
    화면 관련 결정은 "추천안으로 만들어 보여주고 조정"해도 된다고 사용자가 말했다.

## 8. 화면 캡처 방법

이 컴퓨터에서 동작을 확인한 방법이다(2026-11-25).

1. 저장소 루트에서 `npm run dev`를 백그라운드로 실행한다. 첫 화면은 컴파일에 약 18초가 걸린다. 주소는
   `http://localhost:3000`이다.
2. 아래 같은 Node 스크립트를 **임시 폴더에** 만들어 실행한다. Playwright는 루트의 `node_modules/playwright`를
   쓴다. 브라우저는 이미 설치돼 있다.

```js
const { chromium } = require('<저장소 루트>/node_modules/playwright');
(async () => {
  // GPU가 없는 환경에서도 WebGL(3D 뷰)이 그려지도록 하는 옵션
  const browser = await chromium.launch({ args: ['--use-angle=swiftshader', '--enable-unsafe-swiftshader'] });
  const page = await browser.newPage({ viewport: { width: 1440, height: 900 } });
  await page.goto('http://localhost:3000', { waitUntil: 'networkidle', timeout: 60000 });
  await page.waitForTimeout(6000);                 // 3D 장면이 그려질 때까지 기다림
  await page.screenshot({ path: 'nuscenes.png', fullPage: true });
  await page.getByRole('button', { name: /coco/i }).first().click();   // 데이터셋 전환
  await page.waitForTimeout(5000);
  await page.screenshot({ path: 'coco.png', fullPage: true });
  await browser.close();
})();
```

3. 스크롤 유무는 `page.evaluate(() => document.documentElement.scrollHeight === document.documentElement.clientHeight)`로 확인한다.
4. 확인이 끝나면 개발 서버를 끈다.
5. 확인할 화면 크기: 1440×900, 1280×720, 390×844. 사용자의 노트북 브라우저 창은 약 1536×700이므로 이 크기도 함께 본다.

**F3 세션에서 알게 된 것 (2026-11-25)**
- 사용자가 이미 3000번 포트에 개발 서버를 띄워 두는 경우가 있다. 이때 `npm run dev`는 lock 오류로 끝나며,
  3000번 서버를 그대로 쓰면 된다. 내가 띄우지 않은 서버는 끄지 않는다.
- Next.js 개발 표시(`<nextjs-portal>`)가 왼쪽 아래 Play 버튼을 가려 클릭이 막힌다. 클릭 전에
  `page.addStyleTag({ content: 'nextjs-portal { display: none !important }' })`로 숨긴다.
- F3 이후 화면 영역에 `aria-label`이 붙어 있어 선택자로 쓰기 좋다: `section[aria-label="3D view"]`,
  `"Camera image"`, `"Details"`, `"Objects"`, `"Frames"`.
- 사용자에게 보여줄 때는 캡처를 실제 크기로 넣은 HTML 페이지를 만들어 브라우저로 열어 주었다(PowerShell
  `Start-Process`). 이미지를 클릭하면 "이전 / 시안 / 지금"이 같은 자리에서 바뀌게 하면 비교가 쉽다.
- 캡처와 시안은 용량이 가벼우면 저장소(`docs/plan-feature/assets/F#/`)에 날짜를 붙여 남긴다(사용자 요청).
  F3에서는 PNG를 1:1 크기 그대로 JPEG(품질 85)로 다시 저장해 2.6MB로 줄였다.
- 이 환경의 Bash 도구는 heredoc 안의 역슬래시(`\\`)를 바꿔 버린다. 스크립트 파일은 Write 도구로 만든다.
- 저장소의 일부 파일은 줄바꿈이 CRLF다. Node로 문자열을 찾아 바꾸면 실패할 수 있으니 Edit 도구를 쓴다.
