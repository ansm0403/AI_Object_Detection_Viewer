# 인수인계 문서 (F3 ~ F8)

큰 기능(F) 하나를 세션 하나에서 진행한다. 세션이 바뀌면 이전 대화 내용은 사라지므로, 다음 세션이 이어서
일할 수 있도록 **무엇을 왜 그렇게 정했는지**를 여기에 남긴다.

- **읽는 사람:** 새 세션의 Claude, 그리고 사용자.
- **최초 작성:** 2026-11-25 (방향을 정하고 F3 설계 문서를 쓴 세션).
- **갱신 규칙:** 세션을 끝낼 때마다 1장(현재 상태)과 9장(세션 기록)을 고친다. 4장의 기능별 내용은
  그 기능을 실제로 진행하면서 달라진 점이 생기면 고친다.

---

## 0. 세션을 시작할 때

아래 순서로 읽는다. 다 읽기 전에는 코드를 고치지 않는다.

1. `CLAUDE.md` (자동으로 읽힘): 불변 규칙, 작업 규칙.
2. **이 문서의 1장**: 지금 어디까지 왔고 다음에 할 일이 무엇인지.
3. 이 문서의 2장, 3장: 사용자와 일하는 방식, 방향이 정해진 이유.
4. 이 문서의 4장에서 **이번 세션에서 할 기능** 부분.
5. `.claude/docs/post-mvp-checklist.md`의 "Roadmap — F3+ direction"과 직전 기능의 완료 기록.
6. 이번 기능의 설계 문서(`docs/plan-feature/F#_*.md`). 없으면 5장을 따라 먼저 쓴다.
7. `.claude/docs/architecture.md`: 구조를 바꾸는 작업이면 반드시.

그다음 사용자에게 "이번 세션에서 할 일"을 짧게 확인받고 시작한다.

## 2. 사용자와 일하는 방식

**사용자**
- 신입 프론트엔드 개발자. React, Next.js, TypeScript는 익숙하다.
- **3D(Three.js, R3F), AI 데이터(탐지, 박스, 포인트클라우드), Zustand는 처음 배우는 영역이다.**
- 이 프로젝트의 목적은 포트폴리오다. 목표 직무는 자율주행·로봇 데이터를 다루는 프론트엔드다.

**설명할 때**
- 사용자가 "설명이 어렵다"고 말한 적이 있다. 전문용어는 그 자리에서 풀어 쓰고, 비유를 먼저 든다.
- 새 용어를 도입하면 `.claude/docs/domain-glossary.md`에 바로 추가한다.
- 답변은 "지침에 의거하여 답변할게"로 시작한다(CLAUDE.md 필수조건).

**일할 때**
- 여러 파일을 고치거나 구조를 바꾸기 전에는 계획을 보여주고 승인을 받는다.
- **화면에 관한 판단은 추측하지 않는다.** 앱을 띄워 캡처한 뒤 말한다(8장에 방법).
- 사용자는 "직접 보기 전에는 판단할 수 없다"고 했다. 화면 관련 결정은 **일단 추천안으로 만들어 보여주고
  조정하는 방식**으로 진행한다. 글로 길게 묻지 않는다.
- 확인하지 않은 것을 사실처럼 말하지 않는다. 이 세션에서 빈 명령 파일을 확인하지 않고 "`/plan-feature`로
  하자"고 여러 번 말한 실수가 있었다.
- 커밋은 요청받았을 때만 한다. 형식은 `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`.

**문서 언어**
- `.claude/docs/`의 영어 문서: 영어 본문을 쓰고, 바로 아래에 한국어 번역을 HTML 주석 블록
  (`<!-- KO (move to a localized file) ... -->`)으로 넣는다.
- `docs/plan-feature/`: 한국어로 쓴다. 사용자가 직접 읽고 승인하는 문서이기 때문이다.
- `docs/PROJECT_DESIGN.md`와 `.claude/docs/mvp-checklist.md`는 **절대 고치지 않는다.**

**포트폴리오에 쓰는 말은 정확해야 한다**
- "실무 도구를 만들었다"가 아니라 "실무 도구의 핵심 흐름을 재현했다"고 쓴다.
- "3D 플랫폼을 만들었으니 2D 플랫폼 경험도 있다"고 쓰지 않는다. 해본 것과 응용할 수 있는 것을 구분한다.
- 측정하지 않은 숫자는 쓰지 않는다.

2026-11-25 세션에서 논의한 순서대로 적는다. **이미 정한 것을 다음 세션에서 다시 논쟁하지 않기 위한 기록이다.**

### 3.1 출발점: 지금 앱의 문제
- 화면을 캡처해 보니, 앱은 **읽기 전용 뷰어**였다. 둘러보고 거르고 클릭할 수는 있지만 사용자에게 남는
  결과물이 없다.
- 사용자가 먼저 떠올린 문제의식: "실무 데이터 도구는 스크롤 없이 쓴다." 이것이 F3의 출발점이다.

### 3.2 도구의 종류 세 가지를 비교했다

| 종류 | 사용자가 하는 일 | 판단 |
|---|---|---|
| 라벨 검수 | 정답 박스가 맞는지 승인/반려 | **채택 (F4).** 라벨링 회사 제품과 직접 연결되고 프론트엔드 실력이 가장 많이 드러난다 |
| 모델 오류 검수 | 모델이 어디서 틀렸는지 찾기 | **채택 (F5).** AI 평가 개념을 이해한다는 차별점 |
| 데이터 탐색 | 조건에 맞는 장면 찾기 | **뒤로 (F7).** 데이터가 10프레임뿐이면 설득력이 없다. 데이터를 늘린 뒤에 한다 |

### 3.3 2D 중심 계획을 세웠다가 3D 중심으로 바꿨다
- 처음에는 COCO(2D 사진) 중심으로 계획했다: 정답 vs 예측 비교, 2D 박스 수정.
- 사용자가 "원래 자율주행 데이터 직무를 보고 시작한 프로젝트"라고 알려줬다. `PROJECT_DESIGN.md` 1장에 당시
  공고의 요구 역량이 있다: AI 데이터 플랫폼, 멀티모달 데이터, 3D 시각화, 어노테이션, 데이터 탐색 UI.
- 이 기준으로 보면 2D 중심 계획은 **프로젝트의 가장 강한 부분(F2: 실측 3D, LiDAR, 좌표계)을 키우지 않고**
  일반 2D 라벨링 도구 쪽으로 기울어 있었다. 불변 규칙 #5(3D가 메인)와도 어긋난다.
- 그래서 **nuScenes(3D) 중심**으로 바꿨다. 사용자의 표현으로는 "선회가 아니라 확장"이다. 플랫폼 역량(화면,
  검수 흐름, 상태, 성능, 탐색)의 대부분은 2D든 3D든 같기 때문이다.

### 3.4 세 가지 방향 중 B를 골랐다

| 방향 | 내용 | 판단 |
|---|---|---|
| A | 2D AI 데이터 플랫폼 (COCO 라벨 검수·수정) | 3D 강점이 묻힌다 |
| **B** | **3D AI 데이터 플랫폼 (3D 라벨 검수 + 모델 평가 + 장면 탐색)** | **채택** |
| C | 3D 데이터 분석 앱 (주행 기록 재생·디버깅, Foxglove나 Rerun 같은 것) | GPS·IMU 같은 새 센서 데이터가 필요해 범위가 가장 크다 |

### 3.5 평가를 COCO가 아니라 nuScenes 카메라 이미지에서 하기로 했다
- 걱정: 3D 검수와 2D 모델 평가를 한 프로젝트에 넣으면 중구난방으로 보이지 않을까.
- 해결: 평가를 **nuScenes의 카메라 사진 위에서** 한다. 사진에 YOLO(2D 모델)를 돌리고, 3D 정답 박스를 사진에
  투영한 것과 비교한다.
- 이렇게 하면 COCO로는 불가능한 분석이 생긴다: **"모델이 놓친 객체는 3D 공간에서 어디에 있었나"**, 그리고
  **거리별 탐지율**. 정답 박스에 LiDAR로 잰 실제 거리가 있기 때문이다.
- 두 기능은 "데이터 품질"의 양면으로 묶인다. 라벨 품질(정답이 맞나)과 모델 품질(모델이 맞히나).
- 사용자가 이 장점 때문에 평가를 넣기로 확정했다.

### 3.6 하지 않기로 한 것과 이유

| 항목 | 이유 |
|---|---|
| 3D 탐지 모델 실행 | NVIDIA GPU와 까다로운 설치 환경이 필요하고 Windows 지원이 약하다. 입력 준비가 복잡하다(여러 스캔을 겹쳐야 하고, 지금 데이터는 화면용으로 점을 솎아낸 것이라 원본부터 다시 처리해야 한다). 회전된 3D 박스의 판정도 따로 공부해야 한다 |
| 백엔드, DB, 로그인, 다중 사용자 | CLAUDE.md에서 금지. 풀려면 사용자의 명시적 결정이 필요하다 |
| WebGPU 렌더러 전환, 실시간 스트리밍 | 지금 목표와 거리가 멀다 |
| 2D 전용 라벨 유형(폴리곤, 마스크, 키포인트) | 3D 중심 초점을 흐린다 |

### 3.7 기술 고도화는 "먼저 재고, 느리면 바꾼다"
- 서버 컴포넌트 전환, `useTransition`, 포인트클라우드 바이너리 전환, Web Worker는 **독립 기능으로 하지 않는다.**
  필요가 측정으로 확인될 때 끼워 넣고, 전후 숫자를 기록한다.
- 서버 컴포넌트 전환은 처음에 "초급 1순위"로 추천했다가 코드를 본 뒤 뒤로 미뤘다. 데이터셋 전환이 어차피
  브라우저에서 일어나고, 2.9MB 데이터를 서버가 페이지에 실어 보내면 오히려 무거워질 수 있기 때문이다.
- 사용자에게 강조한 원칙: 신입 포트폴리오에서는 "바꿨다"보다 **"왜 바꿨고 얼마나 좋아졌는지"**가 중요하다.

### 3.8 현업 도구와의 거리 (솔직한 평가)
- 이 계획으로 갈 수 있는 곳: **현업 도구와 비슷하게 동작하는 1인용 검수 도구.**
- 갈 수 없는 곳: 현업에서 그대로 쓰는 도구. 다중 사용자, 작업 배정, 권한, 서버 저장이 없다.
- 사용자에게 권한 것: 계획을 확정하기 전에 **CVAT나 Label Studio를 1시간 써보기.** 실제로 써봤는지는
  확인되지 않았다. F4 세션을 시작할 때 물어볼 것.

### F4 — 3D 박스 검수

**✅ 완료 (2026-11-25).** 자세한 결과는 `post-mvp-checklist.md`의 F4 항목과 `architecture.md`의 "Review (F4)".
여기에는 다음 기능에 필요한 것만 적는다.

- 설계 문서: [F4_box_review.md](F4_box_review.md). 계획 당시의 기록으로 두고 고치지 않았다.
- **진행 방식:** 사실 확인(코드, 원본 데이터, 캡처) → 가장 큰 결정 하나를 먼저 물음 → 시안 → 설계 문서 →
  단계(A~F)마다 실제 앱을 조작해 확인 + 캡처 페이지 → 사용자 확인 → 커밋 → 마지막에 엣지 케이스 검증.
- **시안을 만드는 새 방법:** 정적 HTML을 따로 만들지 않고, **실제 앱을 띄운 뒤 그 화면의 DOM에 제안하는 UI를
  그려 넣고 찍었다.** 3D 뷰, 사진, 목록이 실제라서 판단하기 쉽고 만드는 시간도 짧다(8장).
- **만든 것 요약:** 판정(승인 / 반려 / 판단 불가) + 사유 + 메모, 저장(localStorage), 진행률, 정렬과 대기열,
  단축키, 카메라 확대와 투영한 3D 박스, 근거 한 줄, 내보내기(JSON / CSV), 연습 모드(변형 + 채점).
- **구조:** 검수 로직은 전부 `lib/review/`의 순수 함수(테스트 132개), 기록은 `store/review-store.ts`,
  화면은 `components/review/`. 선택 상태는 여전히 `selectedObjectId` 하나다.
- **HANDOFF의 원래 개요와 달라진 큰 점:** "판단 불가" 판정 추가, 연습 모드 추가, IndexedDB 대신 localStorage,
  근거(LiDAR 점 개수, 가려짐)를 버튼 위 한 줄로 표시.

### F5 — 카메라 탐지 평가

**✅ 완료 (2026-11-26).** 자세한 결과는 `post-mvp-checklist.md`의 F5 항목과 `architecture.md`의 "Evaluation (F5)".
여기에는 다음 기능에 필요한 것만 적는다.

- 설계 문서: [F5_camera_detection_eval.md](F5_camera_detection_eval.md). 계획 당시의 기록으로 두고 고치지 않았다
  (2.2절 표의 숫자 2개가 틀렸다는 것은 체크리스트와 Edge_F#5 Case 7에 적었다).
- **쉬운 설명 (사용자에게 통했던 비유):** 시험 채점이다. 사진은 문제, YOLO의 박스는 학생 답안, nuScenes 정답 박스는
  정답지다. F4는 정답지에 오타가 없는지 보는 일, F5는 답안을 채점하는 일이다. 찾음 / 놓침 / 헛짚음은 F4 연습 모드의
  채점과 같은 세 칸이다. 용어는 `domain-glossary.md`의 "Evaluation Terms (F5)"에 있다.
- **진행 방식:** 사실 확인(코드, 원본 데이터, **YOLO를 실제로 돌려 본 결과**) → 가장 큰 결정 하나를 시안으로 물음 →
  설계 문서 → 단계(0, A~D)마다 실제 앱을 조작해 확인 + 캡처 페이지 → 사용자 확인 → 마지막에 엣지 케이스 검증.
  설계 전에 모델을 임시 폴더에 돌려 본 것이 결정(IoU 0.3, 채점 제외, 입력 크기)의 근거가 됐다.
- **만든 것 요약:** 상단의 `Review | Evaluate` 모드. 평가 모드에서는 화면 틀은 그대로이고 칸의 역할이 바뀐다:
  결과 목록(놓침 → 헛짚음 → 찾음 → 채점 제외), 카메라 칸의 정답(점선)과 모델(실선), 3D 박스의 결과 색,
  평가 패널(Precision / Recall, 거리별·클래스별 Recall, 선택한 결과의 이유 한 줄), Min score 슬라이더, 타임라인의 "N missed".
- **구조:** 채점 로직은 전부 `lib/evaluation/`의 순수 함수(테스트 139개), 화면은 `components/evaluation/`.
  예측은 `Frame`에 넣지 않은 별도 타입 `Prediction2D`이고 파일도 따로다(`predictions.json`).
  선택 상태는 여전히 `selectedObjectId` 하나(헛짚음은 `pred:<프레임>:<번호>` ID). store는 바꾸지 않았다.
- **뷰어에 생긴 "밖에서 받는 입력"** (F6에서 그대로 쓸 수 있다): `Viewer2D`의 `overlay`(그릴 사각형 목록 + 확대 영역)와
  `legend`, `Viewer3D`의 `boxColors`(박스별 선 색)와 `legend`, `Timeline`의 `badges`, `Header`의 `modeSwitch`.
  이 컴포넌트들은 평가가 무엇인지 모른다.
- **HANDOFF의 원래 개요와 달라진 큰 점:** `Frame.predictions2D` 대신 별도 타입과 파일, `frameHasConfidence`는 바꾸지 않음
  (타입이 갈라 줘서 필요 없었다), 정답 2D 박스는 지금 방식 유지(LiDAR 점으로 조이면 오히려 나빠짐을 실측),
  자전거 거치대 규칙은 만들지 않음(앞 카메라에 하나도 없음).
- **실제 숫자 (기본 규칙: 점수 0.25 이상, 같은 클래스, IoU 0.3 이상, 가시성 0~40% 채점 제외):** 찾음 91, 놓침 83,
  헛짚음 13, 채점 제외 26 → Precision 88%, Recall 52%. 클래스별 Recall: 차 18/22, 보행자 73/112, **오토바이 0/40**
  (이 장면의 특징: 주차된 오토바이 줄). 거리별: 10~20m 36/64, 20~30m 45/87, 30~40m 10/23.
  **프레임 10개, 카메라 1대라 모델 성능으로 인용하지 않는다.**

### F6 — 카메라 6대

**✅ 완료 (2026-11-26).** 자세한 결과는 `post-mvp-checklist.md`의 F6 항목과 `architecture.md`의 "Six Cameras (F6)".
여기에는 다음 기능에 필요한 것만 적는다.

- **쉬운 설명 (사용자에게 쓴 비유):** 차 지붕에 카메라 6대가 바깥을 보고 둥글게 달려 있다. 사람이 제자리에서 한 바퀴 돌며

- **진행 방식:** 사실 확인(원본 데이터 조사 + YOLO를 60장에 시험 실행, 결과는 임시 폴더에만) → 실제 앱 위에 그린 시안 →
  설계 문서(결정 17개) → 사용자 승인("추천대로") → 단계 A~C마다 실제 앱 확인 + 캡처 페이지 → 사용자 확인 → D와 엣지 검증.
  **조사 스크립트가 앱의 규칙과 같은지를 먼저 검증했다**(앞 카메라 결과 91 / 83 / 13 / 26을 재현). F5에서 조사 숫자가 틀렸던
  일(Edge_F#5 Case 7)을 되풀이하지 않기 위해서였고, 그 결과 설계 문서의 숫자가 구현 뒤에도 모두 맞았다.
- **만든 것 요약:** 카메라 칸 아래 썸네일 6개, 고른 박스를 보는 카메라로 큰 사진이 자동 전환(재생 중에도 따라감),
  `[` `]` 단축키, 목록과 근거 줄의 카메라 표시, 정렬 "By camera" / "Unsure first", 평가를 사진 60장으로(사진 단위 채점,
  물체 단위 3D 색, 거치대 규칙, 카메라별 Recall).
- **구조:** 카메라 관련 순수 함수는 `lib/cameras/`(테스트 62개), 화면은 `components/camera/`.
  `Frame`에 `cameras?: CameraView[]`가 생겼고 기존 필드는 그대로다. **핵심은 `frameAsCamera(frame, 이름)`**: 그 카메라의 사진과
  2D 박스를 기존 필드 자리에 넣은 프레임을 돌려주므로, 사진 한 장을 다루던 코드(`Viewer2D`, `evaluateFrame`, `buildOverlay`)를
  고치지 않았다. 선택 상태는 여전히 `selectedObjectId` 하나이고, 지금 보는 카메라는 page의 화면 설정이다(`useActiveCamera`).
- **실수하기 쉬운 자리:** nuScenes 프레임의 `frame.detections2D`는 **"기본(앞) 카메라의 박스"** 다. "어느 카메라든"을 물으려면
  `lib/cameras`(`camerasSeeing`, `bestViewsByObject`)를 쓴다. F6-D에서 직접 읽는 곳을 전부 확인했다.
- **실제 숫자 (기본 규칙):** 앞 카메라만은 그대로 91 / 83 / 13 / 26. 사진 60장은 찾음 349, 놓침 182, 헛짚음 107, 채점 제외 180 →
  Precision 77%, Recall 66%(거치대 규칙을 끄면 헛짚음 121). 물체 단위로는 418개 중 295개를 카메라 한 대 이상이 찾았다.
  박스 583개는 모두 어느 카메라엔가 보인다(1대 443, 2대 140). **장면 하나, 프레임 10개라 모델 성능으로 인용하지 않는다.**
- **HANDOFF의 원래 개요와 달라진 큰 점:** "한 물체가 두 카메라에 보이면 한 번만 셀지"는 **사진 단위로 두 번 세는 것**으로 정했다
  (물체 단위는 3D 색과 한 줄 요약에만). 지연 로딩이 아니라 **미리 받기**로 했다(10개 프레임, 60장 8MB). 거치대 규칙은 만들었다
  (헛짚음 14개가 모두 거치대 안). 연습 모드는 "어느 카메라든" 기준이 되어 같은 시드라도 심기는 오류가 달라졌다.

### F7 — 장면 탐색

**무엇:** 훨씬 많은 키프레임을 넣고, 조건으로 장면을 찾는다. 예: "보행자가 20m 안에 5명 이상", "모델이 놓친
객체가 있는 장면".

**확인된 사실:** nuScenes-mini에는 장면 10개, 키프레임 404개가 있다. 지금은 장면 하나(scene-0916, 키프레임
41개 중 10개)만 쓴다. 장면마다 영어 설명 텍스트가 있다.

**왜:** 공고의 "데이터 탐색 UI"에 답한다. F5의 평가 결과와 만나면 "모델이 틀리는 장면을 모아 다음 학습에
쓴다"는 현업의 작업이 된다. 데이터가 커지면서 **기술 고도화가 실제로 필요해지는 지점**이기도 하다.

**설계 문서에서 다룰 것**
- **데이터를 나눠서 불러오기.** 지금은 `nuscenes.json` 하나(2.9MB)에 모든 것이 들어 있다. 40배로 늘리면
  한 번에 받을 수 없다. 현재 생각: 가벼운 **목록 파일**(프레임별 요약: 클래스별 개수, 거리 분포, 평가 요약)을
  먼저 받고, 무거운 데이터(포인트클라우드, 사진)는 프레임을 열 때 받는다. 검색은 목록 파일만으로 한다.
- **포인트클라우드 바이너리 전환.** 지금은 JSON 안에 숫자가 글자로 들어 있다. `Float32Array` 그대로 `.bin`으로
  저장하면 파일이 작아지고 해석이 빨라진다. **바꾸기 전에 반드시 지금 수치를 잰다**(파일 크기, 받는 시간,
  해석 시간). 필요하면 Web Worker도 검토한다.
- **호스팅 용량.** Vercel에 올릴 수 있는 정적 파일의 한도를 확인한다. **확인 필요.**
- **타임라인 재설계.** 썸네일을 한 줄로 늘어놓는 지금 방식은 수백 프레임을 감당하지 못한다.
- **목록 성능.** 검색 결과가 수백 건이면 화면에 보이는 줄만 그리는 방식(가상 스크롤)을 검토한다. 먼저 재본다.
- 검색 조건 계산은 `lib/selectors`의 순수 함수로 만들고 테스트한다. 백엔드는 없다.
- **확인됨 (F4, 2026-11-25):** 준비 스크립트는 다시 돌려도 같은 결과를 낸다. 값 3개를 추가해 다시 만든 파일을
  이전 파일과 비교했더니 새 값 외에는 LiDAR 점 배열과 사진까지 같았다.
- **(F4에서 받은 것)** 프레임과 박스가 늘면 **three.js 상시 비용**(1장 참고)이 그대로 커진다. F7 전에 처리한다.
  **→ 처리했다(2026-11-26, Edge_F#6.5).**
- **(상시 비용 세션에서 받은 것)** 지금의 바닥 비용: nuScenes 박스 40개 프레임에서 가만히 있을 때 JS 초당 약 15ms
  (소프트웨어 렌더링) / 34ms(내장 GPU), 그리기 호출 프레임당 41번(박스 선 1개당 1번 + 점구름 + 격자). **3D 장면은 여전히
  매 프레임 다시 그린다**(R3F 기본값). F7에서 프레임당 박스가 크게 늘면 그리기 호출이 박스 수만큼 늘어난다. 그때
  `renderer.info.render.calls`와 CPU 프로파일을 **먼저 재고**, 필요하면 박스 선을 한 번에 그리는 방법(`instancedMesh` 또는
  선을 하나의 도형으로 합치기)이나 바뀔 때만 그리기(`frameloop="demand"`)를 검토한다. 둘 다 이번에는 재 보고 하지 않았다
  (박스 40개에서는 두드러진 비용이 없었고, 뒤쪽은 맥동·감속·재생·이름표가 계속 그리기에 기대고 있어 동작이 바뀐다).
- **(상시 비용 세션에서 받은 것)** 새 3D 객체를 만들 때의 규칙 두 가지가 `architecture.md`의 "R3F Performance Rules"에
  생겼다: 클릭만 받는 mesh는 `visible={false}`, 매 프레임 그리는 것에 "투명 + 양면"을 함께 쓰지 않기. F8(위에서 본 화면의
  손잡이 등)에서 클릭 대상을 만들 때 그대로 적용한다.
- **(F4에서 받은 것)** 검수 기록은 박스당 약 150바이트이고 저장할 때마다 **전체를 다시 쓴다.** 박스가 수만 개가 되면
  localStorage(약 5MB)와 저장 시간을 다시 재야 한다. 진행률 계산도 매번 모든 프레임을 훑는다(지금 583개라 문제없음).
- **(F4에서 받은 것)** 타임라인 배지가 "검수한 수/전체"를 보여준다. 타임라인을 다시 설계할 때 이 정보를 유지한다.
- **(F5에서 받은 것)** 평가 모드의 타임라인 배지는 "N missed"다(`Timeline`의 `badges` 입력). 이것도 유지한다.
  "모델이 놓친 객체가 있는 장면" 검색의 재료가 이미 있다: `evaluateFrames`가 프레임별 결과 개수를 준다
  (10개 프레임에 0.2~0.4ms). 프레임이 수백 개가 되면 슬라이더를 움직일 때마다 전체를 다시 채점하는 지금 방식의
  비용을 다시 잰다(재지 않은 추정: 프레임 수에 비례한다면 400프레임에 10~15ms쯤).
- **(F5에서 받은 것)** 평가 숫자를 포트폴리오에 쓸 수 있게 되는 시점이 F6·F7이다(표본이 늘어야 한다).
  그때도 "가장 작은 YOLO를 추가 학습 없이 돌린 결과"임과 IoU 0.3 기준임을 함께 적는다.
  **(F6 뒤 갱신)** F6으로 사진은 60장이 됐지만 장면은 여전히 하나다. 숫자를 쓸 수 있게 하는 것은 **장면 수**이고, 그것은 F7이다.
- **(F6에서 받은 것) 데이터가 카메라 수만큼 커진다.** 프레임 하나가 사진 6장(약 0.8MB)이다. 키프레임 404개 전부면 사진만
  약 2,400장, 320MB쯤이다(지금 60장 8MB에서 비례 계산한 추정). 저장소와 Vercel에 그대로 올릴 수 없다. 프레임 수와 함께
  **사진을 어떻게 줄일지**(해상도를 낮춘 사본, 썸네일용 작은 사본, 카메라 일부만)를 F7 설계에서 정한다. 준비 스크립트는
  지금 표준 라이브러리만 쓴다. 사진을 줄이려면 Pillow가 필요해진다(이 컴퓨터에는 이미 있다).
- **(F6에서 받은 것) 미리 받기의 범위.** `page.tsx`의 `PRELOAD_FRAMES_AHEAD = 10`(지금은 전부). 프레임이 늘면 이 숫자를 줄이면
  된다(`lib/cameras`의 `preloadOrder`가 "지금 프레임부터 재생 순서로 N개"를 돌려준다). 썸네일은 지금 큰 사진과 같은
  1600×900 파일을 작게 그린다. 프레임이 수백 개면 타임라인까지 합쳐 부담이 된다. 미리 받은 사진이 쓰는 메모리는 재지 않았다.
  측정값(F6): 20Mbps에서 프레임 하나의 6장 1.1초, 60장 6.5초. 재생에는 초당 12장이 필요한데 20Mbps에서는 약 10장이 온다.
- **(F6에서 받은 것) 채점 비용은 사진 수에 비례한다.** 60장에 1.1ms(F5: 10장에 0.2~0.4ms). 프레임 400개 × 6대 = 2,400장이면
  슬라이더 한 칸에 약 45ms로 추정된다(재지 않은 비례 계산). 그때는 프레임별 결과를 기억해 두거나, 보이는 프레임만 다시
  채점하는 방법을 **재 본 뒤** 정한다.
- **(F6에서 받은 것) 목록 파일에 넣을 요약의 재료.** `evaluateFrames`가 프레임별·카메라별 개수(`FrameCamerasEvaluation`)와
  물체 단위 결과를 준다. "모델이 놓친 객체가 있는 장면", "어느 카메라에서 많이 놓치는가" 같은 검색 조건의 재료다.
- **(F6에서 받은 것) 프레임마다 카메라 수가 달라도 동작한다**(Edge_F#6 Case 2에서 확인). 다른 장면을 넣을 때 카메라가 빠진
  프레임이 있어도 화면이 깨지지 않는다. 다만 **카메라 평면에 걸친 박스**(차 바로 옆 물체)는 이번 장면에 하나도 없어 실제
  데이터로 본 적이 없다. 장면이 늘면 나올 수 있다(지금 규칙: 그 카메라에는 2D 박스가 없음).
- **(F6에서 받은 것) 타임라인 배지.** 평가 모드의 "N missed"는 이제 프레임의 사진 6장 합계다. 유지한다.

### F8 (도전) — 위에서 본 화면에서 3D 박스 수정

**무엇:** F4에서 반려한 박스를 직접 고친다.

**왜 "위에서 본 화면"인가:** 3D 공간에서 박스를 직접 잡아 고치는 것은 매우 어렵다. 위에서 내려다보면
3D 박스는 **회전된 사각형**으로 보인다. 위치, 가로세로 크기, 방향은 이 2D 편집으로 고치고 높이만 숫자로
입력받으면, 자율주행 라벨링의 핵심을 현실적인 난이도로 다룰 수 있다. 이 화면을 BEV(Bird's Eye View)라고 한다.

**설계 문서에서 다룰 것**
- 편집 화면을 무엇으로 그릴지. 현재 생각: SVG. 포인터 좌표 계산이 단순하고, 이미 2D 박스를 SVG로 그리고 있다.
- 회전된 사각형의 조작 방식: 이동, 모서리로 크기 조절, 회전 손잡이.
- **원본을 고치지 않는다.** 수정 내용은 원본 위에 덮어쓰는 별도 기록으로 저장하고, 화면에는 "수정됨"을
  표시한다. 내보낼 때는 무엇이 바뀌었는지 알 수 있게 한다.
- 실행 취소: 수정 이력을 쌓는 방식(커맨드 패턴)을 직접 만들지, 라이브러리(`zundo` 등)를 쓸지. 라이브러리를
  쓰면 지금의 Zustand 버전과 맞는지 먼저 확인한다.
- 박스를 고치면 카메라 사진 위의 투영이 실시간으로 따라 바뀐다. 기존 투영 함수를 그대로 쓴다.
- 저장: 이 시점에 저장할 데이터가 커지면 IndexedDB를 검토한다.
- **(F4에서 받은 것)** 반려 기록(사유 포함)이 수정할 박스의 목록이다. 내보내기 형식(`ai-detection-viewer/review@1`)에
  수정 내용을 더할 때는 형식 버전을 올린다. F4의 연습 모드처럼 "원본 JSON 위에 변경을 덮어 파싱"하는 구조
  (`makePracticeSet`)가 수정 내용을 덮어쓰는 방식의 참고가 된다.

- **(F6에서 받은 것)** 박스를 고치면 **카메라 6대의 투영이 모두** 바뀌어야 한다. 2D 박스는 파서가 한 번 만들어 `Frame.cameras`에
  넣어 두므로, 고친 박스만 다시 투영하는 순수 함수가 필요하다(파서의 카메라별 투영 부분을 꺼내 쓰면 된다). 고치는 동안
  큰 사진은 그 박스를 보는 카메라에 머문다(`pickCamera`는 지금 카메라가 박스를 보면 바꾸지 않는다). 박스를 옮겨 다른
  카메라로 넘어가면 사진이 바뀐다. 편집 중에는 바꾸지 않을지 정해야 한다.
- **(F6에서 받은 것)** "Unsure first" 정렬과 `nextUnsure`가 "다시 봐야 할 박스를 차례로 넘기는" 흐름의 예다. 반려한 박스를
  차례로 고치는 흐름에 같은 방식을 쓸 수 있다(정렬 하나 + 넘김 규칙 하나, `lib/review/queue.ts`).

**이 기능은 "도전"이다.** 시간이 부족하면 하지 않아도 로드맵은 성립한다.

## 5. 설계 문서를 쓰는 방법

기능을 시작하는 세션의 첫 작업이다. 형식은 [README.md](README.md)의 "문서 형식"과 F3 문서를 따른다.

1. **코드를 먼저 읽는다.** 이 문서와 로드맵에 적힌 내용은 작성 당시의 생각이다. 직전 기능이 구현되면서
   달라졌을 수 있다. 관련 파일과 `architecture.md`를 읽고 사실을 다시 확인한다.
2. **화면에 관한 내용은 앱을 띄워 캡처한 뒤 쓴다.**
3. **"지금의 문제"에는 확인한 사실만 쓴다.** 어느 파일의 무엇 때문인지 함께 적는다.
4. **결정이 필요한 항목마다 추천안, 대안, 이유, 대가를 쓴다.** 좋은 점만 쓰지 않는다. F3 문서가 "카메라
   이미지가 작아진다"를 대가로 밝힌 것처럼 쓴다.
5. **완료 기준은 확인할 수 있는 문장으로 쓴다.** "깔끔하다"가 아니라 "1440×900에서 페이지 스크롤이 없다".
6. **불변 규칙 7개와의 관계를 하나씩 적는다.** 특히 #1(ID), #2(선택 상태 하나), #3(로직 위치), #6(정직한 표시).
7. **범위 밖을 분명히 적는다.** 다음 기능으로 넘길 것을 이번 기능에 넣지 않는다.
8. **확인하지 못한 것은 "확인 필요"로 표시한다.**
9. 사용자가 읽는 문서다. 쉬운 말로 쓰고, 새 용어는 그 자리에서 푼다.
10. 다 쓰면 사용자에게 요약과 결정 항목을 보여주고 승인을 받는다. 승인 전에는 구현하지 않는다.
    화면 관련 결정은 "추천안으로 만들어 보여주고 조정"해도 된다고 사용자가 말했다.

## 6. 세션 절차

### 한 세션의 흐름
```
0장 순서대로 읽기 → 설계 문서 쓰기(없으면) → 사용자 승인 → 단계별 구현
→ 단계마다 화면 캡처로 확인(사용자 확인 후 커밋) → 엣지 케이스 검증 → 문서 갱신 → 인수인계 갱신
```

**엣지 케이스 검증 (F4에서 사용자가 구현 직후 요청한 단계. 다음 기능에서도 한다)**
- `/edgecase-review`를 쓴다. 체크리스트를 코드만 읽고 채우지 말고, **단계 확인에서 한 번도 시험하지 않은 조건**을
  실제 앱에서 돌린다. F4에서 실제 문제가 나온 조건: 약속한 최소 폭(1024px)과 그 근처, 탭 두 개, 한글 입력 상태의 키,
  필터를 건 채 끝까지 진행, 저장소가 가득 참 / 차단됨, 옛 형식 데이터, 깨진 저장값.
  **F5에서 실제 문제가 나온 조건:** 한 모드의 Reset이 다른 모드의 필터를 지움(두 모드가 store를 함께 쓸 때),
  슬라이더 값이 데이터가 가진 범위 밖일 때의 표시, 선택은 그대로인데 목록 순서가 바뀔 때의 스크롤,
  지원 폭보다 훨씬 좁은 창(390px)에서의 가로 넘침. **새 모드를 만들면 "다른 모드의 상태를 건드리는가"를 반드시 본다.**
  **F6에서 실제 문제가 나온 조건:** 새 정렬이 **살아 있는 상태(판정)** 를 읽을 때, 판정 하나로 선택한 줄이 목록 아래로
  옮겨져 화면 밖으로 사라짐(선택도 정렬 이름도 그대로라 스크롤이 일어나지 않았다). **데이터가 고르지 않을 때**(프레임마다
  카메라 수가 다름)의 칸 크기. 정상 데이터만으로는 둘 다 나오지 않는다. 데이터를 바꿔 끼워 시험한다(8장).
- 성능이 의심되면 **배포용 빌드로 잰 뒤** 판단한다. F4에서 개발 서버 수치(글자당 110ms)만 보고 최적화를 넣었다가,
  배포용 빌드(글자당 약 2ms)를 재고 되돌렸다.
- 찾은 문제가 이번 기능이 만든 것인지 `git log`로 확인하고, 아닌 것은 고치지 말고 기록해 사용자에게 묻는다.

### 지킬 것
- **세션 하나에 기능 하나.** 이번 기능이 일찍 끝나도 다음 기능을 시작하지 않는다. 다음 기능에 대해 알게 된
  것은 이 문서의 4장에 적어 둔다.
- 관련 없는 파일을 고치지 않는다.
- 새 라이브러리를 넣기 전에 지금의 Three.js, R3F, React, Next 버전과 맞는지 확인한다.
- 테스트는 `lib/`의 순수 로직과 `store/`만 쓴다. 화면 렌더링은 테스트하지 않고 캡처로 확인한다.

      영향을 주는 내용.

  두 카메라에 보이는 채점 대상 113개: 둘 다 찾음 54, 한쪽만 찾음 39, 둘 다 놓침 20.
- (F6에서 확인) nuScenes 공식 평가 코드(`nuscenes-devkit`의 `filter_eval_boxes`)는 자전거·오토바이 박스의 중심이 거치대 박스
  안이면 채점에서 뺀다. 그 함수가 예측과 정답 중 어디에 적용되는지는 그 파일만으로는 확인하지 못했다.

## 8. 화면 캡처 방법

이 컴퓨터에서 동작을 확인한 방법이다(2026-11-25).

1. 저장소 루트에서 `npm run dev`를 백그라운드로 실행한다. 첫 화면은 컴파일에 약 18초가 걸린다. 주소는
   `http://localhost:3000`이다.
2. 아래 같은 Node 스크립트를 **임시 폴더에** 만들어 실행한다. Playwright는 루트의 `node_modules/playwright`를
   쓴다. 브라우저는 이미 설치돼 있다.

```js
const { chromium } = require('<저장소 루트>/node_modules/playwright');
(async () => {
  // GPU가 없는 환경에서도 WebGL(3D 뷰)이 그려지도록 하는 옵션
  const browser = await chromium.launch({ args: ['--use-angle=swiftshader', '--enable-unsafe-swiftshader'] });
  const page = await browser.newPage({ viewport: { width: 1440, height: 900 } });
  await page.goto('http://localhost:3000', { waitUntil: 'networkidle', timeout: 60000 });
  await page.waitForTimeout(6000);                 // 3D 장면이 그려질 때까지 기다림
  await page.screenshot({ path: 'nuscenes.png', fullPage: true });
  await page.getByRole('button', { name: /coco/i }).first().click();   // 데이터셋 전환
  await page.waitForTimeout(5000);
  await page.screenshot({ path: 'coco.png', fullPage: true });
  await browser.close();
})();
```

3. 스크롤 유무는 `page.evaluate(() => document.documentElement.scrollHeight === document.documentElement.clientHeight)`로 확인한다.
4. 확인이 끝나면 개발 서버를 끈다.
5. 확인할 화면 크기: 1440×900, 1280×720, 390×844. 사용자의 노트북 브라우저 창은 약 1536×700이므로 이 크기도 함께 본다.

  3000번 서버를 그대로 쓰면 된다. 내가 띄우지 않은 서버는 끄지 않는다.

**F5 세션에서 알게 된 것 (2026-11-26)**

- **캔버스가 다시 만들어지지 않았는지**는 캔버스 요소에 표시를 남겨(`canvas.__mark = 'same'`) 나중에 다시 읽어 확인한다.

- **요청을 붙잡아 두는 시험**(파일이 늦게 오는 경우)에서는 `waitUntil: 'networkidle'`이 끝나지 않는다. `'load'`를 쓴다.

  (끝나면 지운다).
- **로컬 `tsc --noEmit`이 `.next/dev/types/routes.d.ts` 오류를 내는 일이 있었다.** 떠 있는 개발 서버가 만든 임시 파일이
  깨진 것으로 소스 문제가 아니다. 소스만 보려면 출력에서 `.next/`로 시작하는 줄을 걸러 본다. 세션 뒤쪽에서는 오류가
  없어졌다(개발 서버가 그 파일을 다시 쓴다. 정확히 언제 고쳐졌는지는 확인하지 않았다). 배포용 빌드는 `next-env.d.ts`의
  경로를 `.next/dev/types`에서 `.next/types`로 바꿔 놓으므로, 빌드 뒤에는 그 파일을 `git checkout`으로 되돌린다.
- **단계별 확인 스크립트는 끝까지 남겨 두고 매 단계 다시 돌렸다**(0, B, C, D, 엣지, 회귀). 뒤 단계가 앞 단계를 깨지
  않았는지 2~3분 안에 알 수 있었다. 스크립트가 실패하면 앱 문제인지 스크립트의 기대값 문제인지부터 가린다
  (이번 세션의 스크립트 실패는 대부분 기대값 쪽이었다).
- 캡처 페이지(`steps.html`)는 화면이 9개를 넘으면 숫자키로 다 고를 수 없다. `←` `→` 이동을 넣었다.

**F6 세션에서 알게 된 것 (2026-11-26)**
- **조사 스크립트는 숫자를 쓰기 전에 검증한다.** 설계 전에 Python으로 투영과 채점을 다시 구현해 원본 데이터에 돌렸는데,
  먼저 **앱이 이미 내는 결과(앞 카메라 91 / 83 / 13 / 26, 예측 428개가 저장소 파일과 같음)를 재현하는지** 확인한 뒤에
  새 숫자를 읽었다. 그 결과 설계 문서의 숫자가 구현 뒤 테스트와 모두 일치했다.
- **다른 카메라의 사진을 시안에 쓰는 방법.** 저장소에 아직 없는 사진은 `page.route('**/__mock/*.jpg', …)`로 임시 폴더의
  파일을 내주고, 화면의 `<image href>`를 그 주소로 바꾼다. 저장소를 건드리지 않고 실제 사진으로 시안을 찍을 수 있다.
- **3D 박스를 ID로 찾는 방법.** three.js 장면의 박스 선(`isLineSegments`)에는 이름이 없다. `getWorldPosition`으로 얻은 위치를
  데이터의 박스 중심(three 좌표 = ego 좌표의 (−y, z, −x))과 맞춰 찾는다. 시안에서 박스 색을 결과에 맞게 칠할 때 썼다.
- **데이터를 바꿔 끼워 시험한 것:** 카메라 목록이 없는 옛 형식(`cameras`를 지움), 프레임마다 카메라 수가 다른 데이터,
  옛 형식 예측 파일(@1), 예측 파일 404, 사진 한 폴더 요청 실패(`route.abort()`), 사진이 4초 늦게 오는 경우.
- **사진을 받는 시간은 브라우저의 resource timing으로 잰다.** `performance.getEntriesByType('resource')`의 `responseEnd`와
  `transferSize`를 읽는다(탐색 시작 기준). CDP로 캐시를 끄면(`setCacheDisabled`) 같은 사진을 여러 번 받은 것으로 잡혀
  숫자가 부풀려진다. 캐시는 켠 채 새 창으로 잰다. 속도 흉내는 `Network.emulateNetworkConditions`.
- **이 환경에서는 CDP의 JS 시간으로 조작별 차이를 볼 수 없다.** 3D를 소프트웨어로 그려 메인 스레드가 늘 바쁘다
  (가만히 있어도 JS 시간이 벽시계 시간의 약 80%). 조작이 화면에 반영될 때까지의 시간(`performance.now()` + 조건이 참이 될
  때까지 `waitForFunction` + `requestAnimationFrame`)을 재고, **같은 조작을 비교 대상(카메라 1대짜리 데이터)과 번갈아** 잰다.
- **확인 스크립트의 실패는 이번에도 전부 스크립트 쪽이었다**(약 12번). 자주 나온 것: 이미 검수한 박스의 판정을 바꾼 것이라
  개수가 늘지 않음, 배지 글자가 생겨 선택자가 여러 개에 걸림, CSS로 대문자가 된 제목, 슬라이더를 덜 움직임, 기존 동작을
  잘못 기억함. **실패를 보면 화면의 글자를 그대로 찍어 본다.**
- `aria-label`이 붙은 영역이 하나 늘었다: `section[aria-label="Camera thumbnails"]`. 썸네일 버튼의 `aria-label`은 카메라 이름이고,
  선택한 박스가 보이면 뒤에 `, sees the selected box`가 붙는다. `aria-pressed`가 지금 보는 카메라다.
- 측정이 끝나면 3100번 서버를 끄고(`Get-NetTCPConnection -LocalPort 3100`으로 PID를 찾아 종료), `next-env.d.ts`를
  `git checkout`으로 되돌린다. 3000번(사용자의 개발 서버)은 건드리지 않는다.
- Git Bash heredoc은 여전히 작은따옴표가 든 내용에서 깨진다. 이번에는 **줄 끝(CRLF)을 지키는 작은 치환 도구를 임시 폴더에
  만들어**(`read_bytes` → `\r\n`을 `\n`으로 → 정확히 한 번 나오는 문자열만 바꿈 → 다시 CRLF로) 여러 파일을 고쳤다.
  치환할 문자열이 0번 또는 2번 나오면 멈추게 해서 엉뚱한 곳을 고치지 않았다.

**three.js 상시 비용 세션에서 알게 된 것 (2026-11-26)**
- **이 컴퓨터에는 GPU가 있다**(Intel UHD 내장 + RTX 4060). 지금까지 "GPU가 없는 환경"이라고 적은 것은 Playwright를
  `--use-angle=swiftshader`로 띄웠기 때문이다. `--use-angle=d3d11 --enable-gpu --ignore-gpu-blocklist`로 띄우면 창 없는
  Chromium도 실제 GPU를 쓴다(이번에는 내장 그래픽이 선택됐다). 어느 쪽인지는 `WEBGL_debug_renderer_info`의
  `UNMASKED_RENDERER_WEBGL`로 확인한다. **성능은 두 환경 모두 재고, 화면 비교는 소프트웨어 렌더링으로 한다**(같은 화면을
  두 번 찍으면 픽셀이 완전히 같다).
- **`__THREE_DEVTOOLS__`는 배포용 빌드에서도 동작한다**(F5에서는 개발 서버에서만 시험했다). 장면뿐 아니라 렌더러도
  알려 준다(`e.detail.isWebGLRenderer`). `renderer.info.render.calls`(프레임당 그리기 호출), `renderer.info.programs.length`,
  `renderer.info.memory.geometries`를 읽을 수 있다. R3F의 카메라와 조작기는 `scene.__r3f.root.getState()`의
  `camera`, `controls`(`controls.target`)로 읽는다.
- **가만히 있을 때의 비용을 재는 방법.** CDP `Profiler`(`setSamplingInterval` 200µs)를 5초 돌리고, 노드별 자기 시간을 함수
  이름으로 합친다. `(idle)`과 `(program)`을 뺀 것이 JS 시간이다. 창을 매번 새로 띄워 3번 재고 가운데 값을 쓴다. 한 경우에
  약 13초가 걸린다. 배포용 빌드에서도 three.js 안쪽 함수 이름(`getParameters` 등)은 남아 있다(앱 쪽 함수는 짧게 바뀐다).
- **원인을 찾는 값싼 신호: 재질의 `version`.** 장면의 모든 재질에서 `material.version`을 5초 간격으로 두 번 읽어, 아무것도
  바뀌지 않는데 올라가는 재질을 찾는다. 이번에는 클릭용 상자의 재질 40개만 프레임당 2씩 올랐다.
- **고치기 전에 실험한다.** 코드를 바꾸지 않고 `page.evaluate`로 실행 중인 장면의 재질이나 `visible`을 바꾼 뒤 같은 측정을
  돌리면, 후보 방법들의 효과를 승인받기 전에 숫자로 보여 줄 수 있다(R3F는 바뀐 prop만 다시 적용하므로, 가만히 있는 동안에는
  실행 중에 바꾼 값이 유지된다).
- **화면이 같은지는 "같은 화면에서 바꿔 가며" 찍어 픽셀을 센다.** 따로 띄운 두 화면을 비교하면 안 되는 경우가 있다:
  COCO의 추정 점구름은 띄울 때마다 무작위로 흩어져(`pointcloud-generator.ts`의 `Math.random`) 그것만으로 4.6%가 달랐다.
  픽셀 비교는 Pillow의 `ImageChops.difference`로 한다. 카메라를 돌린 뒤에는 감속이 끝날 때까지 **6초**를 기다린다
  (2.5초로는 두 번 찍은 그림이 서로 달랐다).
- **3D 클릭과 마우스 올림의 전후 비교.** 3D 칸에 15×9 격자로 마우스를 옮기고 누르면서 "커서 모양 + 이름표"와 "선택된 ID"를
  기록해 두고, 고친 뒤 같은 기록과 통째로 비교한다. **박스 안에서의 클릭**은 첫 줄을 선택 → Follow → 3D 칸 가운데에서
  휠을 260번 올려 박스 중심까지 들어감 → 목록에서 다른 줄 선택 → 가운데 클릭 → 처음 박스가 선택되는지로 확인한다.
- 측정 중에는 다른 브라우저를 띄우지 않는다(숫자가 흔들린다). 긴 측정은 백그라운드로 돌리고 끝나기를 기다린다.
- 이번 세션의 확인 스크립트는 한 번에 통과했다(46 / 46). 미리 화면의 글자를 찍어 보는 조사 스크립트를 먼저 돌린 것이 도움이 됐다.
