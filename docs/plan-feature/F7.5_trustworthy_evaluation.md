## 1. 목표

F7에서 nuScenes-mini 전체(장면 10개, 프레임 404개, 사진 2,424장)를 채점하게 됐다. 그런데 화면이 보여 주는 결과 가운데
**맞는지 모르는 것**이 있다. 이번 기능은 평가 기능을 늘리는 일이 아니라, **지금 보여 주는 결과를 믿을 수 있게** 하는 일이다.

여섯 가지를 한다.

| # | 하는 일 | 무엇에 답하나 |
|---|---|---|
| ① | 헛짚음 표본 검수 | "근처에 정답 없는 헛짚음 1,452개는 모델이 틀린 것인가, 정답이 빠진 것인가" |
| ② | IoU 기준 고르기 (0.3 / 0.5) | "기준을 표준(0.5)으로 바꾸면 숫자가 얼마나 달라지나" |
| ③ | 주행 단위 표(8줄)와 고유 물체 수 | "이 숫자는 서로 독립인 자료 몇 개 위에 서 있나" |
| ④ | 거리 구간을 맞춘 낮/밤 비교 | "밤에 덜 찾는 것은 밤이라서인가, 물체가 멀어서인가" |
| ⑤ | 평가 패널에 조건 한 줄 | "무엇으로 잰 숫자인가"(입력 크기 1280, 추가 학습 없음) |
| ⑥ | README 갱신 + 이력서 한 줄 초안 | 위의 숫자, 조건, 한계를 방침대로 적는다 |

**채점 규칙은 바꾸지 않는다.** 테스트가 잠근 숫자는 그대로여야 한다.

**새 용어 (그 자리에서 풀어 쓴다)**
- **표본(sample):** 전체를 다 보는 대신 무작위로 뽑은 일부. 1,452개를 다 보는 대신 100개를 본다.
- **추정:** 표본에서 본 비율로 전체의 비율을 짐작하는 것. "100개 중 40개였다 → 전체도 40% 안팎일 것이다".
  전체를 센 것이 아니므로 항상 **범위**와 함께 말한다("31~50% 사이").
- **모집단:** 표본을 뽑아 온 전체. 여기서는 "근처에 정답 없는 헛짚음" 1,452개.
- **주행(drive):** 차가 한 번 나가서 찍은 기록 하나. nuScenes는 주행 하나에서 20초짜리 **장면**을 여러 개 잘라 낸다.
  같은 주행에서 나온 장면들은 같은 날, 같은 동네, 같은 날씨다.

(임시 Vitest 파일. 끝난 뒤 저장소에서 뺐다). 먼저 잠긴 숫자가 그대로 나오는지 확인했다: 기본 규칙(점수 0.25, IoU 0.3)에서

  같은 클래스인데 겹침 부족 786, 이미 짝지어진 정답에 박스가 하나 더 482. 합 3,514.
- "근처에 정답 없음"의 정의: 그 사진의 모든 정답(클래스 무관, 채점 제외 포함)과의 IoU가 0.1 미만(`match.ts`의 `NEAREST_MIN_IOU`).
- 지금 화면에서는 이것들을 하나씩 찾아가 볼 수는 있다(Explore의 "Unlabelled?"). **판정을 남길 곳은 없다**(시안 4번).

### 2.2 표본을 몇 개 보면 얼마나 믿을 만한가

1,452개에서 무작위로 n개를 뽑아 그중 40%가 "정답이 빠진 실제 물체"였다고 하자. 전체의 진짜 비율이 있을 만한 범위(95% 구간)는:

| 표본 크기 | 표본이 40%일 때 전체의 범위 | 폭 | 걸리는 시간 (하나에 5~10초로 어림) |
|---|---|---|---|
| 50 | 28 ~ 54% | ±13%p | 4~8분 |
| **100** | **31 ~ 50%** | **±9%p** | **8~17분** |
| 200 | 34 ~ 46% | ±6%p | 17~33분 |
| 300 | 35 ~ 45% | ±5%p | 25~50분 |

- 쉬운 말로: **100개를 보면 "대략 열에 서넛에서 다섯"까지 말할 수 있고, 200개를 보면 "열에 서넛에서 넷 반"으로 좁아진다.**
  두 배로 봐도 폭은 3%p쯤만 줄어든다. 표본 크기의 효과는 갈수록 작아진다.
- "95% 구간"의 뜻: 이런 식으로 표본을 뽑아 범위를 만들면 100번 중 95번쯤은 진짜 값이 그 안에 든다.
- 계산 방법: Wilson 구간(비율이 0%나 100%에 가까워도 범위가 음수로 가지 않는 방법)에, 전체가 1,452개로 정해져 있다는 보정을
  넣었다. 이 표는 설계용으로 계산한 값이고, 구현할 때 식을 함수로 고정하고 테스트한다. 시간은 재지 않은 어림이다.
- **주의:** 2.1의 "같은 것이 여러 번" 때문에 실제 불확실성은 이 표보다 조금 더 크다. 화면과 README에 "박스 기준"이라고 적는다.

### 2.3 IoU 기준을 고를 수 없다

- 짝짓기는 이미 기준값을 입력으로 받는다(`EvaluationRules.iouThreshold`). `page.tsx`가 고정값(`IOU_THRESHOLD = 0.3`)을 넣을 뿐이다.
- **0.5로 바꾼 실제 화면의 숫자가 F7 때 조사한 값과 같다**(앱의 기준값을 잠깐 0.5로 바꿔 화면을 읽고 되돌렸다. 시안 3번).

| | 기본 (IoU 0.3) | IoU 0.5 | F7 문서의 조사값 |
|---|---|---|---|
| 찾음 / 놓침 / 헛짚음 / 제외 | 6,726 / 5,292 / 3,514 / 5,278 | 5,462 / 6,556 / 5,231 / 5,278 | |
| 전체 Precision / Recall | 65.7% / 56.0% | **51.1% / 45.4%** | 51% / 45% ✓ |
| 낮 Recall | 64.1% (5,711 / 8,916) | **52.3%** (4,659 / 8,916) | 52% ✓ |
| 밤 Recall | 32.7% (1,015 / 3,102) | **25.9%** (803 / 3,102) | 26% ✓ |
| "근처에 정답 없음" 헛짚음 | 1,452 | **1,452** | |

- 다른 곳이 없다. 같은 기준값이 "채점 제외 물체 위의 박스를 빼는 판정"에도 쓰이지만(F7 문서 13.1의 ⑧이 확인하라고 한 것)
  결과 숫자는 조사값과 같다.
- **"근처에 정답 없음"은 IoU 기준과 무관하게 1,452개다.** 정의가 "모든 정답과 IoU 0.1 미만"이라 0.3이든 0.5이든 같은 박스다.
  그래서 표본 검수의 모집단은 IoU 고르기의 영향을 받지 않는다.
- 위쪽 줄 제목의 설명 글(`page.tsx` 1314번 줄)은 상수 `IOU_THRESHOLD`를 직접 찍는다. 고르기를 넣으면 고쳐야 한다.

### 2.5 "밤이라서가 아니라 멀어서"인지 화면에서 알 수 없다

지금 패널의 "Recall by distance"는 화면의 장면 하나만 보여 준다. 낮과 밤을 같은 거리끼리 나란히 놓은 것은 없다.

| 차에서의 거리 | 낮 (찾음 / 정답) | 밤 (찾음 / 정답) |
|---|---|---|
| 0~10m | 76% (838 / 1,108) | 55% (154 / 280) |
| 10~20m | 79% (1,740 / 2,209) | 30% (228 / 769) |
| 20~30m | 69% (1,463 / 2,121) | 38% (321 / 836) |
| 30~40m | 62% (755 / 1,226) | 29% (138 / 478) |
| 40~50m | 49% (395 / 799) | 20% (48 / 239) |
| 50~60m | 38% (242 / 636) | 39% (70 / 179) |
| 60~70m | 42% (158 / 378) | 26% (24 / 93) |
| 70~80m | 26% (63 / 244) | 29% (28 / 95) |
| 80~90m | 37% (42 / 115) | 2% (1 / 56) |
| 90m 이상 | 19% (15 / 80) | 4% (3 / 77) |

- **구간마다 정답이 충분한가:** 90m까지는 낮과 밤 모두 구간마다 50개 이상이다. 그 밖은 밤의 구간들이 6~28개라 구간별로는
  비교할 수 없어 하나로 합쳤다.
- **0~50m의 다섯 구간 모두에서 밤이 낮다.** 이 범위에 낮 정답의 83.7%, 밤 정답의 83.9%가 있다(0~50m 합: 낮 69.6%, 밤 34.2%).
- **50m 밖에서는 차이가 없거나 뒤집히는 구간이 있다**(50~60m 38 : 39, 70~80m 26 : 29). 둘 다 낮고 정답 수가 적다.
- **낮과 밤은 정답의 거리 분포가 거의 같다.** 밤의 거리 분포를 낮과 같게 맞춰 다시 계산하면 밤 Recall은 32.7% → **33.9%**
  (낮 64.1%). 반대로 낮을 밤의 분포에 맞추면 64.1% → 63.6%. 즉 **거리로는 이 차이가 설명되지 않는다.**
- IoU 0.5에서도 같다: 0~50m 낮 56.5% / 밤 26.4%, 거리 분포를 맞춘 밤 26.8%.
- 이것은 "밤이라서"의 증명이 아니다. 밤은 여전히 주행 한 번이고, 그 주행의 장소, 카메라 노출, 물체 구성이 함께 들어 있다.

### 2.6 조건 두 가지가 화면에 없다

- 평가 패널에 **입력 크기 1280**과 **"추가 학습 없음"**이 나오지 않는다(F7 문서 13.1에서 찾은 것).
- 예측 파일에 재료가 있다: `model: { name: "yolov8n", weights: "yolov8n.pt", imageSize: 1280, minScore: 0.05, … }`.
  `imageSize`는 이미 읽고(`PredictionModelInfo.imageSize`) 쓰지 않는다. `weights`는 읽지 않는다.
- "추가 학습 없음"은 파일에 글자로 적혀 있지 않다. `yolov8n.pt`가 Ultralytics가 공개한 가중치 파일의 이름이고,
  `predict_nuscenes.py`가 그 파일을 그대로 읽어 쓴다는 사실(스크립트 177번 줄 `YOLO(weights_path)`, 학습 호출 없음)에서 나온다.

### 3.1 표본 검수 (시안 5)

- 평가 모드에 **"Check a sample"** 버튼이 생긴다. 누르면 평가 모드 안에서 화면의 역할이 바뀐다(네 번째 모드가 아니다).
- **위쪽 줄:** "Sample check · 무작위 100개 / 1,452개 · 다시 열어도 같은 박스 · 표본 크기 100 | 200 | 300 · Export · Exit".
  점수 슬라이더와 IoU 고르기는 이 화면에서 보이지 않는다(모집단은 고정 규칙으로 정한다).
- **왼쪽 목록:** 표본의 박스가 뽑힌 순서대로. 줄마다 번호, 판정 아이콘, 클래스, 점수, 장면, 카메라.
- **사진:** 고른 박스가 있는 카메라의 사진으로 자동으로 바뀌고 그 박스로 확대된다. `Z`로 전체 사진을 본다.
- **오른쪽 아래 패널:** 그 박스의 사실(모델이 말한 클래스, 점수, 크기), 판정 버튼 세 개, 지금까지의 추정.
- **판정과 단축키 (F4와 같은 키):** `A` 진짜 물체인데 정답이 빠짐 / `R` 모델이 틀림 / `U` 애매함. `C` 지우기, `J` `K` 앞뒤,
  `Z` 확대, `[` `]` 옆 카메라. 판정하면 **아직 판정하지 않은 다음 박스**로 넘어간다. 그 박스가 다른 장면에 있으면 장면이 바뀐다.
- **추정:** 항상 "N개 중 M개"와 범위로 나온다. 예: "100개 중 41개 → 전체 1,452개의 약 32~50%. 표본에서 추정한 값이며 전체를
  센 것이 아니다." 표본을 다 보기 전에는 "not final"이 붙는다.
- **저장:** 브라우저(localStorage), F4의 검수 기록과 같은 저장소, 같은 방식. 새로 고쳐도 남는다.
- **내보내기:** JSON 파일 하나(표본의 정의, 박스별 판정, 추정). 판정은 README에 쓸 숫자의 근거이므로 파일로 남길 수 있어야 한다.

### 3.2 IoU 기준 고르기와 조건 한 줄 (시안 2, 3)

- 평가 모드의 위쪽 줄, 점수 슬라이더 옆에 **Min overlap (IoU) [0.3 | 0.5]**. 기본 0.3.
- 0.5를 고르면 이 장면의 숫자, 목록, 사진, 3D 색, 타임라인, 전체 장면 숫자가 모두 0.5로 다시 계산된다.
  패널과 설명 글의 "IoU ≥ 0.3"도 따라 바뀐다. 0.5 옆에는 "표준 기준. 투영한 정답에는 엄격하다"는 말이 붙는다.
- 평가 패널에 한 줄: **"YOLOv8n · no fine-tuning · input 1280 · score ≥ 0.25 · IoU ≥ 0.3"**.

### 3.3 주행 단위 표, 거리별 낮/밤 (시안 6, 7, 8)

두 가지 배치를 그렸다. **먼저 정해 줄 것**이다(7장 결정 2).

- **배치 A (패널 안):** 지금의 "All scenes" 블록에 Scenes | Drives 전환, 주행 표 8줄, 거리별 낮/밤 표를 넣는다.
  1536×700에서는 패널이 232px라 표가 두 줄만 보이고 스크롤해야 한다.
- **배치 B (보고서 창, 추천):** "All scenes"의 버튼으로 목록과 3D 화면 자리 위에 창을 연다. 조건 줄, 전체 숫자, 헛짚음 확인 상태,
  주행 표 8줄, 거리별 낮/밤 표가 한 화면에 들어간다. `Esc`로 닫는다. 3D 화면은 밑에 그대로 있다.

두 배치 모두:
- 주행 표에는 날짜, 장소, 장면 수, 채점된 서로 다른 물체 수, Recall, 찾음 / 정답이 나온다. 밤 주행은 색이 다르다.
- 거리별 낮/밤 표에는 구간마다 낮과 밤의 Recall과 **정답 수**가 나온다. 표 안에 **"night = 1 drive"**와 "원인은 이것으로 밝혀지지
  않는다"가 함께 있다(9장 방침: 낮/밤을 나눈 표에는 단서를 함께 넣는다).
- "헛짚음 1,452개(41%)는 근처에 정답이 없다 — 확인 안 됨 / 100개 중 N개 판정됨"이 숫자 옆에 나온다.

### 3.4 README와 이력서 한 줄

- README에 "평가 결과" 절을 만든다: 조건 → 숫자(기본 규칙, IoU 0.5) → 주행 단위 표 → 낮/밤(거리별 포함, "주행 1회", "관찰됐다")
  → 헛짚음 표본 검수 결과(사용자가 넣기로 하면) → 한계(F7 문서 9장의 9가지 + 2.7절에서 확인한 것) → 공식 평가와의 관계.
- 낡은 부분을 고친다: 테스트 수, F3~F7 기능 설명, 화면 캡처 안내.
- README를 고친 뒤 이력서 한 줄 초안을 2~3개 만들어 보여 준다. 넣을지는 사용자가 정한다.

## 4. 범위와 범위 밖

**범위:** 1장의 여섯 가지.

**하지 않는 것 (지시받은 것)**
- 채점 규칙 변경: 제외 영역, 사진 안에 들어온 비율, 카메라 평면에 걸친 박스.

- F8.

**하지 않기로 한 것 (이번에 떠올랐지만 넣지 않는다. 이유와 함께)**

| 떠오른 것 | 넣지 않는 이유 |
|---|---|
| 판정 결과로 Precision을 다시 계산해 보여 주기("정답이 빠진 것을 빼면 70%") | 채점 규칙을 바꾸는 것과 같다. 정답이 빠진 물체가 있다면 모델이 **놓친** 빠진 물체도 있을 텐데 그것은 셀 수 없다. 한쪽만 고치면 치우친 숫자가 된다. README에는 "Precision이 실제보다 낮게 계산됐을 수 있다. 다시 채점하지는 않았다"고 쓴다 |
| 헛짚음 네 종류(1,452 / 794 / 786 / 482)를 화면에 표로 | "근처에 정답 없음" 하나만 있으면 표본 검수의 맥락이 선다. 나머지는 묶음 나(혼동행렬)에 가깝다 |
| IoU 0.3과 0.5를 한 화면에 나란히 | 고르기 버튼으로 오갈 수 있다. README에는 두 값을 함께 적는다 |
| 원본 해상도로 자른 사진을 표본용으로 따로 싣기 | 재 보니 차이가 거의 없다(2.1절, 시안 9) |
| 내보낸 판정 파일을 다시 불러오기 | 이번에는 혼자, 한 브라우저에서 판정한다. 필요해지면 그때 |
| 사진 위에 LiDAR 점을 겹쳐 "거기 무언가 있는지" 보기 | 판정에 도움이 되겠지만 새 기능이다. 적어 두고 묻는다 |

## 7. 결정이 필요한 항목

### 먼저 정해 줄 것 (2가지)

**결정 1. 표본을 몇 개로 시작할까**
- **추천: 100개.** 약 ±9%p(2.2절), 8~17분. 부족하면 200, 300으로 늘린다. **늘려도 앞의 100개와 그 판정은 그대로다**
  (전체를 한 번 섞어 둔 순서의 앞에서부터 N개를 쓰기 때문이다).
- 대안: 처음부터 200개(±6%p, 17~33분) 또는 300개(±5%p).
- 대가: 100개로는 "40%"와 "50%"를 가르지 못한다. README에 범위째로 써야 한다.

**결정 2. 주행 표와 거리별 낮/밤을 어디에 둘까 (시안 6, 7, 8)**
- **추천: 배치 B(보고서 창).** 조건, 전체 숫자, 주행 8줄, 거리별 낮/밤, 헛짚음 확인 상태가 한 화면에 들어간다.
  숫자를 읽기 전에 조건이 먼저 보인다. README에 실을 캡처 한 장이 된다.
- 대안: 배치 A(패널 안). 만들 것이 가장 적다. 네 노트북 창(1536×700)에서는 232px 칸 안에서 스크롤해야 표가 보인다.

## 9. 불변 규칙과의 관계

| 규칙 | 이번 기능에서 |
|---|---|
| #1 2D와 3D의 ID가 같다 | 건드리지 않는다. 모델 박스는 여전히 `Frame` 밖의 별도 타입이다 |
| #2 `selectedObjectId` 하나 | 표본의 박스를 고르는 것도 `selectedObjectId`에 예측 ID를 넣는 것이다(F5부터 있던 방식). "지금 판정 중인 박스"라는 별도 상태를 만들지 않는다. 표본의 순서와 크기는 선택이 아니라 화면 설정이다 |
| #3 파싱과 좌표 변환은 컴포넌트와 store 밖 | 표본 뽑기, 추정, 주행 집계, 거리 비교는 모두 `lib/`의 순수 함수이고 테스트한다. store는 기록만 갖는다 |
| #4 범위를 넓히지 않는다 | 4장의 "하지 않기로 한 것". 넓히고 싶어지면 적어 두고 묻는다 |
| #5 3D가 메인 | 화면 틀은 그대로다. 보고서 창(배치 B)은 여닫는 것이고 3D 캔버스를 떼지 않는다 |
| #6 추정을 사실처럼 말하지 않는다 | 이번 기능의 중심이다. 표본의 결과는 "N개 중 M개, 범위"로만. 낮/밤은 "주행 1회, 원인은 모른다"와 함께. "추가 학습 없음"은 근거가 있을 때만. 정답 박스가 투영한 근사라는 말은 그대로 둔다 |
| #7 COCO에서 3D를 읽지 않는다 | 건드리지 않는다. COCO에는 평가 모드가 없다 |

## 10. 위험 요소

- **판정은 한 사람의 눈이다.** 작은 박스, 줄인 사진, 한 명. README에 "한 사람이 960×540 사진으로 판정했다"를 적는다.
- **같은 물체가 표본에 여러 번.** 범위가 실제보다 좁게 나온다(2.1절). "박스 기준"이라고 적는다.
- **localStorage가 지워지면 판정이 사라진다.** 내보내기를 만들고, 판정이 끝나면 내보내라고 안내한다.
- **`page.tsx`가 더 커진다.** 새 상태와 연결은 `useSampleCheck`에 둔다. page에는 호출과 전달만.
- **장면을 넘는 넘김.** 판정 뒤 다음 박스가 다른 장면이면 장면 받기 → 프레임 → 카메라 → 선택이 순서대로 일어나야 한다.
  F7의 "다른 장면의 검색 결과 열기"와 같은 길을 쓰되, 장면이 바뀔 때 선택을 지우는 기존 동작과 순서가 꼬일 수 있다. 단계 B에서 먼저 확인한다.
- **위쪽 줄의 폭.** IoU 고르기가 1024px에서 넘칠 수 있다.
- **패널 높이 232px.** 조건 한 줄이 들어가면 내용이 20px 밀린다.
