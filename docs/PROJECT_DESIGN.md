# 포트폴리오 프로젝트 설계 — 컨텍스트 전달 문서 v2

> 이 문서는 다음 대화에서 현재까지의 모든 논의 맥락을 그대로 이어받을 수 있도록 정리한 것이다.
> 읽는 AI는 이 내용을 바탕으로 구체적인 프로젝트 설계도를 바로 작성해야 한다.
> v1 문서 이후 추가 결정사항과 논의 내용이 모두 반영되어 있다.

\---

## 1\. 배경과 목적

### 관심을 갖게 된 계기

자율주행 데이터를 시각화하는 프론트엔드 직무 공고를 접하면서 이 방향의 포트폴리오를 만들겠다는 생각을 시작했다. 해당 공고에서 요구하는 역량은 AI 데이터 플랫폼, 멀티모달 데이터, 3D 시각화, 어노테이션, 데이터 탐색 UI 등이었다.

### 현재 목표

**해당 공고는 이미 종료되었고, 지금 이 프로젝트의 목적은 특정 공고에 지원하기 위한 것이 아니다.**

현재의 목표는 다음 두 가지다.

* **3D 시각화와 데이터 처리 경험을 실제로 쌓는 것**
* **그 경험을 포트폴리오로 보여주는 것**

즉 "해당 공고에 얼마나 맞는가"가 아니라, "3D 시각화와 데이터 처리 역량을 포트폴리오에서 증명할 수 있는가"가 평가 기준이다.

## 2\. 나의 현재 상황과 제약 조건

### 기술 수준

* **React / Next.js**: 수준 높음. 호텔 예약 서비스, 쇼핑몰 포트폴리오를 TypeScript + Next.js로 구현한 경험 있음. API 연동, 라우팅, 전역 상태, 성능 최적화까지 경험 있음.
* **백엔드**: Nest.js로 쇼핑몰 프로젝트 구현 경험. AI 코딩 보조를 활용했지만, 의존성 주입, 동작 파이프라인 등 핵심 개념은 이해하고 있음.
* **3D 툴**: 경험 없음. Three.js, WebGL, React Three Fiber 등 3D 관련 기술을 처음 접함.
* **AI 데이터 도메인**: 경험 없음. Object Detection, Bounding Box, Point Cloud, 어노테이션 등의 개념은 이번에 처음 배움.
* **Zustand**: 사용 경험 없음. 개념은 이번 대화를 통해 이해함.

### 시간 제약

* **하루 10시간 학습 + 개발 가능**
* **2주 안에 완성 목표, 최대 3주**

### 도움 방식

* 강의 + AI(Claude 등) 도움을 받아서 제작 예정
* 포트폴리오이기 때문에, 가능한 한 AI 코딩 도움 없이 직접 구현하는 방향을 원함
* 시간이 부족해질 경우 어쩔 수 없이 AI 보조(바이브 코딩) 허용

### 도메인 학습 의지

* 데이터 시각화를 위해 필요한 도메인은 공부할 의향 있음
* 단, 시간 제한이 있으므로 필수적인 것만 요구할 것

## 3\. 왜 자율주행 데이터 전체를 다루지 않기로 결정했는가

자율주행 데이터 시각화 직무에서 요구하는 도메인은 다음과 같이 분류된다.

|분류|포함 개념|
|-|-|
|센서 데이터 계열|카메라 데이터, LiDAR 데이터, GPS, IMU|
|공간 표현 계열|포인트 클라우드, 바운딩 박스|
|시간 정렬 계열|센서 타임스탬프 동기화|
|AI 데이터 계열|AI 모델 학습 데이터, 어노테이션|

각 도메인 개념 요약:

* **카메라**: 사람의 눈처럼 이미지나 영상을 인식하는 데이터
* **LiDAR**: 레이저를 이용해 주변 물체까지의 거리와 3D 형태를 측정하는 데이터
* **GPS**: 차량의 전역 위치를 측정하는 데이터
* **IMU**: 가속도, 회전, 자세 변화를 측정하는 데이터

이 모든 도메인을 초보자가 2\~3주 안에 구현까지 함께 소화하기는 현실적으로 불가능하다. 따라서 자율주행 데이터의 방향성은 유지하되, **범용적인 AI 관련 데이터를 활용한 3D 시각화** 프로젝트로 범위를 좁히기로 결정했다.

## 4\. 확정된 프로젝트 방향

### 프로젝트명

**AI Object Detection Viewer**

### 한 줄 설명

AI 객체 탐지 결과를 3D 공간과 2D 이미지에서 동시에 탐색하는 데이터 시각화 뷰어

### 핵심 개념

AI 모델이 이미지를 보고 판단한 객체 탐지 결과를, 2D 이미지 뷰어와 3D 공간 뷰어에서 동시에 보여주는 도구. 사용자가 2D에서 객체를 클릭하면 3D에서도 같은 객체가 강조되고, 반대도 성립한다. 이것을 "멀티뷰 데이터 동기화"라고 부른다.

## 5\. 확정된 기술 스택

### 프레임워크 / 언어

|스택|역할|
|-|-|
|Next.js|앱 전체 프레임워크|
|TypeScript|전체 언어. 데이터 구조를 타입으로 명확히 정의|

### 3D 시각화

|스택|역할|선택 이유|
|-|-|-|
|Three.js|3D 렌더링 엔진. WebGL 기반|웹 3D의 사실상 표준|
|React Three Fiber (R3F)|Three.js를 React 방식으로 사용하는 래퍼|React 생태계와 자연스럽게 연동, Zustand와 직접 연동 가능, 메모리 관리 자동화|
|@react-three/drei|R3F 편의 기능 모음|OrbitControls, CameraControls 등 한 줄로 사용 가능|

> \*\*R3F 선택 근거\*\*: Three.js 직접 사용은 React와의 렌더링 루프 충돌, 메모리 수동 관리, Zustand 상태 동기화 코드를 별도 작성해야 하는 문제가 있다. R3F는 이 모든 것을 React 방식으로 자동 처리한다. 타협이 아니라 React + 3D 조합에서 현업 기준으로도 합리적인 선택이다. R3F를 배우는 것은 곧 Three.js 핵심 개념(geometry, material, camera, lighting)을 배우는 것이기도 하다.

### 상태 관리

|스택|역할|
|-|-|
|Zustand|전역 상태 관리. 선택된 프레임, 선택된 객체, 필터 값을 2D/3D 컴포넌트가 공유|

### UI / 스타일

|스택|역할|
|-|-|
|Tailwind CSS|레이아웃, 패널, 버튼 등 UI 스타일링|
|Recharts|confidence 분포 등 간단한 통계 차트|
|SVG / CSS absolute|2D 이미지 위 바운딩 박스 오버레이|

### 데이터

|항목|내용|

|데이터 출처|MS COCO val2017 subset (10 images, person/bicycle/car, 실제 ground-truth bbox)|

> \*\*TanStack Query 제거 결정\*\*: 로컬 파일 또는 정적 JSON을 사용하는 단계에서 불필요. 추후 Nest.js API 연동 시점에 도입 여부 결정.

```

│ AI Object Detection Viewer                             │
├────────────────────────────────────────────────────────┤
│                                                        │
│            3D Scene Viewer (메인 뷰, 화면 절반 이상)     │
│    · · · · ·      ┌──── car ────┐                      │
│     · · ·         │             │  ← OrbitControls     │
│        · ·        └─────────────┘    회전/확대/축소      │
│                                                        │
├──────────────────────┬─────────────────────────────────┤
│  2D Image Panel      │  Object List                    │
│  \[이미지]             │  car    92%  ←→ 3D 연동         │
│  ┌── person ──┐      │  person 88%                     │
│  └────────────┘      │  bicycle 76%                    │
├──────────────────────┴─────────────────────────────────┤
│ Timeline:  ◄ Frame 001 ── Frame 002 ── Frame 003 ►     │
└────────────────────────────────────────────────────────┘
```

## 9\. 마우스 이벤트 정리

3D 뷰어에서 발생하는 마우스 이벤트는 이 프로젝트의 핵심 기능 중 하나다.

|이벤트|용도|처리 방식|
|-|-|-|
|드래그|씬 회전|OrbitControls 자동 처리|
|휠|줌인/줌아웃|OrbitControls 자동 처리|
|클릭|객체 선택 → 2D 동기화|raycaster + Zustand 업데이트|
|호버|객체 강조 효과|onPointerOver (선택 구현)|

> raycaster: 마우스 클릭이 3D 공간의 어떤 오브젝트에 닿았는지를 감지하는 기술.

## 10\. Zustand store 설계 방향

2D 뷰어, 3D 뷰어, 객체 목록, 필터, 타임라인이 모두 공유하는 전역 상태.

```typescript
{
  // 지금 어떤 프레임을 보고 있는가
  selectedFrameId: string | null,

  // 지금 어떤 객체가 선택되어 있는가 (2D와 3D가 공유하는 핵심)
  selectedObjectId: string | null,

  // confidence 슬라이더 값 (0~1)
  confidenceThreshold: number,

  // 어떤 클래스를 보여줄 것인가 (Set으로 O(1) 조회)
  visibleClasses: Set<string>,
}
```

`selectedObjectId` 하나가 바뀌면 2D 뷰어, 3D 뷰어, 오브젝트 리스트가 동시에 반응한다. 이것이 멀티뷰 동기화의 핵심 구조다.

## 11\. 내부 데이터 타입 설계

```typescript
// 실제 구현 타입 (architecture.md가 정본)
type Detection2D = {
  id: string;
  class: string;      // COCO category name ("person" | "bicycle" | "car" 등)
  confidence: number;
  bbox: { x: number; y: number; width: number; height: number };
};

type Detection3D = {
  id: string;         // Detection2D.id와 동일 — 2D/3D 동기화의 핵심
  class: string;
  confidence: number;
  bbox3D: { center: [number, number, number]; size: [number, number, number] };
};

type Point3D = {
  x: number;
  y: number;
  z: number;
  intensity?: number;
};

type Frame = {
  id: string;
  imageUrl: string;
  imageWidth: number;   // 원본 이미지 픽셀 너비 (SVG viewBox 기준)
  imageHeight: number;  // 원본 이미지 픽셀 높이 (SVG viewBox 기준)
  detections2D: Detection2D[];
  detections3D: Detection3D[];
  pointCloud: Point3D[];
};
```

Detection2D.id === Detection3D.id → 같은 객체. 클릭 시 양쪽 뷰어에서 동시 하이라이트.

## 12\. 기능 우선순위

### 반드시 구현 (MVP)

1. COCO annotation JSON 파싱 및 내부 타입 변환
2. 프레임 리스트 + 프레임 선택
3. 이미지 위 2D 바운딩 박스 표시 (SVG)
4. **3D 뷰어 — point cloud + 3D bounding box + OrbitControls**
5. **2D ↔ 3D 객체 선택 동기화** (raycaster + Zustand)
6. 객체 목록 패널 (class, confidence 표시)
7. Confidence threshold 슬라이더 필터
8. Class 필터
9. 프레임 타임라인

### 하면 좋은 추가 기능 (시간 여유 시)

1. 프레임 자동 재생
2. Point cloud 색상 인코딩 (depth 값 → 색상 그라디언트)
3. 객체 통계 차트 (Recharts)
4. 호버 시 강조 효과 (onPointerOver)

### 포함하지 않는 것

* TanStack Query
* Annotation 수정 UI 흉내 (저장 안 되는 UI)
* JSON inspector
* 실시간 스트리밍, 회원가입, DB 설계

### 1주차 후반 (Day 4\~7): R3F 학습 집중

* Day 4\~5: R3F 공식 문서 + 강의. Scene, Camera, Geometry, Material, OrbitControls 기초
* Day 6\~7: Three.js BufferGeometry 기반 point cloud 렌더링 실습

## 14\. 확장 가능한 추가 기능 (프로젝트가 일찍 끝났을 경우)

MVP 완성 후 시간이 남는다면 다음 순서로 확장을 고려한다.

### 우선순위 높음

**KITTI 데이터셋 연동**
현재 프로젝트는 COCO 2D 어노테이션에서 3D 좌표를 추정하는 구조다. KITTI는 자율주행 공개 데이터셋으로 실제 3D 좌표(LiDAR 기반)를 포함한다. KITTI를 연동하면 "추정값"이 아닌 "실제 3D 데이터"를 시각화하는 것으로 프로젝트 완성도가 한 단계 올라간다. 포트폴리오 설득력도 크게 높아진다.

### 우선순위 중간

**Nest.js 백엔드 API 연동**
현재는 로컬 JSON 파일을 사용한다. Nest.js로 간단한 API 서버를 만들고 프레임 데이터를 서버에서 받아오는 구조로 전환하면 풀스택 경험을 추가할 수 있다.

**프레임 자동 재생 시 3D 애니메이션**
프레임이 넘어갈 때마다 객체의 x, y, z 좌표값이 바뀌면서 객체가 이동하는 것처럼 보이는 효과. R3F의 `useFrame` 훅으로 구현 가능. 물리 기반 애니메이션이 아니므로 추가 라이브러리 없이 구현 가능.

### 우선순위 낮음

**여러 AI 모델 결과 비교 뷰**
모델 A vs 모델 B의 탐지 결과를 나란히 표시. AI 데이터 플랫폼 직무와 연결성이 높아진다.

**Annotation 편집 기능**
바운딩 박스를 드래그로 수정하고 로컬 스토리지에 저장. "흉내"가 아닌 실질적인 저장까지 구현할 경우에만 포트폴리오에 어필 가능.

## 15\. 이력서 / 포트폴리오 어필 포인트

### 어필할 수 있는 역량

**1. 데이터 처리 역량**
COCO라는 실제 공개 데이터셋의 포맷을 파악하고, 파싱 로직을 직접 작성하고, 내부 타입으로 변환하고, 2D 좌표에서 3D 좌표를 추정하는 변환 로직까지 설계한다. 프론트엔드 개발자가 "데이터를 다룰 줄 안다"는 것을 보여줄 수 있는 흔치 않은 경험.

**2. 상태 관리 설계 역량**
2D 뷰어, 3D 뷰어, 객체 목록 패널, 필터, 타임라인이 모두 같은 상태를 공유하며 동시에 반응한다. "여러 뷰가 하나의 상태를 기준으로 어떻게 동기화되는가"를 설계한 경험.

**3. 3D UI 구현 경험**
주니어 포트폴리오에서 3D를 직접 구현한 사례 자체가 드물다. 단순히 3D 오브젝트를 띄우는 수준이 아니라, 클릭 이벤트, 선택 상태 반영, 색상 인코딩까지 인터랙션이 있는 3D 씬을 만든 것은 차별점이 된다.

**4. AI 데이터 도메인 이해도**
Object Detection, 어노테이션, confidence score, point cloud 같은 개념을 실제로 다뤄본 경험. AI 데이터 플랫폼, 데이터 시각화 도구, 디지털 트윈 관련 직무에서 이 경험은 눈에 띈다.

### 이력서 스택란 표기

```
Next.js / TypeScript / React Three Fiber(Three.js) / Zustand / Tailwind CSS
```

숙련도 표시가 있다면 Three.js / R3F는 5점 만점에 2\~3점이 정직하다.

### 포트폴리오 프로젝트 설명란 표기

```
- COCO annotation 포맷 파싱 및 TypeScript 타입 변환
- Three.js BufferGeometry 기반 point cloud 렌더링
- 3D bounding box 및 2D 바운딩 박스 동시 시각화
- Zustand 기반 2D↔3D 객체 선택 멀티뷰 동기화
- Confidence threshold / class 기반 필터링
- raycaster 기반 3D 오브젝트 클릭 이벤트 처리
```

스택란은 짧고 명확하게, 실제 역량은 구현 내용으로 증명하는 구조.

### 피해야 할 표현

* "숙련" "능숙" "중급 이상" → 면접에서 깊은 질문이 들어오면 신뢰가 깎임
* "입문" "기초" → 스스로 깎아내리는 표현

## 16\. 설계도 작성을 위한 판단 기준

다음 사항들이 설계도에 반드시 포함되어야 한다.

1. **3D 좌표 처리 방식 구체화**: 옵션 A(2D bbox에서 z값 추정) 채택 확정. 구체적인 추정 로직 설계 필요.
2. **Point cloud 데이터 생성 방식**: COCO 이미지 기반으로 depth 추정 좌표 배열을 어떻게 자동 생성할 것인가.
3. **폴더 구조 및 컴포넌트 설계**: 각 컴포넌트의 역할과 의존 관계.
4. **데이터 흐름**: COCO JSON 파싱 → 내부 타입 변환 → 뷰어 렌더링의 전체 흐름.
5. **Zustand store 구체적 구조**: 위 초안을 기반으로 실제 구현 가능한 수준의 store 설계.
6. **3D 씬 구성 세부 설계**: 카메라 초기 위치, 조명 종류, 좌표계 기준.
7. **raycaster 기반 클릭 이벤트 처리 전략**: 3D 오브젝트 클릭 → Zustand 업데이트 → 2D 반응의 구체적 구현 방법.
8. **구현 순서와 의존 관계**: 어떤 것을 먼저 만들어야 다음 것을 만들 수 있는가.
9. **예상 난이도 병목 구간과 대응 방법**.

## 17\. 테스트 전략

> 이 절은 **테스트 전략의 설계 의도(왜 이렇게 결정했는가)**만 담는다. 운영 규칙(파일 위치, Step별 작성 항목, 작성 규칙)은 `CLAUDE.md`, `.claude/docs/architecture.md`, `.claude/docs/mvp-checklist.md`에서 관리한다.

### 기본 방침

* **유닛 테스트 우선, 통합 테스트는 나중**. 통합 테스트는 핵심 데이터 흐름이 두 단계 이상 연결되는 시점, 구체적으로 Step 5(2D ↔ 3D 객체 선택 동기화)부터 시작한다.
* **UI 컴포넌트 렌더링 테스트는 MVP에서 제외**한다. 렌더링은 수동 확인이 더 빠르고, 3D 뷰어는 WebGL 기반이라 JSDOM에서 실질적으로 테스트가 어렵다.
* **검증 대상은 데이터 계약과 불변 조건**이다. COCO 파싱(`lib/coco/`), 2D → 3D 좌표 변환(`lib/geometry/`), 상태 액션·셀렉터(`store/`) 같은 **순수 비즈니스 로직**만 테스트한다.
* **모든 코드를 무리하게 테스트하지 않는다.** 변경 가능성이 높거나 Immutable Rule(예: `Detection2D.id === Detection3D.id`, `selectedObjectId`가 선택의 단일 진실 공급원)이 걸린 모듈만 테스트한다.

### 이 전략을 채택한 이유

이 프로젝트의 핵심 가치는 "여러 뷰가 한 상태에 동기화되는 데이터 계약"에 있다. 그 계약을 코드로 잠가두면 리팩토링 안전성이 올라가고, 포트폴리오 측면에서도 "테스트 경계를 의식적으로 결정했다"는 신호가 된다. 반대로 컴포넌트 렌더링·시각적 회귀까지 테스트하면 시간 소모 대비 얻는 게 작고, 3D 영역은 WebGL 의존성 때문에 ROI가 더 낮다.

### 도구

**Vitest**를 사용한다. Next.js + TypeScript와 자연스럽게 동작하고 jest API와 호환된다. Step 1의 마지막 작업으로 도입한다. React 컴포넌트 테스트 라이브러리(`@testing-library/react`)는 MVP 동안 도입하지 않는다.

### 상세 규칙이 살아 있는 위치

|무엇을 찾을 때|어디를 본다|
|-|-|
|Step별로 어떤 테스트를 작성해야 하는가|`.claude/docs/mvp-checklist.md`의 각 Step "Tests" 하위 항목|
|레이어별 테스트 경계, 잠가야 할 불변 조건, 테스트 파일 위치|`.claude/docs/architecture.md`의 "Testing Boundaries"|
|일상 작업에서 지켜야 할 짧은 규칙 요약|`CLAUDE.md`의 "Testing Policy"|

이 절은 설계 의도만 담는다. 위 세 문서가 운영 규칙의 정본이며, 의도와 운영 규칙이 어긋날 경우 **운영 규칙 쪽을 먼저 갱신**한다.

## 요청문

이 내용을 바탕으로 구체적인 프로젝트 설계도를 만들어줘.

설계도에는 다음이 포함되어야 한다.

* 3D 좌표 처리 방식 (2D bbox → 3D 좌표 추정 로직 구체화)
* Point cloud 데이터 생성 방식
* 폴더 구조 및 주요 컴포넌트 설계 (각 컴포넌트의 역할과 의존 관계 포함)
* 데이터 흐름 전체 설계 (COCO JSON 파싱 → 내부 타입 변환 → 뷰어 렌더링)
* Zustand store 구체적 구조 (실제 코드 수준)
* 3D 씬 구성 세부 설계 (카메라, 조명, 좌표계)
* raycaster 기반 클릭 이벤트 처리 전략
* 2D ↔ 3D 동기화 구현 전략 전체 흐름
* 기능별 구현 순서와 의존 관계
* 예상 난이도 병목 구간과 대응 방법
* MVP 완성 후 확장 기능 설계 방향 (KITTI 연동, 백엔드 연동 등)

위 내용이 불충분하거나 더 나은 방향이 있다고 판단된다면, 현재 목표("3D 시각화와 데이터 처리 경험을 포트폴리오로 증명하는 것")에 더 잘 맞는 프로젝트 방향을 먼저 제안해도 좋다.

단, 제안을 하는 경우에도 구체적인 설계도까지 함께 만들어줘.
나는 초보자이므로 설명은 항상 초보자 기준으로 풀어서 설명해줘.
전문 용어가 나올 경우 반드시 그 용어가 무엇인지 함께 설명해줘.
